### List menu — Remove from List
- **Area:** Menus

- **Entry point:** Menu bar **List > Skip Selected now** ([frontend/src/components/MenuBar.tsx](../../frontend/src/components/MenuBar.tsx)), handled by `handleRemoveFromListSelected` in [frontend/src/App.tsx](../../frontend/src/App.tsx).
- **Trigger:** User selects one or more file rows in the result tree and picks **List > Skip Selected now**.
- **Behaviour:** Calls `store.removeFromList(selectedPaths)` → `POST /api/remove` → `remove_from_review` ([core/app_service/execute_service.py](../../core/app_service/execute_service.py)), which finalizes `outcome='ignored'` for those rows (the files stay on disk) and returns the reloaded review groups. The store replaces the tree's groups with them and clears the selection, so the rows drop out of the view at once under `R-SKIP-1`, with no save step. If the remove leaves a group with a single member, the store then runs the singleton-prune offer (see [Singleton-prune offer after destructive ops (#426)](execute-action.md#singleton-prune-offer-after-destructive-ops-426)). This is the immediate path; it is distinct from the staged, reversible **Skip** decision set by the row control or by [Bulk regex — remove from list (deferred decision)](bulk-operations.md#bulk-regex--remove-from-list-deferred-decision).
- **Conditions / variants:** Works with single or multi-select. Lock-aware: the server re-reads each row's lock state from the manifest and is refused under `R-LOCK-1` if any target is locked; the store then opens the lock-confirm dialog, whose force option is `R-LOCK-5`, and whose **Unlocked Only** option re-runs the remove without the locked rows (see [Execute Action — lock-confirm dialog](execute-action.md#execute-action--lock-confirm-dialog)). The route rejects a path outside the allowed roots before any write. The result-tree right-click **Skip now — drop from this review** item and the Execute dialog's remove (behind its own confirm) call the same `store.removeFromList`.
- **Web parity (#678-D):** the web MenuBar carries the same **List → Skip Selected now** entry (labelled "Remove from List" until the 2026-09-18 vocabulary decision; it finalizes `outcome='ignored'` on the spot, so it carries the immediacy marker the reversible row control does not) (`menu-list` / `menu-list-remove-from-list`, [MenuBar.tsx](../../frontend/src/components/MenuBar.tsx)), wired to the SAME `store.removeFromList` path as the web context menu — finalizes `outcome='ignored'` immediately (the web has no dirty-flag/save step), lock-aware under `R-LOCK-1`. Web variant: with no selection the item is **disabled** (same gating idiom as Execute (only selected)) instead of Qt's "No items selected" QMessageBox; there is no "Removed N items" status-bar echo.
- **Web undo (#909):** both immediate Skip entry points — the result-tree context menu's **Skip now — drop from this review** (file and group variants) and **List → Skip Selected now** — still finalize under `R-SKIP-1`, and a successful skip now raises the single-slot undo toast (`main-toast`, the same slot as keep-best): *"N files dropped from this review · Undo"* / 「已從本次檢閱中移除 N 個檔案 · 復原」 (`web.toast.skip_now`), ~6 s, paused while hovered. **Undo** calls `POST /api/restore`, which returns exactly those rows from `outcome='ignored'` to `outcome=''` — a skip writes nothing else (no file I/O, no delete CSV, no decision or lock change), so the skipped rows come back with their staged decisions. If the singleton prune that follows a skip took the skipped row's partner (pref **always**, or **Prune** in the prune dialog while the toast is still up), Undo restores the partner too — otherwise the restored row would be a one-member group the tree never shows; a prune is only ever folded into the toast of the skip that started it. **One thing Undo does not put back:** a lock. If that partner was a **locked** singleton, the prune's lock dialog had to unlock it first (**Unlock & Apply**, its own confirmed step); Undo returns the partner to the review **unlocked**. The restore never touches a `deleted` row. A **locked** dismissed row is gated like every other locked action (`R-LOCK-1`, #981): Undo is refused with 409 `locked_paths`, nothing is written, and the lock-confirm dialog opens with `op` `restore` — **Unlock & Apply** restores the rows unlocked, **Unlocked only** restores the unlocked rows, and Cancel leaves the toast up. Loading another manifest (Open, or a scan that auto-loads) dismisses the toast — its rows live in the manifest that was loaded when it was raised. Not covered: the Execute dialog's Skip (already behind its own confirm, unchanged), and a skip refused under `R-LOCK-1` on a locked row (nothing is written; the lock dialog's retry — including Unlock & Apply — raises no toast).
- **Related:** Originally [PR #158](https://github.com/jackal998/photo-manager/pull/158); web menu entry #678-D; undo toast: [#909](https://github.com/jackal998/photo-manager/issues/909) (`frontend/src/store/useAppStore.ts` `removeFromList(…, { undoable })` / `undoSkipNow`, `core/app_service/execute_service.py::restore_to_review`). QA scenarios [`qa/web/scenarios/s20_multi_remove_from_list.py`](../../qa/web/scenarios/s20_multi_remove_from_list.py) and [`qa/web/scenarios/s21_list_menu_remove.py`](../../qa/web/scenarios/s21_list_menu_remove.py); unit tests `frontend/src/store/useAppStore.test.ts` (`removeFromList` success + 409 paths), `frontend/src/components/MenuBar.test.tsx`, `tests/test_web_execute_service.py` (`remove_from_review`, and `TestRestoreToReview` for the undo).

### Log menu
- **Area:** Menus

- **Entry point:** None — removed with the desktop client in #646. The web menu bar has File / Action / List / View only ([frontend/src/components/MenuBar.tsx](../../frontend/src/components/MenuBar.tsx)), and the web API has no log endpoint.
- **Trigger:** None.
- **Behaviour:** The retired desktop client's **Log** menu opened the latest app log, the latest delete log, or either log directory in the OS default application. The web offers no way to open them. The shared backend still writes both kinds of file, so they can be opened by hand. Every launch through `launcher.py` (the app's only entry point) calls `infrastructure.logging.init_logging()`, which writes a rotating loguru log `app_YYYYMMDD.log` (INFO level, 10 MB rotation, 10-day retention, zip-compressed) under `%USERPROFILE%\AppData\Local\PhotoManager\logs`. Every web **Execute** run that attempts at least one delete writes an audit CSV `delete_<YYYYMMDD_HHMMSS>.csv` under `%LOCALAPPDATA%\PhotoManager\delete_logs`, with the columns `GroupNumber, FilePath, Success, Reason`, through the shared `write_delete_log` (called from `execute_decisions` in [core/app_service/execute_service.py](../../core/app_service/execute_service.py)). `POST /api/execute` returns that CSV's path as `log_path`, but no web UI shows it.
- **Conditions / variants:** The web CSV records every successful delete, every failed delete (including a path refused as `outside_allowed_roots`), and every file that left the disk but whose `outcome` write failed (recorded as success, reason `outcome write failed`). Its `GroupNumber` is always `0`. Files already missing at execute time and rows finalized as Skip (`outcome='ignored'`) are not recorded, and a run with no delete attempt writes no CSV. A failed CSV write is logged and leaves `log_path` `null`; the execute itself still succeeds. No test pins the web execute path's CSV; `tests/test_delete_service.py` covers `write_delete_log` through `DeleteService`. Exposing the logs through the browser would need a product decision plus new endpoints and a menu.
- **Related:** QA scenario `s18_log_menu` — `status: skip` in [qa/web/scenario_map.yml](../../qa/web/scenario_map.yml) (no web equivalent surface). Delete-audit CSV for the UI delete path: #505. Log helpers in `infrastructure/logging.py`; launcher start-up in [launcher.py](../../launcher.py) (see [Web — desktop shell (pywebview launcher)](web-ui.md#web--desktop-shell-pywebview-launcher)).
