### Empty-state action buttons
- **Area:** Main window

- **Entry point:** The main area's empty state (`main-empty-state`, rendered by [frontend/src/App.tsx](../../frontend/src/App.tsx) in place of the result tree) — the primary **Scan…** (`main-empty-scan`) and the secondary **Open Manifest…** (`main-empty-open`).
- **Trigger:** No manifest is loaded and none is loading — every fresh page load until a scan finishes or a manifest is opened.
- **Behaviour:** **Scan…** opens the Scan dialog (the same handler as **File → Scan Sources…**). **Open Manifest…** opens the filesystem picker in file mode (the same handler as **File → Open Manifest…**); confirming a file loads it. The buttons sit under a heading ("Find duplicate & similar photos") and one sentence on what the app does; only **Scan…** is filled (the single-primary rule, layout slice E). No "nothing is deleted" safety line and no recent-sources list are drawn — both owner decisions. The labels come from the `web.empty_state.*` keys, translated in zh_TW (`掃描…` / `開啟清單…`). The Scan label differs from its menu item (Scan… vs File → Scan Sources…); Open Manifest… reads the same as File → Open Manifest….
- **Conditions / variants:** The whole empty state is replaced by the result tree as soon as a manifest path is set; while a manifest is loading, the tree area shows "Loading manifest…" instead.
- **Related:** [PR #197](https://github.com/jackal998/photo-manager/pull/197) (closes [#137](https://github.com/jackal998/photo-manager/issues/137)); layout slice E of [#878](https://github.com/jackal998/photo-manager/issues/878) — computed sizes and colours under [Web — Daylight theme and results-tree framing](web-ui.md#web--daylight-theme-and-results-tree-framing); QA scenarios [`qa/web/scenarios/s41_empty_state_action_buttons.py`](../../qa/web/scenarios/s41_empty_state_action_buttons.py) (both buttons present; Scan opens `scan-dialog`, Open Manifest opens `fs-browser`) and [`qa/web/scenarios/s78_empty_state.py`](../../qa/web/scenarios/s78_empty_state.py) (the empty state at size, in both locales); unit [`frontend/src/App.test.tsx`](../../frontend/src/App.test.tsx) (composition, zh_TW, both handlers, the two deliberate absences).

- **Area:** Main window

- **Entry point:** None — removed with the desktop client in #646.
- **Trigger:** None on the web.

### Main window — close-during-scan confirm
- **Area:** Main window

- **Entry point:** `useBeforeUnloadGuard` ([frontend/src/hooks/useBeforeUnloadGuard.ts](../../frontend/src/hooks/useBeforeUnloadGuard.ts)), mounted once in `App`; the backend's cooperative cancel `POST /api/scan/{id}/cancel` ([app/web/routes/scan.py](../../app/web/routes/scan.py)) and the app's shutdown lifespan ([app/web/main.py](../../app/web/main.py)).
- **Trigger:** The user reloads, navigates away from or closes the page while `scan.status === "running"`; or closes the desktop-shell window while a scan runs.
- **Behaviour:** The browser gives a page no close event it can answer with its own Yes/No dialog, so the guard has two parts, both keyed on the live `scan.status` read via `getState()` when the event fires. (1) **Warn:** a `beforeunload` handler arms the browser's native Leave/Stay confirm (`preventDefault()` + `returnValue = ""`) only while a scan is running; idle / finished / failed / cancelled pages navigate freely. The browser owns the prompt's wording and buttons. (2) **Cancel on Leave ([#703](https://github.com/jackal998/photo-manager/issues/703)):** on a confirmed unload a `pagehide` handler sends a best-effort `navigator.sendBeacon('/api/scan/{id}/cancel')`, so the scan does not keep running with nobody watching it. The handler listens on `pagehide`, not on `beforeunload`, which fires before the user chooses and would cancel even on Stay, and not on `visibilitychange`, which fires on a tab switch. A bfcache stash (`e.persisted`) is skipped, and the call is optional-chained so the handler never throws where `sendBeacon` is missing. Closing the desktop-shell window shuts the embedded server down, and the lifespan shutdown requests cancel on every running scan and joins its thread for up to 5 s. The ScanDialog **Cancel** button uses the same endpoint. **What a cancel does in the backend:** the endpoint sets the task's cancel token, which the scan pipeline ([core/app_service/scan_runner.py](../../core/app_service/scan_runner.py)) polls at every stage boundary and inside its hot loops; the task then ends with `"Scan cancelled."` and the output manifest is never written. A cancel during HASH hard-kills the live exiftool processes (`ExiftoolProcess.kill`) before joining their consumer threads ([#561](https://github.com/jackal998/photo-manager/issues/561)). A consumer blocked inside a large batch read only checks the token between queue gets, so without the kill the join timed out and exiftool was left running. The EXIF drain after HASH is cancel-aware the same way (#607), so a cancel there does not wait out exiftool's 60 s read timeout. The bounded read and EXIF queues watch the token too, so a cancel cannot deadlock on a full queue (#564 / #594).
- **Conditions / variants:** **Hard exit (crash / Task Manager kill):** process-mode hash workers are placed in a Windows `KILL_ON_JOB_CLOSE` job object, so they die with the app instead of spinning the disks ([#460](https://github.com/jackal998/photo-manager/issues/460) / #549). The job assignment had been silently inert until [#555](https://github.com/jackal998/photo-manager/issues/555) fixed a handle-lifetime bug: `int(PyHANDLE)` dropped the OS handle before `AssignProcessToJobObject` ran. exiftool is jailed the same way only when the app is **not** already inside another job (`_process_in_any_job`, which fails safe to "in a job"; [#556](https://github.com/jackal998/photo-manager/issues/556) → [#558](https://github.com/jackal998/photo-manager/issues/558)). exiftool is a PAR self-extracting Perl exe whose child interpreter, a grandchild of the app, gets forced into a nested job chain and starved by the outer job's limits. That corrupted the extended EXIF pass under a CI runner / console host: `s42_scoring` NULL `exif_tag_count`. A bare-desktop hard exit reaps exiftool; a job-nested launch skips jailing and relies on the outer job's owner. **Residual (best-effort):** `sendBeacon` is best-effort by spec. If the browser drops it, the scan keeps running and finishes by itself; while it runs, the registry answers 409 to a new scan. A backend cancel-on-SSE-disconnect grace period is intentionally not built: the SSE stream deliberately does not cancel on disconnect, so a reconnecting page can resume.
- **Related:** issue [#468](https://github.com/jackal998/photo-manager/issues/468) (desktop origin), [#687](https://github.com/jackal998/photo-manager/issues/687) (web guard), #703 (cancel on leave). QA scenario [`qa/web/scenarios/s63_late_cancel_and_main_window_guard.py`](../../qa/web/scenarios/s63_late_cancel_and_main_window_guard.py) — asserts the `beforeunload` guard arms while a scan runs and is dormant when idle and after cancel (a non-vacuity bracket), plus a late HASH-stage cancel that stops cleanly and never writes the manifest; [`qa/web/scenarios/s03_cancel_scan.py`](../../qa/web/scenarios/s03_cancel_scan.py) (Cancel button). The `pagehide` → `sendBeacon` cancel is unit-covered in `frontend/src/hooks/useBeforeUnloadGuard.test.ts` (beacons only while running with a task id; never with a null task id, on a bfcache stash, or after unmount), since real navigation in Playwright is the `playwright#20624` CI-hang class. Backend: `tests/test_scan_pipeline.py` (HASH cancel kills exiftool, process-pool workers assigned to the kill job, post-HASH cancel exits promptly, bounded-queue cancel does not deadlock), `tests/test_scanner_exif.py` (job-nesting gate).

### Main window — column order/width persistence
- **Area:** Main window

- **Entry point:** The resize handle on the right edge of each result-tree column header ([frontend/src/components/result/ColumnHeaderRow.tsx](../../frontend/src/components/result/ColumnHeaderRow.tsx)), persisted by [frontend/src/lib/columnWidths.ts](../../frontend/src/lib/columnWidths.ts).
- **Trigger:** User drags a column's resize handle, or double-clicks it.
- **Behaviour:** The width follows the drag live and is written to `localStorage` (`pm.result-tree.column-widths.v1`) once, when the drag ends; a double-click on the handle restores that column's default width. Widths are read back when the store is created, so they survive a reload (`R-LAYOUT-1`) and a manifest load. Column **order** is fixed — the column registry's order is the render order, and the web has no drag-to-reorder (the retired desktop client let the user reorder columns). Floor, end-of-drag rules and the fill-column behaviour are in [Web — result-tree column sort and resize persistence](web-ui.md#web--result-tree-column-sort-and-resize-persistence).
- **Conditions / variants:** Storage is per browser profile and origin; Playwright contexts are isolated automatically, so QA needs no reset. In the desktop shell, `launcher.py` starts pywebview without `private_mode=False`, and pywebview's default private mode (WebView2 InPrivate) is documented not to preserve local storage, so there the widths are expected to reset on every launch (code-read, not live-verified; tracked as [#944](https://github.com/jackal998/photo-manager/issues/944)).
- **Related:** [PR #227](https://github.com/jackal998/photo-manager/pull/227) (closes [#214](https://github.com/jackal998/photo-manager/issues/214), desktop origin); web column model [#685](https://github.com/jackal998/photo-manager/issues/685); QA scenario [`qa/web/scenarios/s47_column_layout_persist.py`](../../qa/web/scenarios/s47_column_layout_persist.py); unit tests `frontend/src/lib/columnWidths.test.ts`.

### Main window — geometry + splitter persistence
- **Area:** Main window

- **Entry point:** The drag handle between the result tree and the preview pane (`preview-resize-handle`, [frontend/src/App.tsx](../../frontend/src/App.tsx)) and the title bars / corner grips of the full-res viewer, Execute dialog and Set Action dialog. The desktop-shell window itself is created by [launcher.py](../../launcher.py).
- **Trigger:** User drags the tree/preview boundary, or moves / resizes one of those overlays.
- **Behaviour:** The splitter's web analog is the preview-pane width. A drag is clamped to [200 px, 60% of the viewport], so a drag cannot squeeze either pane to invisibility (the [#136](https://github.com/jackal998/photo-manager/issues/136) guarantee); a stored width is not re-clamped on load or window resize; the default is 320 px, and the width is stored in localStorage under `panelWidths` — see [Web — preview panel resizable + persistence](web-ui.md#web--preview-panel-resizable--persistence). Each overlay keeps its own position (and, once resized, size) — see [Web — overlay window geometry (movable / resizable / persisted)](web-ui.md#web--overlay-window-geometry-movable--resizable--persisted). The app window has no persisted geometry: the desktop shell always opens a 1280×800 window, and in a browser tab the browser owns the window.
- **Conditions / variants:** Same storage caveat as [Main window — column order/width persistence](#main-window--column-orderwidth-persistence): localStorage is per browser profile and origin, and under the desktop shell's pywebview private mode it is expected not to survive a relaunch (code-read, not live-verified; tracked as [#944](https://github.com/jackal998/photo-manager/issues/944)).
- **Related:** [PR #191](https://github.com/jackal998/photo-manager/pull/191) (closes [#141](https://github.com/jackal998/photo-manager/issues/141), [#136](https://github.com/jackal998/photo-manager/issues/136), desktop origin); web preview resize [#739](https://github.com/jackal998/photo-manager/issues/739). QA scenarios [`qa/web/scenarios/s39_layout_persist.py`](../../qa/web/scenarios/s39_layout_persist.py) (preview width + viewer geometry) and [`qa/web/scenarios/s48_dialog_geometry_persist.py`](../../qa/web/scenarios/s48_dialog_geometry_persist.py) (both dialogs); unit tests `frontend/src/lib/panelWidths.test.ts`, `frontend/src/App.previewResize.test.tsx`.

### Main window — keyboard navigation
- **Area:** Main window

- **Entry point:** The main result tree's scroll container (`main-result-tree`, `role="tree"`, `tabIndex=0`, [frontend/src/components/ResultTree.tsx](../../frontend/src/components/ResultTree.tsx)) for the arrow-key cursor, and a document-level hook ([frontend/src/hooks/useDecisionShortcuts.ts](../../frontend/src/hooks/useDecisionShortcuts.ts), mounted once by [frontend/src/App.tsx](../../frontend/src/App.tsx)) for the `d` / `k` decision shortcuts.
- **Trigger:** With the tree focused, press ArrowDown / ArrowUp. Outside a text field and with no dialog or menu open, press bare `d` or `k`.
- **Behaviour:**
  - **Decision shortcuts ([#615](https://github.com/jackal998/photo-manager/issues/615), web [#708](https://github.com/jackal998/photo-manager/issues/708)).** Bare `d` sets the current selection's decision to `delete`; bare `k` clears it to `''` (no decision / keep). Both drive the same `store.setDecisions` the multi-select context menu uses, so a multi-selection is written in one `PATCH /api/decision`, and a locked row in it opens the lock-confirm dialog. Modifier-bearing presses (Ctrl/Cmd, Alt, Shift) fall through. The shortcuts are inert while an editable field (input, textarea, select, contenteditable) has focus or while any modal layer is open (`[role="dialog" | "alertdialog" | "menu"]`, which covers every dialog and the context menus), and with an empty selection they do nothing.
  - **Roving arrow-key cursor ([#709](https://github.com/jackal998/photo-manager/issues/709)).** ArrowDown / ArrowUp move the cursor through the tree in visible row order, group headers included; the first press starts at the top (Down) or the bottom (Up), and the ends clamp. The rows are virtualized, absolutely positioned, non-focusable `<div>`s, so the scroll container keeps DOM focus and names the active row with `aria-activedescendant`, pointing at the row's `role="treeitem"` wrapper; the attribute is dropped while the active row is virtualized out of the DOM, so it never names a missing element. Landing on a **file row** does what a click does (`setSelection` + `setSelectedFile`), so the preview pane and `d` / `k` follow the cursor. Landing on a **group header** selects the group for the grid preview without expanding or collapsing it, and **clears the file selection** — a header is not part of the multi-selection model (see [Web — main result tree multi-selection](web-ui.md#web--main-result-tree-multi-selection)), so `d` / `k` are no-ops there and a decision can never land on a row the user has visibly moved off; clicking a header does the same. Arrowing back onto a file row re-selects it. The cursor is held as a row identity, so it survives a manifest rebuild (a decision write replaces `manifest.groups` wholesale), and it also moves to a clicked row (under any modifier), a right-clicked row, and the first keeper the post-scan auto-select scrolls to. The active row is kept on screen with `virtualizer.scrollToIndex(…, {align: "auto"})`, and the virtualizer is given `scrollPaddingStart` = the measured sticky-header height ([#699](https://github.com/jackal998/photo-manager/issues/699)), so a row scrolled in from above comes to rest at the header's bottom edge instead of underneath it. Modifier-bearing arrows fall through, and the handler is scoped to the tree container, so arrows typed in any input elsewhere never move the cursor.
  - **The cursor is visible (layout slice T, 2026-09-18).** `aria-activedescendant` is heard by a screen reader but not seen, so the cursor row draws a **2 px inset terracotta ring** (`outline: 2px solid #a85a2c; outline-offset: -2px; border-radius: 6px`) plus a **▸ caret** in the row's existing left gutter. Fill = state, stroke = cursor: the ring composes over the selection and hover tints rather than replacing them, so a row can be focused *and* selected. The caret is `aria-hidden` and is what carries the cursor in grayscale and for colour-blind users; it sits inside padding the row already had, so no row moves by a pixel. Both are `:focus-visible`-gated through the scroll container (`group-focus-visible:`) — DOM focus never moves onto a row — so a mouse user never sees the ring, and it never lands on the row's decision control.
- **Conditions / variants:** Group headers are also Tab stops (`role="button"`); Enter or Space toggles one that has DOM focus. Not provided: Shift+arrow range extension, Home / End / PageUp / PageDown and Left / Right expand-collapse do not move the cursor; there is no play/pause key (video uses the player's native controls), and no Alt+F menu mnemonic — Radix and the browser own dialog focus, Esc and Tab order.
- **Related:** QA scenario [`qa/web/scenarios/s26_keyboard_navigation.py`](../../qa/web/scenarios/s26_keyboard_navigation.py) (branches A–C: `d` / `k` on a single and a multi-selection; branch D: the roving cursor, the group-header stop and the below-header scroll-in) and [`qa/web/scenarios/s74_daylight_theme.py`](../../qa/web/scenarios/s74_daylight_theme.py) (the ring's computed outline and offset and the caret, after a real key press); unit [`frontend/src/hooks/useDecisionShortcuts.test.ts`](../../frontend/src/hooks/useDecisionShortcuts.test.ts) (modifier, editable-field and open-modal guards) and [`frontend/src/components/ResultTree.keyboard.test.tsx`](../../frontend/src/components/ResultTree.keyboard.test.tsx) (cursor order, header stop, rebuild survival, which row carries the ring).

### Main window — results tree double-click
- **Area:** Main window

- **Entry point:** File rows and group-header rows of the main result tree — `onDoubleClick` on [frontend/src/components/result/FileRow.tsx](../../frontend/src/components/result/FileRow.tsx) and `onClick` on [frontend/src/components/result/GroupRow.tsx](../../frontend/src/components/result/GroupRow.tsx), wired in [frontend/src/components/ResultTree.tsx](../../frontend/src/components/ResultTree.tsx).
- **Trigger:** The user double-clicks a file row, or clicks a group-header row.
- **Behaviour:** **File row** → opens the in-app full-resolution viewer (`fullres-dialog`, [frontend/src/components/FullResViewer.tsx](../../frontend/src/components/FullResViewer.tsx)) on that file via `store.openFullRes`; the double-click's first click has already selected the row. An image opens at native resolution with drag-to-pan and Ctrl+wheel zoom; a video opens in a native-controls player without autoplay — see [Preview pane — full-resolution viewer](preview-pane.md#preview-pane--full-resolution-viewer). The retired desktop client opened the file in the OS default viewer instead. **Group-header row** → toggles expand/collapse on a single click (it has no double-click handler), and the same click makes the group the preview target (grid view) while clearing the file selection.
- **Conditions / variants:** Double-clicking the preview pane's image, or an image tile in its grid view, opens the same viewer (see [Preview pane — full-resolution viewer](preview-pane.md#preview-pane--full-resolution-viewer) for what a video does). Enter or Space toggles a group header that has keyboard focus. Revealing the file in Explorer is the right-click **Open folder**, not a double-click.
- **Related:** Originally [PR #198](https://github.com/jackal998/photo-manager/pull/198) (closes [#143](https://github.com/jackal998/photo-manager/issues/143)); QA scenarios [`qa/web/scenarios/s05_huge_preview.py`](../../qa/web/scenarios/s05_huge_preview.py) (row double-click → the full-res image loads), [`qa/web/scenarios/s68_full_res_viewer_double_click.py`](../../qa/web/scenarios/s68_full_res_viewer_double_click.py) (preview-tile double-click → the viewer opens; Esc closes it) and [`qa/web/scenarios/s40_results_tree_double_click.py`](../../qa/web/scenarios/s40_results_tree_double_click.py) (group-header click collapses and re-expands — `aria-expanded` plus member-row visibility); unit [`frontend/src/components/result/GroupRow.test.tsx`](../../frontend/src/components/result/GroupRow.test.tsx) (toggles on a row click and on Enter) and [`frontend/src/components/PreviewPane.test.tsx`](../../frontend/src/components/PreviewPane.test.tsx) (preview double-click calls `openFullRes`).

### Main window — row selection (no horizontal auto-scroll)
- **Area:** Main window

- **Entry point:** None — removed with the desktop client in #646.
- **Trigger:** None.
- **Behaviour:** The desktop result tree turned off its toolkit's auto-scroll so that selecting a row no longer jerked a horizontally scrolled table sideways. The web tree has no such auto-scroll to turn off: a row click updates only the selection, the preview target and the keyboard cursor, with no scroll call, and the tree's two programmatic scrolls — the arrow-key cursor keeping its row in view ([#709](https://github.com/jackal998/photo-manager/issues/709)) and the one-shot scroll to the first keeper after a scan — go through a vertical-only virtualizer, so neither moves the horizontal position.
- **Conditions / variants:** The web table does scroll horizontally once its columns outgrow the pane (File Name keeps its floor width, then the table scrolls; the sticky column header scrolls sideways with it).
- **Related:** [frontend/src/components/ResultTree.tsx](../../frontend/src/components/ResultTree.tsx); keyboard cursor under [Main window — keyboard navigation](#main-window--keyboard-navigation).

### Main window — sort persistence within session
- **Area:** Main window

- **Entry point:** The **File Name**, **Size** and (since [#923](https://github.com/jackal998/photo-manager/issues/923)) **Action** header cells of the result tree ([frontend/src/components/result/ColumnHeaderRow.tsx](../../frontend/src/components/result/ColumnHeaderRow.tsx)), which call `store.toggleSort`; the chosen column and direction live in the `resultView` slice of [frontend/src/store/useAppStore.ts](../../frontend/src/store/useAppStore.ts).
- **Trigger:** User clicks a sortable column header.
- **Behaviour:** The first click on a column sorts ascending; a repeat click flips the direction (the Action header instead cycles Keep first → Delete first → clear — see [Web — sort by decision](web-ui.md#web--sort-by-decision-action-header)). The sort orders rows within each group (group order is unchanged) and is re-applied from the store on every render. It therefore survives every refresh of the loaded rows within the page session — a decision change, an execute run, re-opening a manifest — because loading a manifest replaces the groups but keeps the sort column and direction in `resultView` (an Action sort re-takes its decision snapshot from the loaded rows, so it starts fresh). With no sort chosen, rows keep the server's score-descending order within each group (see [Keep-worthiness scoring](review.md#keep-worthiness-scoring)); the client sort is stable, so rows that tie under a column sort keep that score order. Full detail: [Web — result-tree column sort and resize persistence](web-ui.md#web--result-tree-column-sort-and-resize-persistence).
- **Conditions / variants:** Session-only by design: the sort is not stored anywhere, and a page reload or relaunch returns to server order. The sortable columns are those `R-SORT-1` names (Action since [#923](https://github.com/jackal998/photo-manager/issues/923), with its own Keep first → Delete first → clear cycle — see [Web — sort by decision](web-ui.md#web--sort-by-decision-action-header)); `R-SORT-2` covers the others.
- **Related:** [#121](https://github.com/jackal998/photo-manager/issues/121) (desktop origin); web column model [#685](https://github.com/jackal998/photo-manager/issues/685); QA scenario [`qa/web/scenarios/s45_sort_persistence.py`](../../qa/web/scenarios/s45_sort_persistence.py) (per-group sort, checked against a SQL oracle, surviving an in-session manifest reopen); unit tests `frontend/src/lib/resultColumns.test.ts`.

### Main window — status bar baseline
- **Area:** Main window

- **Entry point:** The footer [frontend/src/components/StatusBar.tsx](../../frontend/src/components/StatusBar.tsx): the resting message is testid `main-status-bar`, inside the 30 px strip `main-status-strip`; its text (`statusText`) is computed in [frontend/src/App.tsx](../../frontend/src/App.tsx) and passed in.
- **Trigger:** Always present; recomputed on every render from the `manifest` and `scan` store slices.
- **Behaviour:** Five mutually exclusive states, first match wins. A loaded manifest shows `"{groups} {groupWord} · {files} {fileWord}"`, with singular or plural picked per count, so a one-group manifest reads "1 group · 1 file" rather than "1 groups · 1 files" (copy audit S1). `manifest.loading` shows "Loading manifest…". A running scan shows "Scanning" plus the localized stage name (#740). A failed scan shows "Scan failed: {error}". Otherwise the bar shows "Ready". Because the text is derived state rather than a timed message, it cannot expire to blank. That rules out the failure class the retired desktop client fixed in [#138](https://github.com/jackal998/photo-manager/issues/138) (the startup message vanished after 3 s) and [#140](https://github.com/jackal998/photo-manager/issues/140) (a menu hover wiped the load summary). With a manifest loaded, the strip also shows #906's "⊗ N marked to delete" count and "↺ reclaims {size}" total, computed over the whole manifest and shown at zero too. A **Density** switch sits at the right end of the strip.
- **Conditions / variants:** Two additive error lines render **below** the strip, so its fixed height cannot clip them. Each is independently gated and carries `role="alert"`. **`main-status-error`** shows `manifest.error` whenever it is non-null; about ten store actions that call the backend write it (load, decision, lock, remove, prune, save, …) (#712). **`main-execute-error`** shows `execute.executeError` whenever it is non-null **and** the Execute dialog is closed — the open dialog shows the same message inline. That line is what makes a failed **Open Folder** reveal from the main tree visible (see [Context menu — Open Folder](context-menu.md#context-menu--open-folder)). Both lines are user-worded (copy audit S2). [frontend/src/lib/apiErrorText.ts](../../frontend/src/lib/apiErrorText.ts) maps the closed set of shapes the routes raise onto `web.error.*` sentences. That set covers the 409 `detail.code` values such as `locked_paths` and `execute_already_running`, and the `HTTP <status>: <verb> failed: …` bodies. The raw server text is demoted to a smaller technical line inside the same alert, so both testids still carry the whole message. An unrecognised string is never swallowed: it becomes the detail of a generic sentence.
- **Related:** [#138](https://github.com/jackal998/photo-manager/issues/138), [#140](https://github.com/jackal998/photo-manager/issues/140) (desktop origin), #712, #906; QA scenario [`qa/web/scenarios/s37_status_bar_baseline.py`](../../qa/web/scenarios/s37_status_bar_baseline.py) (idle on start-up, then the groups · files summary after a scan); unit tests `frontend/src/components/StatusBar.test.tsx`, `frontend/src/lib/apiErrorText.test.ts`.
