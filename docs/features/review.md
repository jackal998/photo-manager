### Keep-worthiness scoring
- **Area:** Review

- **Entry point:** The **Score** column of the main result tree — the fourth column, after File Name / Similarity / Action ([frontend/src/lib/resultColumns.ts](../../frontend/src/lib/resultColumns.ts)). [frontend/src/components/result/FileRow.tsx](../../frontend/src/components/result/FileRow.tsx) renders the score to two decimals (`—` when it is null) under a small "keep" label, over a mini bar. `GET /api/manifest` returns every group's rows score-descending, so with no column sort active the best copy is at the top of every group.
- **Trigger:** Automatic — every scanned file is scored at scan time and the score is stored in the manifest; no user action. `ManifestRepository.rescore(manifest_path, weights)` recomputes the scores from the cached raw signals without re-scanning (no file I/O); it is a repository method with no web UI or API entry point.
- **Behaviour:** Composite score in `[0.0, 1.0]` measuring how "keep-worthy" each file is, computed as a pure function of file attributes (no user-intent signals). Two-tier algorithm: tier 1 absolute penalties (format, `xmpMM:DerivedFrom`); tier 2 weighted composite of eight continuous signals (resolution, EXIF completeness, date provenance, filename, GPS, path, Live Photo, file size). Live Photo MOV passengers get `score = NULL` and are skipped by ranking. They do **not** inherit the paired still's decision: auto-select and Apply best-copy leave them untouched, so a still marked Delete leaves its MOV at Keep, and Execute does not delete the MOV unless it is decided separately. A video is a passenger when a same-stem, same-folder still sibling is a Live Photo image: HEIC/HEIF or, since #738, JPG/JPEG (iPhone's "Most Compatible" mode exports Live Photos as JPG+MOV). The HEIC-orphan completeness penalty stays HEIC/HEIF-only — a lone JPG is an ordinary photo, not a lost-pair. **Within-group order:** the review view prepends a score-descending sort ahead of any `sorting.defaults` in settings.json (those act as tiebreakers; listing `score` there explicitly replaces the implicit key). The Score column has no header sort (`R-SORT-2`); clicking **File Name** or **Size** (`R-SORT-1`) re-sorts each group on the client, and because that sort is stable, rows that tie keep their score order (see [Main window — sort persistence within session](main-window.md#main-window--sort-persistence-within-session)).
- **Conditions / variants:** Three surfaces turn the score into staged decisions, and all three share one top-N-by-score ranking rule ([#778](https://github.com/jackal998/photo-manager/issues/778), pinned by `tests/test_topn_keeper_parity.py`): the Set Action dialog's **Top N per group** condition on the Score field (see [Set Action dialog — numeric comparison panel](set-action-dialog.md#set-action-dialog--numeric-comparison-panel)); **Apply best-copy decisions to this group**, reachable from the result-tree right-click menu and from the group header's **Keep best · delete rest** button, both calling `store.applyBestCopy` (see [Web — Context menu: Apply best-copy decisions to this group](web-ui.md#web--context-menu-apply-best-copy-decisions-to-this-group)); and auto-select after scan (see [Scan dialog — auto-select after scan](scan.md#scan-dialog--auto-select-after-scan)). The right-click item is refused under `R-LOCK-1` when the group has locked rows, which opens the lock-confirm dialog; the header button sends `skipLocked`, so locked rows keep their decision and their lock with no dialog. The right-click action had been removed from the retired desktop client in [PR #224](https://github.com/jackal998/photo-manager/pull/224) (closes [#210](https://github.com/jackal998/photo-manager/issues/210)) and came back web-only in #744.
- **Per-dimension signals on the manifest API ([#680](https://github.com/jackal998/photo-manager/issues/680)):** every `FileRow` returned by `GET /api/manifest` carries the raw scoring signals `gps_present`, `exif_tag_count` and `xmp_derived` alongside the composite `score`. Nullability mirrors the manifest columns: `exif_tag_count` may be `null` (the extended EXIF census pass did not run for that file — NOT the same as zero tags), while `gps_present` / `xmp_derived` are `NOT NULL` in SQLite and always arrive as booleans. They are produced by extraction rather than by scoring, so a row whose `score` is `null` (isolated row, Live Photo MOV passenger) still carries real values. Purely additive, and no UI surfaces them yet; the consumer is the web QA harness, which previously could only assert the aggregate score.
- **Related:** Cluster originated in [#187](https://github.com/jackal998/photo-manager/issues/187): [PR #199](https://github.com/jackal998/photo-manager/pull/199), [#200](https://github.com/jackal998/photo-manager/pull/200), [#202](https://github.com/jackal998/photo-manager/pull/202), [#203](https://github.com/jackal998/photo-manager/pull/203), [#204](https://github.com/jackal998/photo-manager/pull/204), [#205](https://github.com/jackal998/photo-manager/pull/205), [#206](https://github.com/jackal998/photo-manager/pull/206). Scorer in `scanner/scoring.py` (unit tests `tests/test_scoring.py`); within-group score-DESC default in `app/viewmodels/main_vm.py` (pinned by `tests/test_main_vm.py`), used by `core/app_service/review_service.py`; serialisation in `core/app_service/review_view.py` (`_build_file_row`), the DB read in `infrastructure/manifest_repository.py` (`_LOAD_ALL_SQL` / `_photo_record`), the client type in [`frontend/src/api/types.ts`](../../frontend/src/api/types.ts) (`FileRow`). QA scenarios [`qa/web/scenarios/s42_scoring.py`](../../qa/web/scenarios/s42_scoring.py) (score range, score-DESC order within each group and, since #680, the per-dimension signals via `GET /api/manifest`), [`qa/web/scenarios/s56_action_dialog_apply_by_score.py`](../../qa/web/scenarios/s56_action_dialog_apply_by_score.py), [`qa/web/scenarios/s72_apply_best_copy.py`](../../qa/web/scenarios/s72_apply_best_copy.py), [`qa/web/scenarios/s75_keep_best_button.py`](../../qa/web/scenarios/s75_keep_best_button.py). ### Similarity column
- **Area:** Review

- **Entry point:** The **Similarity** column of the main result tree, right of File Name (header key `web.column.similarity`; the column order lives in [frontend/src/lib/resultColumns.ts](../../frontend/src/lib/resultColumns.ts)), rendered per file row by [frontend/src/components/result/FileRow.tsx](../../frontend/src/components/result/FileRow.tsx) from the `similarity` object that `GET /api/manifest` serializes for every row ([core/app_service/review_view.py](../../core/app_service/review_view.py)). The preview pane repeats the same badge for the selected file, and a legend pinned to the bottom of the pane ([frontend/src/components/SimilarityLegend.tsx](../../frontend/src/components/SimilarityLegend.tsx)) names the five states.
- **Trigger:** Populated automatically when a manifest loads; no user action.
- **Behaviour:** The server picks at most one **Ref** per group — the highest-score row among the Ref-tier rows (classification `KEEP`, `UNDATED` or none), an unscored row losing to a scored one, with the lexicographic file path as the final tie-break ([#241](https://github.com/jackal998/photo-manager/issues/241)); a group with no Ref-tier row (e.g. all `EXACT`) has no Ref. Each file row then gets one `similarity.kind`, which [frontend/src/lib/format.ts](../../frontend/src/lib/format.ts) turns into the cell text:
  - `ref` → **Ref** (`web.format.similarity_ref`) — the Ref winner.
  - `percent` 100 → **100%** — classification `EXACT` (SHA / format duplicate).
  - `percent` N → **N%** — `REVIEW_DUPLICATE`, computed server-side as `round((64 - hamming) / 64 * 100)`, where `hamming` is the pHash Hamming distance between the row and **the displayed Ref**, not the scanner's anchor ([#253](https://github.com/jackal998/photo-manager/issues/253)).
  - `passenger` → **★ N%** — a Ref-tier row that did not win the Ref pick (e.g. a same-stem companion, a [#824](https://github.com/jackal998/photo-manager/issues/824) complementary RAW + lossy pair, or a [#538](https://github.com/jackal998/photo-manager/issues/538)-reconnected member), measured against the displayed Ref the same way; the ★ marks an indirect / transitive member ([#536](https://github.com/jackal998/photo-manager/issues/536) Direction A).
  - `near_dup` → **~dup** (`web.format.similarity_near_dup`; zh_TW `~近似`) — a `REVIEW_DUPLICATE` row with no computable distance.
  - `none` → **—** — a Ref-tier passenger with no comparable pHash (e.g. a Live Photo MOV).

  The cell is a pill whose colour and two grayscale-safe cues — border style and font weight — differ per state ([#878](https://github.com/jackal998/photo-manager/issues/878) slice (a), [frontend/src/lib/similarityBadge.ts](../../frontend/src/lib/similarityBadge.ts)): `ref` → gold, solid, semibold, with a leading `aria-hidden` ★ outside the label span (so the queryable cell text stays exactly the label); `percent` at 100 → purple, solid, bold; `percent` under 100 **and** `near_dup` → blue, solid, medium (one relationship, told apart by their labels); `passenger` → gray, **dashed**, medium; `none` → muted, **dotted**, normal. The badge keys on the percentage, so a `REVIEW_DUPLICATE` row at distance 0 from the Ref wears the 100 % pill too. Hovering the badge shows the row's classification in words (Exact copy / Near-duplicate / Best in group / No date). The keeper row carries no second "Ref" pill (copy audit R7 / design Q2, 2026-09-18): besides this badge it is readable from the left of the row by its filename at weight 600 (500 elsewhere) and a 2 px accent strip on its left edge (`border-l-warm`); every row reserves those 2 px, so the strip costs no horizontal shift.
- **Conditions / variants:** The render-time recomputation needs both the displayed Ref's pHash and the row's pHash. When either is missing (old manifests without the pHash column, video rows, or `imagehash` not installed — [scanner/phash_distance.py](../../scanner/phash_distance.py) then returns `None`), a `REVIEW_DUPLICATE` row falls back to the scanner's stored `hamming_distance` (relative to the scanner's anchor, not the displayed Ref), and only with neither does it read `~dup`. The scanner still writes `hamming_distance`, but it is not the source of truth for the rendered percentage whenever pHashes are available. The column has no sort control (`R-SORT-2`).

### Review — Undo of Keep best under named confirmation (A7, #999)
- **Area:** Review

- **Behaviour:** The Undo of a **Keep best · delete rest** toast is one `PATCH /api/decision`. Each restored row carries its prior `decision` and its prior `locked` (`DecisionItem.locked`, written in the same statement as the decision). The request's `confirmed_locked` names only the locks the action itself created: a row unlocked before the action and locked by it (the keeper). A toolbar Undo names none. A lock set after the toast appeared, or a keeper that was already locked before the action (owner ruling D10 = (a), no exception), is not named: the server answers 409 and writes nothing, the lock-confirm dialog opens with op `undo` using the decision wording, and the toast stays up. The dialog's three outcomes: **Unlock & Apply** re-sends with the dialog's rows added to the confirmed set (rows confirmed in earlier rounds are carried forward, so a second 409 accumulates); **Unlocked only** undoes the rest and leaves the excluded rows as they are; **Cancel** writes nothing and leaves the toast up with its Undo. Skip-now Undo (`POST /api/restore`) is unchanged.
- **Conditions / variants:** Setting a lock on an unlocked row needs no name; clearing one (`locked: false` on a locked row) does. `locked: false` on an unlocked row is a no-op on the lock and is not refused, so a toolbar Undo of unlocked rows succeeds. The toast's timer is held while the undo dialog is open and gets a full budget again after Cancel.
