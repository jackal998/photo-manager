### Scan dialog — auto-select after scan
- **Area:** Scan

- **Entry point:** **Auto select after scan** checkbox (testid `scan-auto-select`) inside the Scan dialog's **Advanced settings** disclosure — [frontend/src/components/ScanDialog.tsx](../../frontend/src/components/ScanDialog.tsx). Sent as `auto_select_enabled` on `POST /api/scan` (`WebScanRequest`, [app/web/models.py](../../app/web/models.py)) and applied by the scan pipeline ([core/app_service/scan_runner.py](../../core/app_service/scan_runner.py)) with the helpers in [core/services/auto_select.py](../../core/services/auto_select.py).
- **Trigger:** User expands **Advanced settings**, ticks **Auto select after scan**, and starts the scan. The checkbox defaults **off** and is **not persisted** — it resets to off every time the dialog opens. The autotune checkbox, the cloud opt-in and the **Ask me to confirm when confidence is below** select ([confirm threshold](#scan-dialog--confirm-threshold-setting), PR-3) and the **Rules** block are the controls in that panel that persist.
- **Behaviour:** After scoring, `plan_auto_select` ([core/services/auto_select.py](../../core/services/auto_select.py), PR-3) picks the top-scored row of each duplicate group (`top_score_path_per_group`) and sets its `action` to `KEEP`, before the manifest summary is printed and the manifest is written. A group is stamped only when every one of its rows is at or above the confirm threshold; a group with a row below it gets **no** stamp and is shown under the **Needs your look** filter instead ([#1047](https://github.com/jackal998/photo-manager/issues/1047)). A stamped keeper also gets `user_decision=""` — the canonical keep state ([#425](https://github.com/jackal998/photo-manager/issues/425) fixed an earlier literal-`"keep"` write that leaked into the Action column as raw text) — and no lock: PR-3 removed the `is_locked=1` keeper lock that [#393](https://github.com/jackal998/photo-manager/issues/393) introduced, so an auto-picked keeper is ordinary, editable state. Since [#651](https://github.com/jackal998/photo-manager/issues/651) those decision + lock writes run inside `write_manifest`'s own transaction ([scanner/manifest.py](../../scanner/manifest.py)), before its single commit and atomic `os.replace`, so a crash mid-write can never leave a manifest on disk whose keepers are unlocked. In the result tree the stamped keeper shows **Keep** in the Action column with an unlocked lock toggle, and its decision buttons stay enabled. No lock gate (`R-LOCK-1`, `R-LOCK-4`, `R-LOCK-7`) applies to an auto-picked keeper, so a later bulk **Set Action** or **Execute** does not ask before touching it. Other duplicates keep their classifier action (`EXACT` / `REVIEW_DUPLICATE` / …) and the default decision (`user_decision=""`, shown as **Keep**), so deleting anything still takes an explicit user decision. Auto-select picks keepers, never deleters — unless the aggressive sub-option below is also on. The scan log reports `Auto-select: marked N keeper(s); M group(s) need your look (confirm below T).` and, after the write, `Auto-select: decisions written (no keeper is locked).`
- **Conditions / variants:** Default is off. Ranking is the one shared top-N-by-score rule (`top_n_paths`, [#778](https://github.com/jackal998/photo-manager/issues/778)) that the Set Action "Top N by score" pattern (see [Set Action dialog — numeric comparison panel](set-action-dialog.md#set-action-dialog--numeric-comparison-panel)) and the right-click **Apply best-copy decisions to this group** also use: `score=None` rows are excluded, ties break by `source_path` ascending — so manual and automatic picks converge on the same keeper. The checkbox is disabled while a scan runs. After the scan the dialog selects and scrolls to the keepers (see [Scan flow — visual selection of KEEP rows after scan](#scan-flow--visual-selection-of-keep-rows-after-scan)).
- **Related:** [PR #232](https://github.com/jackal998/photo-manager/pull/232) (closes [#212](https://github.com/jackal998/photo-manager/issues/212)); [#393](https://github.com/jackal998/photo-manager/issues/393) (keep + lock writes and the aggressive sub-option); [#651](https://github.com/jackal998/photo-manager/issues/651) (atomic write); [#778](https://github.com/jackal998/photo-manager/issues/778) (shared ranking). Pinned by `tests/test_auto_select.py` (`TestTopScorePathPerGroup`), `tests/test_scan_runner.py::TestAutoSelectPipeline::test_auto_select_enabled_stamps_keeper_without_lock` (keeper stamp, no lock, atomic write; the post-write `apply_auto_select_decisions` it replaced was deleted in A5) and `tests/test_topn_keeper_parity.py`; QA scenarios [`qa/web/scenarios/s49_scan_auto_select.py`](../../qa/web/scenarios/s49_scan_auto_select.py) (keep stamp, no lock, keeper highlighted) and [`qa/web/scenarios/s57_scan_auto_select_aggressive.py`](../../qa/web/scenarios/s57_scan_auto_select_aggressive.py) (aggressive).

### Scan dialog — auto-select aggressive ("delete all others")
- **Area:** Scan

- **Entry point:** **Also mark all other files for delete** checkbox (testid `scan-aggressive-delete`), indented beneath **Auto select after scan** in the Scan dialog's **Advanced settings** — [frontend/src/components/ScanDialog.tsx](../../frontend/src/components/ScanDialog.tsx). Sent as `auto_select_aggressive_delete` on `POST /api/scan`; the eligible rows are chosen by `non_keepers_for_aggressive_delete` in [core/services/auto_select.py](../../core/services/auto_select.py).
- **Trigger:** User expands **Advanced settings**, ticks **Auto select after scan**, then ticks the indented sub-option, and starts the scan. Defaults **off**; not persisted (resets to off every time the dialog opens).
- **Behaviour:** Destructive-leaning, opt-in. Alongside the parent's KEEP stamp on each admitted group's keeper, every eligible non-keeper in a scored group (eligibility excludes rows below the threshold, so a group that needs a look still deletes its admitted copies, and its unstamped keeper is never a delete) gets `user_decision='delete'`, written in the same atomic manifest write as the keeper stamps ([#651](https://github.com/jackal998/photo-manager/issues/651)). Non-keepers are **not** locked, so they stay editable. When the manifest auto-loads, the triage is already staged — keepers stamped **Keep**, eligible non-keepers on **Delete** — and one **Execute** run carries it out. The scan itself deletes nothing: deletion still goes through the standard Execute flow (`POST /api/execute`, which the client always sends with `recycle: true`, and whose gate (`R-LOCK-4`) asks before touching any row that was locked after the scan — see [Execute Action — base flow](execute-action.md#execute-action--base-flow) and [Execute Action — lock-confirm dialog](execute-action.md#execute-action--lock-confirm-dialog)).
- **Conditions / variants:** The sub-checkbox is disabled while **Auto select after scan** is off, and the request never carries the aggressive flag without the parent. Unticking the parent also **clears** the sub-option (the retired desktop client kept it for a later re-tick). A non-keeper is eligible only if all of these hold: (a) it is a ranked peer — `group_id` and `score` both set — so `score=None` rows (Live Photo MOV passengers, all-MOV groups) are never tagged, except a B6 Live-video follower (see [rules (setting)](#scan-dialog--rules-setting)); (b) **since [#517](https://github.com/jackal998/photo-manager/issues/517)**, its `match_confidence` is not `"low"` — a near-duplicate matched on pHash alone (no independent dHash agreement) is a hint on an ungrouped row, so it never reaches review, while byte-identical (SHA) and dHash-confirmed near-dups are `"high"` and stay eligible. The same `"low"` cap applies to a pair where both files are PNG screenshots that are not pixel-identical (dedup-core research 2026-11-05 class B; `scanner/dedup.py` `_screenshot_pair`); it is a hint on ungrouped rows, so it never reaches review and is never delete-eligible. Since GROUPING 14 a shot-time disagreement is not a cause: shot time is not grouping evidence, a grouping verdict is decided on content. A pixel-identical PNG pair is an `EXACT` grouped row (GROUPING 12), so aggressive delete may mark it like any exact copy; (b2) **since [#1047](https://github.com/jackal998/photo-manager/issues/1047) / PR-3**, it is not below the confirm threshold (`below_threshold` in `core/services/auto_select.py`): at **high** (the default) a `REVIEW_DUPLICATE` row (same pHash, pixels differ) is not delete-eligible and only `EXACT` copies are, while at **medium** the #517 set is unchanged; (c) **since [#536](https://github.com/jackal998/photo-manager/issues/536)**, the classifier positively flagged it as a duplicate (`action` = `EXACT` or `REVIEW_DUPLICATE`) — a Ref-tier row (`""` / `KEEP` / `UNDATED`) pulled into a group by the unconditional, filename-based pair edge (same-stem RAW+JPG / HEIC+JPG, Live Photo) renders as the `"—"` passenger and is never auto-tagged, so a complementary original can't be silently swept; (d) **since [#824](https://github.com/jackal998/photo-manager/issues/824)**, when a group's keeper is a RAW (`.tif` / `.tiff` included), the best non-RAW row — the one that would have been keeper without the RAW — is protected as well, so a RAW that joins a group through the exact-tier complementary edge can't demote the lossy copy it outscored into the delete set. The same eligibility rule drives the right-click [Web — Context menu: Apply best-copy decisions to this group](web-ui.md#web--context-menu-apply-best-copy-decisions-to-this-group).
- **Rule toggles (PR-4a):** (e) **B3** exact copies: while the rule is off, no `EXACT` row is marked for delete, and the keeper stamp is unchanged. (f) **B8** people and pets: while the rule is on (the default), only `EXACT` rows are eligible, at either threshold. The screenshot cap in (b) applies only while **B7** is on, and the RAW protection in (d) only while **B4** is on. See [rules (setting)](#scan-dialog--rules-setting).
- **Related:** [#393](https://github.com/jackal998/photo-manager/issues/393); [#517](https://github.com/jackal998/photo-manager/issues/517) (multi-hash confidence gate); [#1047](https://github.com/jackal998/photo-manager/issues/1047) (a REVIEW near-duplicate is not deleted as a copy under the high threshold); [#536](https://github.com/jackal998/photo-manager/issues/536) (Ref-tier "—" passenger exclusion — only `EXACT`/`REVIEW_DUPLICATE` eligible); [#824](https://github.com/jackal998/photo-manager/issues/824) (RAW keeper protects the best lossy copy); composes with [Scan dialog — auto-select after scan](#scan-dialog--auto-select-after-scan). Pinned by `tests/test_auto_select.py::TestNonKeepersForAggressiveDelete` and `tests/test_scan_runner.py::TestAutoSelectPipeline::test_auto_select_aggressive_delete_marks_non_keepers`; QA scenario [`qa/web/scenarios/s57_scan_auto_select_aggressive.py`](../../qa/web/scenarios/s57_scan_auto_select_aggressive.py) (sub-option defaults off and can be ticked once the parent is on — the disabled-while-parent-off state is not asserted by any test; keeper stamped KEEP without a lock, every eligible non-keeper duplicate marked delete (the s80 scenario covers the high threshold) — keyed off each row's classifier action, since which quality variants classify as duplicates is platform-dependent).

### Scan dialog — stage / throughput / ETA progress (#424)
- **Area:** Scan

- **Entry point:** The backend half of scan progress: stage events emitted by the scan pipeline in [core/app_service/scan_runner.py](../../core/app_service/scan_runner.py) (`_emit_stage` + `_StageTracker`) and streamed to the browser as SSE `stage` events by `SseScanBus.stage` in [app/web/routes/scan.py](../../app/web/routes/scan.py). The panel that renders them inside the Scan dialog is documented under [Web — scan progress throughput / ETA / localized stages (#740)](web-ui.md#web--scan-progress-throughput--eta--localized-stages-740).
- **Trigger:** Automatic while a scan runs — at every stage boundary and inside the hot loops.
- **Behaviour:** Each event carries `{stage_name, completed, total, files_per_sec}`. There are six stages, passed as canonical strings — `WALK`, `HASH`, `EXIFTOOL`, `CLASSIFY`, `SCORE`, `WRITE` (the `STAGE_*` constants); the client localises them. Emission is throttled per stage to at most one event per second (`_STAGE_EMIT_INTERVAL_SECONDS`); the first event of a stage, the `completed == total` boundary and forced boundary emits always go out. Throughput is computed backend-side as `(latest_count − oldest_count) / (latest_ts − oldest_ts)` over a 5-second rolling window (`_THROUGHPUT_WINDOW_SECONDS`), and reported as 0 when the window holds fewer than two samples or spans under 0.1 s — so a fast SSD scan doesn't claim a million files/sec on its first event. Samples and events are produced only as work completes, so during a stall no event arrives and the client keeps showing the last rate it received. Per stage: `HASH` reports `completed` out of the total file count; `EXIFTOOL` reports files done against a total that keeps growing while HASH is still routing files to it (JPEGs, whose scoring signals are read in memory, skip exiftool entirely — #786); `WALK` has no upfront total and emits `total=0` with a live running count from the walker's `progress_callback` ([#448](https://github.com/jackal998/photo-manager/issues/448)); `CLASSIFY`, `SCORE` and `WRITE` emit `total=0` when they start and `(1, 1)` when they finish. The client draws an indeterminate bar with an "N files found" count whenever `total` is 0 and a determinate bar otherwise; the ETA is computed client-side and held back until the current stage has run ≥5 s (see the #740 entry). The free-text `log` event stream (the per-line trace — "Hashed N/M", calibration lines, the manifest summary) runs alongside these events and is not affected by them.
- **Conditions / variants:** **Cancel during WALK ([#491](https://github.com/jackal998/photo-manager/issues/491)):** the pipeline hands its cancel token to the walker (`scan_sources(cancel_check=…)`, [scanner/walker.py](../../scanner/walker.py)), which polls it at the top of its per-entry loop and between sources, so a **Cancel** lands within about one directory entry instead of waiting for the walk to finish. A post-WALK gate then ends the scan with `failed("Scan cancelled.")` — the same shape as the HASH, post-HASH, CLASSIFY, SCORE, auto-select and WRITE gates — which `SseScanBus.failed` classifies as `cancelled` (any other message is a real `failed`). A scan cancelled before WRITE never writes its output `.db`. **The progress UI never outlives the scan ([#510](https://github.com/jackal998/photo-manager/issues/510)):** the running-state panel is rendered only while `scan.status === "running"`, so every terminal event removes it — on `finished` and `cancelled` the dialog closes, on `completed_empty` it stays open as `R-SCAN-2` states ([#896](https://github.com/jackal998/photo-manager/issues/896)), and on `failed` the dialog stays open showing the error alert, never a stuck bar. An unreadable entry during WALK is skipped instead of failing the scan ([#509](https://github.com/jackal998/photo-manager/issues/509) — see [Scan walk — skip-on-error traversal](#scan-walk--skip-on-error-traversal)).
- **Related:** [#424](https://github.com/jackal998/photo-manager/issues/424) (stage events + throughput), [#448](https://github.com/jackal998/photo-manager/issues/448) (live WALK count), [#491](https://github.com/jackal998/photo-manager/issues/491) (WALK cancel checkpoint), [#509](https://github.com/jackal998/photo-manager/issues/509), [#510](https://github.com/jackal998/photo-manager/issues/510); client panel [#740](https://github.com/jackal998/photo-manager/issues/740). Pinned by `tests/test_walker.py::TestCancelCheck` + `::TestProgressCallback` (walker hooks), `tests/test_scan_pipeline.py::TestPipelineWalkCancel` + `::TestCancelTokenWiring` (WALK cancel end to end, prior manifest preserved), `tests/test_scan_runner.py::TestRunPipelineHappyPath` (a `WALK` stage event is emitted) and `tests/test_web_scan_bus.py::TestBusFailedClassification` (clean cancel vs error). No unit test currently pins `_StageTracker`'s window / throttle arithmetic. Web scenarios [`qa/web/scenarios/s03_cancel_scan.py`](../../qa/web/scenarios/s03_cancel_scan.py) (HASH- and WALK-stage cancel) and [`qa/web/scenarios/s02_empty_folder.py`](../../qa/web/scenarios/s02_empty_folder.py) (an empty scan, `R-SCAN-2`).

### Scan dialog — collapse Advanced Settings
- **Area:** Scan

- **Entry point:** **Advanced settings** disclosure (a native `<details>` / `<summary>`, testid `scan-advanced`) in the Scan dialog — [frontend/src/components/ScanDialog.tsx](../../frontend/src/components/ScanDialog.tsx).
- **Trigger:** User clicks **Advanced settings** to expand or collapse the panel.
- **Behaviour:** Tuning controls live in one collapsed panel, so the default view is just the source rows, the output path and **Start Scan**. Inside, in order: **Auto-tune reader concurrency (experimental)** (default on — see [read-knee autotune opt-out](#scan-dialog--read-knee-autotune-opt-out)); **Auto select after scan** and its indented **Also mark all other files for delete** (both default off — see [auto-select after scan](#scan-dialog--auto-select-after-scan)); the **Ask me to confirm when confidence is below** select (default **High**, PR-3 — see [confirm threshold](#scan-dialog--confirm-threshold-setting)); then the **Rules** block (the five auto-select rule toggles, see [rules (setting)](#scan-dialog--rules-setting)); then a **Grouping sensitivity** section with three number inputs — **pHash Similarity Threshold** (default 10, range 2–20, testid `scan-phash-threshold`), **dHash Confidence Threshold** (default 10, range 2–20, [#517](https://github.com/jackal998/photo-manager/issues/517), testid `scan-dhash-threshold`) and **Mean Color Gate** (default 30, range 0–100, testid `scan-color-threshold`). Each threshold shows a short one-line description under its label, with the full technical explanation as a hover tooltip on that description line only — the label itself has no tooltip. The dHash value sets how close the second, independent perceptual hash must be for a pHash near-duplicate to count as high-confidence; it travels as `dhash_threshold` on `POST /api/scan` → `ScanConfig` → `classify(dhash_threshold=…)`. There is no hash-pool control and no hash-workers control: the pool mode is resolved from settings (see [hash pool mode](#scan-dialog--hash-pool-mode)) and worker counts are picked per device (see [hash workers](#scan-dialog--hash-workers-nas-aware-auto-no-ui-control)). Every label, description and tooltip resolves through the `web.scan.*` catalog, and every control is disabled while a scan runs.
- **Near-duplicate threshold floor ([#823](https://github.com/jackal998/photo-manager/issues/823)):** the pHash and dHash inputs run **2–20**, not 1–20. `classify` groups on `0 < distance <= threshold`, and a photographic pHash always carries exactly 32 of its 64 bits, so the Hamming distance between any two of them is **even**: a threshold of 1 admitted only distance-1 pairs — i.e. nothing — so the *strictest* end silently switched near-duplicate detection **off**, and every odd value matched exactly what the even value below it matched (measured: 0 of 86 400 pairwise distances odd over the study's 1 500-hash corpus). A helper line under each hash input (`web.scan.threshold_parity_note`, testids `scan-phash-parity-note` / `scan-dhash-parity-note`) says plainly that an odd value usually matches the same files as the even value below it and that **2 is the strictest useful setting**. The inputs render `min="2"`; because `min` is only a browser hint, `clampThresholdInput` clamps the value when the request is built, and the field snaps to the clamped value on blur and again on **Start Scan**, so what is shown is what runs (details under [Web — ScanDialog source/output persistence](web-ui.md#web--scandialog-sourceoutput-persistence)). The **mean-colour gate is unchanged** (0–100; 0 legitimately means "off"), and **`scanner/dedup.py` is unchanged** — the predicate was right, the control was misdescribing it.
- **Conditions / variants:** The panel opens **collapsed every time** — its expanded state is not persisted. The three thresholds and the two auto-select checkboxes reset to their defaults on every open and are sent per scan only, never written to settings; the autotune checkbox, the cloud opt-in, the confirm threshold and the Rules block are the controls here whose state persists. The #823 floor started as a UI-only floor; [#876](https://github.com/jackal998/photo-manager/issues/876) moved it to the trust boundary, where a scripted client actually arrives: `WebScanRequest.threshold` and `.dhash_threshold` (`app/web/models.py`) are `Field(ge=…, le=…)`, so a hand-rolled `POST /api/scan` asking for 1 (or 21) gets **422 `Input should be greater than or equal to 2`** instead of a scan that silently finds no near-duplicates, and `/openapi.json` advertises `minimum: 2` / `maximum: 20` on both fields. The bounds are the single pair of constants `NEAR_DUP_THRESHOLD_MIN` / `NEAR_DUP_THRESHOLD_MAX` in `core/app_service/dtos.py`, which the API model imports; the dialog keeps its own literal 2 / 20 in `frontend/src/components/ScanDialog.tsx` (its rendered minimum is asserted by s17, and the API rejects anything outside the shared bounds). The mean-colour gate is not fenced (its 0 legitimately means "off"). A manifest scanned before the floor with `threshold=1` is not rewritten.
- **Related:** [PR #179](https://github.com/jackal998/photo-manager/pull/179) collapsed the grouping parameters into one panel; [#163](https://github.com/jackal998/photo-manager/issues/163) drove the original consolidation; the short-description + hover-tooltip layout first shipped in [#520](https://github.com/jackal998/photo-manager/pull/520); [#736](https://github.com/jackal998/photo-manager/issues/736) added the grouping-sensitivity inputs to the web dialog. Threshold floor [#823](https://github.com/jackal998/photo-manager/issues/823), origin `docs/audits/visual-autoselect-feasibility.md` §3c (popcount-32 parity) + §9 item 6; API bound [#876](https://github.com/jackal998/photo-manager/issues/876). Pinned by `tests/test_web_scan_routes.py::TestNearDupThresholdBounds` (the API bound + the OpenAPI schema), `frontend/src/components/ScanDialog.test.tsx` (defaults / min / max, clamp-to-2 in the request, snap on blur and on Start, parity note, thresholds reset on reopen) and [`qa/web/scenarios/s17_scan_dialog_widgets.py`](../../qa/web/scenarios/s17_scan_dialog_widgets.py) (rendered input minimums + threshold values reaching the `POST /api/scan` body).

### Scan dialog — folder list (no priority arrows)
- **Area:** Scan

- **Entry point:** The **Sources** list in the Scan dialog (testid `scan-source-list`) — rows rendered by [frontend/src/components/scan/SourceRow.tsx](../../frontend/src/components/scan/SourceRow.tsx), list and ordering in [frontend/src/components/ScanDialog.tsx](../../frontend/src/components/ScanDialog.tsx).
- **Trigger:** Always — applies to every interaction with the source list.
- **Behaviour:** Each row is a **Label** input, a **Path** input, a **Browse…** button, a **Recursive** checkbox and a **✕** (*Remove source*) button; **+ Add source** appends a blank row. - **Conditions / variants:** There are no ↑/↓ priority arrows (removed in [#213](https://github.com/jackal998/photo-manager/issues/213)) and no duplicate-path check. Every control on a row is disabled while a scan runs.

### Scan dialog — exiftool workers (setting-only)
- **Area:** Scan

- **Entry point:** `scan.exif_workers` key in `settings.json` — read by `WebScanRequest.resolved_with()` ([app/web/models.py](../../app/web/models.py)) at the start of every `POST /api/scan` that does not carry its own `exif_workers` (the Scan dialog never sends one), then clamped by `ScanConfig` ([core/app_service/dtos.py](../../core/app_service/dtos.py)).
- **Trigger:** Always — resolved on every scan start.
- **Behaviour:** Sets how many parallel `ExiftoolProcess` instances the EXIF stage runs ([core/app_service/scan_runner.py](../../core/app_service/scan_runner.py)): one consumer thread per instance, all draining the single producer-consumer queue the HASH stage feeds ([#450](https://github.com/jackal998/photo-manager/issues/450)), each sending exiftool 500-file batches. Default 2 — also the fallback when the setting is missing or not an integer; clamped to `[1, min(4, cpu_count() // 2)]` in `ScanConfig.__post_init__`. The scan log names the count (`… N parallel process(es)…`). exiftool is single-threaded within one `-stay_open` instance, so parallel instances are what scale the stage (near-linearly up to ~4 on a modern CPU, per [#451](https://github.com/jackal998/photo-manager/issues/451)).
- **Conditions / variants:** No UI control — raise the value in `settings.json` (the key is also on the `/api/settings` allowlist, so `PATCH /api/settings` can set it). A request that sends `exif_workers` explicitly is used as-is (still clamped). This is intentionally a *safe rollout knob* per the issue body, not a power-user control. The EXIF queue is bounded at `2 × 500 × exif_workers` entries ([#564](https://github.com/jackal998/photo-manager/issues/564)) so a slow exiftool can't grow it without limit. On cancel the pipeline kills the live exiftool processes ([#561](https://github.com/jackal998/photo-manager/issues/561)), drains the queue, posts one sentinel per consumer and joins each with a 5 s timeout — no orphaned exiftool processes. A wedged exiftool (a read that stalls past its time budget) costs only the file it stalled on: that file is recorded as exif-missing (still in the manifest, with no EXIF signal), the process is closed and replaced with a fresh one, and the files after it in the batch resume on the fresh process, so one wedge is one file and one rotation. The scan log names the wedged file (`exiftool wedged reading <file>; rotating and resuming with N files`), prints `EXIF N read (M queued)` after each flushed batch, and the `EXIF done` line counts any wedges. Each file goes to exiftool as its own `-execute` call with a time budget of 300 s + 12 s per cost unit (an image is 1 unit, a video 4), so a bandwidth-starved but alive exiftool is not mistaken for a wedged one.
- **Related:** [#451](https://github.com/jackal998/photo-manager/issues/451); [#450](https://github.com/jackal998/photo-manager/issues/450); [#564](https://github.com/jackal998/photo-manager/issues/564); [#561](https://github.com/jackal998/photo-manager/issues/561); [#652](https://github.com/jackal998/photo-manager/issues/652) (web read-back of the setting). Pinned by `tests/test_scan_pipeline.py::TestPipelineExifWorkers` (clamp + one consumer thread per worker), `::TestBoundedExifQueueCancelSafety`, `::TestPostHashCancelKillsExif`, and `tests/test_web_scan_routes.py::TestExifWorkersResolution` (int coercion, fallback to 2).

### Scan dialog — confirm threshold (setting)
- **Area:** Scan

- **Entry point:** The **Ask me to confirm when confidence is below** select (testid `scan-confirm-below`) in the Scan dialog's **Advanced settings**, after the aggressive sub-option — [frontend/src/components/ScanDialog.tsx](../../frontend/src/components/ScanDialog.tsx). Sent as `auto_select_confirm_below` on `POST /api/scan` (`WebScanRequest.resolved_with`, [app/web/models.py](../../app/web/models.py)) and stored at `scan.auto_select.confirm_below` in `settings.json`, read and written through `GET`/`PATCH /api/settings` ([app/web/routes/settings.py](../../app/web/routes/settings.py)).
- **Trigger:** The user picks a value. It is saved on change (`PATCH /api/settings`), loaded on every dialog open, and sent with the scan request.
- **Behaviour:** Two values. **High** (the default, *"confirm every near-duplicate"*) decides a group only when every one of its rows is an `EXACT` copy or a high-confidence match; a group holding a `REVIEW_DUPLICATE` near-duplicate needs a look. **Medium** (*"confirm only low-confidence matches"*) also decides `REVIEW_DUPLICATE` rows. Since GROUPING 10 no grouped row carries low confidence, so the difference is only the `REVIEW_DUPLICATE` rows: they are medium level, Medium admits them, and High does not. A group that needs a look gets no auto-select keeper stamp and appears under the **Needs your look** filter ([web-ui.md](web-ui.md#web--needs-your-look-filter)). An unset or unrecognised stored value resolves to **High**, so a bad settings file never widens what auto-select decides. The level of each row comes from `row_confidence_level` in `core/services/auto_select.py`; unrated rows (Ref-tier passengers) never make a group need a look.
- **Conditions / variants:** Disabled while a scan runs. Unlike the auto-select checkboxes, the value persists across launches. It is a threshold, so changing it after a scan does not re-decide the stamps already written; the **Needs your look** filter uses the current setting, and a rescan re-decides. The same threshold gates aggressive delete eligibility (see [auto-select aggressive](#scan-dialog--auto-select-aggressive-delete-all-others)).
- **Related:** [#1047](https://github.com/jackal998/photo-manager/issues/1047) (a REVIEW near-duplicate was deleted as a copy by aggressive mode); PR-3 of the auto-select PRD. Pinned by `tests/test_auto_select.py::TestConfidenceThreshold` (threshold, fallback to High, group gating), `tests/test_web_settings_routes.py::test_confirm_below_round_trip`, `tests/test_web_scan_routes.py::TestConfirmBelowResolution`, `tests/test_review_service.py` (`confirm_below` in the manifest payload) and `frontend/src/components/ScanDialog.test.tsx`; QA scenarios [`qa/web/scenarios/s49_scan_auto_select.py`](../../qa/web/scenarios/s49_scan_auto_select.py) and [`qa/web/scenarios/s57_scan_auto_select_aggressive.py`](../../qa/web/scenarios/s57_scan_auto_select_aggressive.py) (medium), and [`qa/web/scenarios/s80_needs_your_look.py`](../../qa/web/scenarios/s80_needs_your_look.py) (high).

### Scan dialog — rules (setting)
- **Area:** Scan

- **Entry point:** The **Rules** block (testid `scan-rules`, one checkbox per rule: `scan-rule-b3`, `scan-rule-b4`, `scan-rule-b5`, `scan-rule-b6`, `scan-rule-b7`, `scan-rule-b8`) in the Scan dialog's **Advanced settings**, after the confirm threshold — [frontend/src/components/scan/ScanRulesBlock.tsx](../../frontend/src/components/scan/ScanRulesBlock.tsx). Stored at `scan.auto_select.rules` in `settings.json` through `GET`/`PATCH /api/settings`, and sent as `auto_select_rules` on `POST /api/scan`. The resolver is [core/services/auto_select_rules.py](../../core/services/auto_select_rules.py).
- **Trigger:** The user ticks or unticks a rule. The block saves all six ids on every change, loads them on every dialog open, and sends them with the scan request.
- **Behaviour:** Each rule is a named engine decision with the PRD default. All six are on by default. B7 stays on by default. A census on 2026-11-08 found that turning it off produced two false merges of bank-app receipt screenshots in 2,043 files, so the PRD v2 default of off was not adopted ([census STATE](../../docs/audits/dedup-core-research-2026-11-05/STATE.md)).
  - **B3 exact copies.** Off leaves byte copies and pixel-identical format duplicates undecided under aggressive delete. The keeper stamp is unchanged. Aggressive only.
  - **B4 RAW + JPEG.** Off lets the JPEG that a RAW keeper outranks be marked for delete. RAW + lossy complementary rows stay protected. Aggressive only.
  - **B5 burst.** Off keeps the classifier verdict on each burst frame, and the group ids are unchanged. Takes effect at the next scan, in every mode.
  - **B7 screenshots.** Off judges two matching PNG screenshots like photos. On (the default), two PNGs group as byte-identical or pixel-identical copies; a PNG pHash match that is not pixel-identical is a hint that names the screenshot rule. Takes effect at the next scan, in every mode.
  - **B8 people and pets.** On (the default) makes aggressive delete take only `EXACT` rows, at either threshold. Off restores the #517 set, in which a near-duplicate at Medium can be deleted. Aggressive only. With B8 off and the threshold at Medium, a demoted REVIEW row is still eligible, which is the user's explicit choice.
  - **B6 Live Photos.** On (the default): in aggressive mode a Live video whose photo is marked for delete is marked too. A qualifying photo is in the same group and folder, has the same stem, is not edited, and has the same ContentIdentifier. Every qualifying photo must be marked, and the video must not be a keeper. An EXACT video needs B3 on. A video is kept when it is the capture's last motion clip. Off keeps the video, as before. Aggressive only. This is the only rule that adds a delete.
  - **Apply best copy** on a group ignores the rules.
  - The scan log names the rule version and each rule's state, then tallies what B3, B6, B4 and B8 decided.
- **Conditions / variants:** A stored value resolves per rule id: an unreadable value, or a non-boolean one, takes that rule's default, and unknown ids are ignored. `PATCH /api/settings` and `POST /api/scan` refuse unknown ids and non-boolean values with `422`, and `PATCH` writes nothing. The B3, B4, B6 and B8 labels read muted while aggressive delete is off, though they stay tickable. A non-default toggle changes classification without a grouping-version bump, so `GROUPING_STRATEGY_VERSION` describes the default scan.
- **Related:** Pinned by `tests/test_auto_select_rules.py`, `tests/test_dedup_rule_toggles.py`, `tests/test_auto_select.py::TestRuleToggles`, `tests/test_scan_runner.py::TestAutoSelectPipeline`, `tests/test_web_settings_routes.py::test_auto_select_rules_round_trip`, `tests/test_web_scan_routes.py::TestRuleTogglesResolution` and `frontend/src/components/ScanDialog.test.tsx`. Rules register [R-SCAN-5](../behaviour/rules.md) to R-SCAN-12. ### Scan dialog — read-knee autotune opt-out
- **Area:** Scan

- **Entry point:** **Auto-tune reader concurrency (experimental)** checkbox (testid `scan-autotune`) in the Scan dialog's **Advanced settings** — [frontend/src/components/ScanDialog.tsx](../../frontend/src/components/ScanDialog.tsx); the same preference is also a checkbox in the Settings dialog ([frontend/src/components/SettingsDialog.tsx](../../frontend/src/components/SettingsDialog.tsx)). Sent as `autotune_read_knee` on `POST /api/scan`; the ramp runs in [core/app_service/scan_runner.py](../../core/app_service/scan_runner.py), with the measurement logic in [scanner/autotune.py](../../scanner/autotune.py).
- **Trigger:** Autotune runs by **default** on every scan — no action needed. To use the static reader count instead, expand **Advanced settings** and untick the checkbox. The choice persists as `ui.scan_dialog.autotune_read_knee` ([#743](https://github.com/jackal998/photo-manager/issues/743)): read when the dialog opens (on when unset) and written back on **Start Scan**.
- **Behaviour:** The scan measures each physical device's read-concurrency knee instead of using the static `NAS=8 / spinning-HDD=1 / else min(4, cpu)` guess: it widens that device's active-reader budget along `1→2→4→8` (never beyond the static count), measures files/s at each level, and settles on the concurrency where doubling stops paying off (less than 15 % gain). A measured knee is cached per `device_key` in `scan.read_knee_cache` (stamped with the autotune recipe version) and reused on later scans of that device: `WebScanRequest.resolved_with()` ([app/web/models.py](../../app/web/models.py)) reads the whole cache into the request whenever the request doesn't supply knees, and a device with a cached knee starts straight at it, with no ramp. Spinning HDDs stay pinned at a single reader. Reader concurrency never changes which duplicates are found — only read speed — because `idx` is threaded through the read→compute pipeline, so completion order can't reach `group_id` ([#526](https://github.com/jackal998/photo-manager/issues/526)/[#538](https://github.com/jackal998/photo-manager/issues/538) lex-min determinism).
- **Conditions / variants:** Default **on** (opt-out, experimental). A device ramps only when it has at least `_RAMP_MIN_SCAN_FILES` eligible image files (1584 — videos, GIFs and skipped files don't count; the conservative N=8 floor that bounds the worst-case first-scan sub-MAX read tax to 12.5 %) and a static count above 1; otherwise it runs at the static count with no ramp. The ramp only ever widens, and never past the static count, so it can under-use a device while climbing but never over-subscribe it — and it never changes results. A knee is written to the cache only when that device's ramp settled on a usable measurement **and** it was the only device ramping in that scan (a contention-free measurement); otherwise the next scan ramps again. A malformed or stale-recipe cache entry counts as a miss. The case it helps is hardware the static guess mis-fits (a low-channel NAS that 8 over-subscribes, an SSD under-served by `min(4, cpu)`); on hardware the static guess already fits, the knee equals the static value and it is a no-op. At the API boundary `autotune_read_knee` defaults to **false**, so a hand-rolled `POST /api/scan` that omits it scans without the ramp.
- **Related:** [#551](https://github.com/jackal998/photo-manager/issues/551) (Phase 4 — flipped the default to on / opt-out; Phase 3 added the dialog control; Phases 1–2 landed the knee logic and the in-pipeline ramp); [#652](https://github.com/jackal998/photo-manager/issues/652) (web read-back of `scan.read_knee_cache`); [#743](https://github.com/jackal998/photo-manager/issues/743) (the web checkbox persists its state). Pinned by `tests/test_autotune.py` (knee math), GATE-1 `tests/test_scan_pipeline.py::TestPipelineReadKneeRamp` (the real ramp finds the knee on a synthetic cliff), GATE-2 `tests/integration/test_autotune_ab.py` (the no-regression A/B), `tests/test_web_scan_routes.py::TestCalibrationReadback` + `::TestBusReadKneeMeasured` (web read-back and persist) and `frontend/src/components/ScanDialog.test.tsx` ("loads the persisted auto-tune-read-knee preference on open (#743)"); QA scenario [`qa/web/scenarios/s66_autotune_read_knee.py`](../../qa/web/scenarios/s66_autotune_read_knee.py) (autotune at default-on still yields the correct grouping).

### Scan dialog — hash pool mode
- **Area:** Scan

- **Entry point:** `scan.hash_pool` key in `settings.json` (power-user escape hatch, default `"auto"`) — resolved by `WebScanRequest.resolved_with()` ([app/web/models.py](../../app/web/models.py)) on every `POST /api/scan` that leaves `hash_pool` unset (the Scan dialog never sets it), and acted on by the HASH stage in [core/app_service/scan_runner.py](../../core/app_service/scan_runner.py). There is no user-facing control: calibration is always on ([#560](https://github.com/jackal998/photo-manager/issues/560)).
- **Trigger:** Always — resolved on every scan start.
- **Behaviour:** Selects the executor for the HASH stage. `"thread"` runs the per-file hash work on in-process thread pools. `"process"` runs the picklable `run_hash_for_record` on `ProcessPoolExecutor`s so CPU-bound hashing escapes the GIL across cores. `"auto"` (the default) times a sample (up to 96 files, stratified across devices) of the *real* scan data through both executors, **projects each to the actual file count** (`thread_per_file × N` vs `spawn_cost + process_per_file × N`) and runs the lower one — so process's one-time spawn cost is charged once against the whole run, not against the sample. Process's per-file rate and spawn cost are measured separately with a cold/warm two-batch split; the projected totals and components go to the scan log. With `"auto"`, the `Hashing … (workers=…, pool=…)` log line names the resolved `thread` or `process`; any other setting is logged as written (an unknown value such as `garbage` shows as `pool=garbage`). Any value other than `"auto"` or `"process"` runs on threads. Outcome routing (corrupt-file skips, EXIF-queue handoff) is identical in both modes — in process mode the parent drains completed futures and routes them, since a worker subprocess can't touch the cancel token or the queue. The same calibration pass also times the grouping stage's micro-rates and derives this machine's BK-tree floor from them ([#526](https://github.com/jackal998/photo-manager/issues/526)).
- **Fingerprint cache (PR3b):** the first `"auto"` scan's measured rates are stored in `settings.json` under `scan.hash_pool_cache`, keyed by `hash_pool_fingerprint` — a digest of `cpu_count`, the sorted source paths + recursive flags, and the `HASH_RECIPE_VERSION` / `GROUPING_STRATEGY_VERSION` tokens. `SseScanBus.hash_pool_measured` ([app/web/routes/scan.py](../../app/web/routes/scan.py)) writes the entry the moment calibration finishes — before the long hash pass, so it survives a mid-scan cancel — and `resolved_with()` looks it up under the identical fingerprint on the next scan. A later scan of the same library on the same machine reuses the cached rates, re-projecting them to the *current* file count without the ~2 s measurement, so the pick still adapts if the file count changed. A different machine or folder set, a recipe-token bump, or a malformed cache entry misses and re-measures.
- **Always-on calibration ([#560](https://github.com/jackal998/photo-manager/issues/560)):** `"auto"` is the default and there is **no user-facing toggle** — every scan either **reuses the cached rates** (cache hit) or **calibrates silently** (cache miss) before the hash pass, since the per-scan cost is low. `scan.hash_pool` = `"thread"` / `"process"` in `settings.json` still overrides `"auto"` verbatim (no fingerprint, no calibration).
- **Conditions / variants:** Because `"auto"` decides per scan, the Windows `spawn` cost (re-importing PIL/rawpy in each worker, ~150–300 ms each) is only paid when process actually wins. Calibration is skipped (→ `thread`) when fewer than 24 files are queued and there is no cached entry, since spawn/pickle overhead swamps the signal on tiny scans. In process mode each physical device gets its own process pool, sized like the thread-mode readers ([#610](https://github.com/jackal998/photo-manager/issues/610)). Cancellation in process mode stops submitting work and cancels queued files (`shutdown(wait=False, cancel_futures=True)`). [#549](https://github.com/jackal998/photo-manager/issues/549)(b): the process branch uses an explicit `try/finally` with `shutdown(wait=False)` rather than `with ProcessPoolExecutor()` — whose `__exit__` runs `shutdown(wait=True)` and would hold a cancelled scan until every in-flight `read_bytes()` finished — so a cancel returns promptly; #549(a) assigns each pool's worker processes to the kill-on-close job so an ungraceful exit of the app reaps them too.
- **Multi-device + NAS shortcut ([#554](https://github.com/jackal998/photo-manager/issues/554) / [#609](https://github.com/jackal998/photo-manager/issues/609) — direction inverted 2026-06-08):** when `"auto"` is active and the scan spans **two or more physical devices with at least one remote (NAS)**, the thread-vs-process calibration is **skipped** and `"process"` is chosen unconditionally (a cached grouping floor is still applied). #554 originally returned `"thread"` here on the bet that per-device thread I/O overlap (HDD 1 reader + NAS 8 readers) would dominate. The 2026-06-08 remediation measured the bet on the real D+J workload with per-second pipeline instrumentation and found the opposite: the shared compute pool is GIL-bound, effective parallelism plateaus at ~2-4 slots, and mixed big+small file interleave (NAS small JPEGs queueing behind 100-130 MB ProRAW DNGs in the shared read→compute queue) triggers 70-second stretches with zero compute completions. The per-device read overlap is real but downstream-gated by the GIL-bound compute pool, so it doesn't pay back. D+J 3400-file apples-to-apples: thread → 601 s timeout (89 % done, projects to ~678 s full) vs process → 421 s complete = **1.6× faster end-to-end**. Single-device and all-local scans are unaffected — calibration still runs and thread can legitimately win (no GIL contention, spawn cost > GIL escape gain). Decision record: `docs/audits/scanner-perf-mixed-workload-process-pool-2026-06-08.md`.
- **Related:** [#486](https://github.com/jackal998/photo-manager/issues/486) (PR1 extracted the picklable compute path); [#652](https://github.com/jackal998/photo-manager/issues/652) (web read-back of `scan.hash_pool` and the cache). Pipeline contract pinned by `tests/test_scan_pipeline.py::TestHashPoolSetting` (incl. unknown value → thread) + `::TestHashPoolCalibration` (projection, small-scan skip, fingerprint + recipe-version invalidation, `test_store_hash_pool_rates_round_trips_through_settings`, multi-device+NAS → process) + `::TestScanTeardownGaps` (no `shutdown(wait=True)` on cancel, kill-job assignment, per-device process pools); web persist + read-back by `tests/test_web_scan_bus.py::TestBusHashPoolMeasured` and `tests/test_web_scan_routes.py::TestCalibrationReadback` (incl. a fingerprint-symmetry pin). Real cross-process spawn is validated by real-world runs, not CI.

### Scan dialog — hash workers (NAS-aware auto, no UI control)
- **Area:** Scan

- **Entry point:** None in the UI — the Scan dialog has no worker-count control. Per-device counts come from [`scanner/workers.py`](../../scanner/workers.py) `hash_workers_for_root` and are applied by the HASH stage in [core/app_service/scan_runner.py](../../core/app_service/scan_runner.py); device identity comes from `device_key` in [infrastructure/device_key.py](../../infrastructure/device_key.py) (re-exported by `scanner/workers.py`).
- **Trigger:** Computed fresh from the scanned files' devices at the start of every HASH stage; no manual override.
- **Behaviour (#548 — per-device concurrent pools):** Records are partitioned by physical device (`device_key`, e.g. `D:` vs `J:`), and the HASH stage runs one reader pool **per device, all concurrently**, each sized by `hash_workers_for_root`: NAS (Windows network drive) → 8, local **spinning HDD** → 1 (single sequential reader, seek-minimising — the disk is the bottleneck at ~97 % active / 38 % CPU, and one reader keeps the head moving sequentially without inter-file seek bouncing; two readers still bounce the head between two concurrently-open files), other local (SSD / NVMe / unknown) → `min(4, os.cpu_count())`. On a mixed scan (local HDD + NAS) the NAS-latency-bound reads overlap the HDD-seek-bound reads instead of queueing behind them, and the HDD itself is no longer over-subscribed. The scan log lists the per-device count and file count (e.g. `D:=1×<n>f, J:=8×<m>f`). The HASH **pool type** (thread vs process) is a separate axis chosen by the [#486 calibration](#scan-dialog--hash-pool-mode), whose sample is stratified across devices so the pick is fair on a mixed scan. **Process** mode also runs one pool per device with the same counts ([#610](https://github.com/jackal998/photo-manager/issues/610)). The request's flat `workers` value (default 4 — the dialog never sends it) now only sizes the calibration sample's executors and appears in the `Hashing … (workers=…)` log line. **NAS server collapsing ([#565](https://github.com/jackal998/photo-manager/issues/565)):** `device_key` maps all Windows drive letters that resolve to the same physical NAS server into **one `\\SERVER` bucket** — e.g. H: and J: on `\\Nas-Host` both become `\\NAS-HOST` and share a single 8-reader pool. Before #565 each mapped letter produced its own device bucket (H: = 8 readers, J: = 8 readers = 16 concurrent SMB reads hammering one NAS box — over-subscription). The collapsing uses `WNetGetConnectionW` via an injectable resolver, memoized per letter per process. Native UNC source paths on the same server (e.g. `\\SRV\share1` and `\\SRV\share2`) also collapse to `\\SRV` without a resolver call. `is_remote_drive` returns True for bare `\\SERVER` keys so `hash_workers_for_root` still yields 8 for the collapsed bucket. Fail-open: any resolver error, non-Windows, or unresolvable letter → falls back to the per-letter key (H: and J: stay distinct), never crashes.
- **Read/compute pipeline split ([#566](https://github.com/jackal998/photo-manager/issues/566)):** in **thread** mode the HASH stage no longer fuses I/O and CPU in one per-file task. Each file flows through a two-stage pipeline: per-device **reader** pools (the #548 counts — HDD=1, NAS=8) each issue one `read_bytes()` (`read_for_record`) whose result goes into a bounded read→compute queue (`maxsize=128`), and a single `cpu_count`-wide **compute** pool drains it (`compute_from_bytes` — SHA + decode + pHash/dHash, the same recipe `run_hash_for_record` uses). This decouples disk-read latency from CPU decode: a reader blocked on an HDD seek no longer stalls a core that could be decoding, and the NAS readers keep the buffer full while the CPU saturates. On a real mixed HDD+NAS scan this measured **~2.3× faster with the throughput sawtooth (忽高忽低) roughly halved** — the fused path serialised read+decode within each task, so utilisation oscillated. Invariants preserved: the single-read guarantee (#446) holds (`read_for_record` reads once; `compute_from_bytes` works from those bytes, RAW via `rawpy.imread(io.BytesIO(data))` — #591 replaced the dead `rawpy.open_buffer` call; video/gif/skip carry `data=None` and stream SHA from disk so the #453 RAM ceiling holds); `idx` is threaded through both stages so results scatter to `hash_results[idx]` in walk order, keeping `classify()` determinism (lex-min `group_id`, the rescore key) unchanged. Cancellation composes with #561 — a cooperative `put(timeout=)` + cancel-token recheck plus `_drain_queue_nowait` release any reader wedged on a full queue before the compute sentinel and the exif kill/sentinels run. **Process** mode + calibration keep the fused `run_hash_for_record`; the split lives only in the thread path. **RAM backpressure ([#587](https://github.com/jackal998/photo-manager/issues/587) / [#596](https://github.com/jackal998/photo-manager/issues/596), replacing #570's task-count semaphore):** `ThreadPoolExecutor.submit()` never blocks, so a queue bound alone cannot cap memory, and a count cap still allows 128 × 130 MB DNGs in flight. Each reader therefore reserves its file's bytes against a byte budget before the bytes enter the queue, and the compute done-callback releases them. The budget is half of physical RAM clamped to 256 MiB–2 GiB (1 GiB if RAM can't be probed), split equally per device so one slow large-file device can't starve another's readers; a single file larger than its slice is admitted alone rather than deadlocking (`scanner/byte_budget.py`). **#569 — JPEG decode shrink-on-load:** `compute_from_bytes` calls `Image.draft("RGB",(256,256))` before `convert()`, decoding JPEG/MPO at ~1/4 resolution (a no-op on PNG/WebP/HEIC/RAW) — ~4× faster JPEG decode. pHash/dHash/mean-color all downsample far below 256px so grouping is unchanged (A/B on 597 real JPEGs: 0 over the threshold, 0 group-membership flips; true `px_w`/`px_h` are read before `draft()` mutates the size). The win lands on **warm re-scans (~5–6×) and compute-bound hardware**; a read-bound first scan is unchanged (its bottleneck is disk/NAS read, not decode). **#822 — EXIF Orientation is applied before pHash/dHash:** `ImageOps.exif_transpose` runs between `draft()` and `convert()` on every non-RAW path, and on the RAW embedded preview (which carries the camera's Orientation in its own EXIF — measured: `raw.sizes.flip` equals that tag on every sampled DNG, and the `postprocess` full-decode fallback needs no transpose because LibRaw applies the flip itself). Previously no orientation was applied anywhere in the hasher, so a copy whose rotation had been baked into its pixels (an export, an edit, a messenger re-save) hashed differently from its EXIF-rotated original and the pair **missed the near-duplicate tier entirely** — a silent false negative on the 19.4 % of this library that carries a non-identity Orientation tag. A/B on 200 real NAS files: all 50 files with a *valid* non-identity Orientation (6/3/8) now hash as their oriented pixels; the 20 carrying the out-of-spec value `0` are correctly left unrotated (Pillow maps only 2–8 to a transpose, matching Explorer/Lightroom). **#826 — the RAW path opens LibRaw once and hashes a reduced preview:** the embedded preview and `raw.sizes` now come off the same handle (it used to open LibRaw twice per file — 0.34–0.38 s per file on 124–129 MB iPhone ProRAW DNGs with the bytes already in RAM), and that preview goes through the same `draft("RGB",(256,256))` the JPEG path uses. On ProRAW the preview is the **full-sensor 8064×6048 = 48.8 MP** frame, not the "1024×768 thumbnail" the old code comment assumed, so pHash was running on ~64× the needed pixels; measured on 25 real DNGs the per-file compute (bytes already in RAM) drops **429 ms → 133 ms median**. True `px_w`/`px_h` still come from `raw.sizes`, never from the preview. **Both changes move hash values, so they share ONE `HASH_RECIPE_VERSION` bump (`"3"` → `"4"`)**; an Orientation-1 non-RAW file is bit-identical to recipe `"3"` (A/B: 105/105 exact parity, pinned in CI by `tests/test_hasher.py::TestHashRecipeParity`). **What the bump does:** the token has exactly one code consumer — `hash_pool_fingerprint` (`core/app_service/scan_runner.py`) — so it invalidates the #486 calibration cache and nothing else. No stored manifest row is keyed to the recipe, so **an existing manifest gets no staleness signal**: its rows keep their recipe-`"3"` hashes and its rotated pairs stay ungrouped **until the user re-scans that library**. Folding both changes into one bump is what makes that re-scan necessary once rather than twice.
- **Conditions / variants:** NAS detection uses Windows `GetDriveTypeW`; the local spinning-disk cap uses the `IncursSeekPenalty` storage IOCTL (`disk_incurs_seek_penalty`, behind an injectable seam). Both fail open: off Windows, or on any detection failure / non-drive-letter root, the device falls through to the SSD-safe `min(4, cpu)` — so a single-device SSD-only scan runs one pool at the historical local count, and a misdetected device is never throttled below that default. Only a **confirmed** spinning HDD gets the single-reader cap. There has been no worker-count control since the [#449](https://github.com/jackal998/photo-manager/issues/449) spinbox was removed, and nothing reads a legacy `scan.workers` setting (orphaned, harmless). Runtime per-device concurrency *calibration* (measuring each device's knee instead of classifying it) shipped separately as [#551](https://github.com/jackal998/photo-manager/issues/551) — see [Scan dialog — read-knee autotune opt-out](#scan-dialog--read-knee-autotune-opt-out).
- **Related:** [#449](https://github.com/jackal998/photo-manager/issues/449) (introduced the spinbox, since removed); [#548](https://github.com/jackal998/photo-manager/issues/548) (per-device concurrent pools); [#452](https://github.com/jackal998/photo-manager/issues/452) (the WALK stage's sibling per-source parallelism); [#565](https://github.com/jackal998/photo-manager/issues/565) (NAS server collapsing); [#566](https://github.com/jackal998/photo-manager/issues/566) (read/compute pipeline split — ~2.3× on mixed HDD+NAS); [#587](https://github.com/jackal998/photo-manager/issues/587) / [#596](https://github.com/jackal998/photo-manager/issues/596) (per-device byte budget); [#610](https://github.com/jackal998/photo-manager/issues/610) (per-device process pools). ### Scan walk — skip-on-error traversal
- **Area:** Scan

- **Entry point:** `_iter_tree` in [scanner/walker.py](../../scanner/walker.py) — the directory traversal primitive behind the WALK stage.
- **Trigger:** Fires automatically during every scan when the walker descends into a source tree that contains an inaccessible entry — typically a broken symlink / junction reparse point (e.g. `node_modules\.bin\acorn`).
- **Behaviour:** The walker used to be `root.rglob("*")` / `root.glob("*")`. `rglob` is a generator: when recursive descent reached an unreadable reparse point, `os.scandir` raised `OSError` [WinError 1920] *from inside* the generator, the exception escaped the walk, and the **entire scan failed on the first bad entry** — even though thousands of good files remained, and the per-path guards (symlink / skip-dir / extension filters) never got a chance to run. The traversal is now a manual `os.scandir` stack: each `scandir` call and each `entry.is_dir()` probe is wrapped in `try/except OSError`, so one inaccessible entry is logged once (a `WARNING` naming the path, in the application log — not in the Scan dialog's log pane) and skipped while the walk keeps going. All the per-path guards (the #491 cancel checkpoint, the #169 Win32-unsafe-name warning, the symlink / skip-directory / `SKIP_FILENAMES` / `MEDIA_EXTENSIONS` filters, the #448 progress callback, and the `limit` cutoff) run unchanged on the new traversal.
- **Conditions / variants:** A symlinked *directory* is not descended into at all (`entry.is_dir(follow_symlinks=False)`), so files buried under it are skipped one step earlier than the per-file `_traverses_symlink` guard would — same end result. A Windows **junction** is different: Python does not report it as a symlink (`is_symlink()` is False), so it passes `is_dir(follow_symlinks=False)`, the walker descends into it, and the per-file guard does not exclude its files (CPython semantics, not live-probed; the walker's own docstring says junctions are excluded). An unreadable *root* (or a subdirectory that becomes unreadable mid-descent) is logged once and yields its partial result rather than failing the scan; if nothing readable is left, the scan ends as an empty scan. A source root that does not exist at all is different: `scan_sources` raises `FileNotFoundError` and the scan fails (see [Web — scan dialog invalid source path](web-ui.md#web--scan-dialog-invalid-source-path)).
- **Related:** [#509](https://github.com/jackal998/photo-manager/issues/509); the stuck-progress-bar symptom this looked like is [#510](https://github.com/jackal998/photo-manager/issues/510) (see [Scan dialog — stage / throughput / ETA progress](#scan-dialog--stage--throughput--eta-progress-424)). Walker contract pinned by `tests/test_walker.py::TestScanAbortResilience`.

### Scan walk — recycle-bin / system folders are never walked
- **Area:** Scan

- **Entry point:** `has_skip_directory_ancestor` + `SKIP_DIRECTORIES` in [scanner/walker.py](../../scanner/walker.py) / [scanner/media.py](../../scanner/media.py) — the per-path guard in the WALK stage.
- **Trigger:** Fires automatically during every scan, for every candidate media file whose path has an ancestor directory named (case-insensitively) `$RECYCLE.BIN`, `System Volume Information`, `.Trashes`, `.Trash`, or `#recycle`.
- **Behaviour:** The file is not indexed — it never reaches hashing, grouping, scoring or the manifest. Everything under those folders is already-deleted or OS-managed scratch space; including it also breaks the delete flow, because `send2trash` refuses to send a recycle-bin file back to the recycle bin (`WinError -2147024809`, the user-reported cluster behind #482). `#recycle` — Synology DSM's per-share Recycle Bin, which sits at the root of every share with the recycle bin enabled — was added in [#821](https://github.com/jackal998/photo-manager/issues/821); before that a source pointed at a NAS share root walked straight into the user's deleted files.
- **Conditions / variants:** The rule is an **ancestor** predicate bounded by the scan root, so (a) a file merely *named* like a skip folder (`#recycle.jpg`) and a folder whose name only *contains* one (`$RECYCLE.BIN backup 2019`) are scanned normally, and (b) a source deliberately pointed AT a recycle bin still walks its contents — the root is the user's declared scope. The same function is the single definition used by the manifest-open reconcile (see [Open Manifest — base flow](file-operations.md#open-manifest--base-flow)); the folder names live in exactly one place.
- **Related:** [#482](https://github.com/jackal998/photo-manager/issues/482) (Windows/macOS names), [#821](https://github.com/jackal998/photo-manager/issues/821) (Synology `#recycle` + the stale-row reconcile). Pinned by `tests/test_walker.py::TestWalkerSkipDirectories` and `::TestHasSkipDirectoryAncestor`; QA scenario [`qa/web/scenarios/s09_walker_exclusions.py`](../../qa/web/scenarios/s09_walker_exclusions.py) covers the sibling `SKIP_FILENAMES` / `MEDIA_EXTENSIONS` guards.

### Scan grouping — complementary RAW + lossy pair
- **Area:** Scan

- **Entry point:** The result tree after a scan — a RAW original and its lossy export now appear as **one review group** instead of two files the tree never shows. Classifier: [scanner/dedup.py](../../scanner/dedup.py) `_classify_format_group` / `_complementary_edges`.
- **Trigger:** A scan finds two or more files with an **identical** pHash where at least one is RAW (`.dng` / `.cr2` / `.cr3` / `.nef` / `.arw` / `.raf` / `.rw2` / `.tif` / `.tiff` — the extensions [scanner/media.py](../../scanner/media.py) `get_file_type` maps to `raw`) — i.e. a RAW plus its JPEG/HEIC export, or a CR2 plus its DNG conversion. No user action.
- **Behaviour:** The bucket forms one group (shared `group_id`) so the files are shown side by side. **No dedup decision is taken:** every member keeps `action = ""` (undecided / "Ref" tier), because a RAW and its lossy export are complementary — the user keeps both unless they decide otherwise. Aggressive auto-select ("delete all others") still cannot touch them: only rows the classifier positively marked `EXACT` / `REVIEW_DUPLICATE` are delete-eligible ([Scan dialog — auto-select aggressive ("delete all others")](#scan-dialog--auto-select-aggressive-delete-all-others)). Non-aggressive auto-select does lock the higher-scoring member as the group keeper, exactly as it does for any other group.
- **A RAW never causes its lossy export to be auto-deleted.** Because a RAW usually outscores its JPEG, joining a group can make the RAW the keeper — and the lossy row it displaced would otherwise lose the only protection it had (being the keeper) and fall into the auto-delete set if it happened to carry `EXACT`. So when a group's keeper is a RAW, the **best non-RAW row in that group is protected alongside it**, in both the scan-time aggressive path and the review-time [Apply best-copy](web-ui.md#web--context-menu-apply-best-copy-decisions-to-this-group) action ([core/services/auto_select.py](../../core/services/auto_select.py) `_raw_displaced_keepers`). Duplicates ranked *below* that row are still deleted — a RAW in the group does not switch auto-delete off wholesale.
- **Conditions / variants:** Only applies to an **exact** pHash match; a near-duplicate RAW/JPEG pair (Hamming 1-threshold) was already grouped by the near-duplicate tier. The pair is dropped — no group — when the two mean colours differ beyond the threshold ([#462](https://github.com/jackal998/photo-manager/issues/462)) or when dHash positively disagrees ([#524](https://github.com/jackal998/photo-manager/issues/524)): those are pHash false positives, not one shot. Same-stem RAW+JPG pairs in one folder were already grouped by the filename-cluster edge ([#88](https://github.com/jackal998/photo-manager/issues/88)); what changes here is the pair whose names or folders **differ** (a renamed or relocated export). **Existing manifests are unaffected until a rescan** — `group_id` is written at scan time and `ManifestRepository.rescore` does not recompute grouping. Measured on the author's 40,774-row library: 200 exact RAW+lossy pairs, of which 79 gain a shared `group_id`; 125 files that were invisible singletons enter review, and 442 of 8,304 existing groups get a different `group_id` because merged components take a new lexicographically-smallest anchor. **Read the 79 as base-code-vs-head-code, not as a count of what is wrong in the library today:** both figures come from re-running `classify()` over a copy of that manifest, and the reconstruction has no stored `dhash` / `mean_color`, so its grouping is slightly more permissive than the scan that wrote the file. The manifest's own stored grouping leaves only **15** of the 200 pairs ungrouped — that column is the residue of an older scan, not a base measurement.
- **Related:** [#824](https://github.com/jackal998/photo-manager/issues/824); prior art [#88](https://github.com/jackal998/photo-manager/issues/88) (group together, decide independently) and [#538](https://github.com/jackal998/photo-manager/issues/538) (edges decoupled from classification); rendering covered by [Similarity column](review.md#similarity-column) (the pair renders as Ref + `N*%` passenger); unit tests `tests/test_dedup.py::TestComplementaryGroupEdge`.

### Scan grouping — EXACT requires pixel identity
- **Area:** Scan

- **Entry point:** The result tree after a scan — a pHash-0 match with different bytes (a colour-graded edit, a resized copy, or the next frame of a burst) is no longer shown as an `EXACT` duplicate; it is a review row in the same group, and a demoted row shows the blue near pill rather than the purple exact pill even at 100 % (the badge keys on the action; [#1047](https://github.com/jackal998/photo-manager/issues/1047)). Classifier: [scanner/dedup.py](../../scanner/dedup.py) `_pixels_identical` / `_grey_identical` / `_format_review_row` / `_classify_format_group`; signatures: [scanner/hasher.py](../../scanner/hasher.py) `_pixel_signature` (colour) and `_grey_signature` (structure); scan-local store: [scanner/grey_store.py](../../scanner/grey_store.py).
- **Trigger:** A scan finds two or more lossy images (JPEG / HEIC / PNG / WebP) with an identical pHash and different bytes. No user action.
- **Behaviour:** `EXACT` now means pixel-identical. The keeper's row is unchanged; a format duplicate keeps `EXACT` only when all three hold: (1) the pixel dimensions are equal, or swapped by a 90° rotation (the EXIF-oriented original and its rotation-baked export); (2) the largest per-channel mean shift of the 32×32 RGB signatures is ≤ 4 (`FORMAT_DUP_MAX_CHANNEL_SHIFT`), which catches a colour edit; (3) on the 128×128 grey signatures, no 4×4-pixel block differs by more than 4 on average (`GREY_BLOCK_MAX`), and at most 16 of 16,384 pixels (0.1 %) differ by more than 8 (`GREY_TAIL_MAX`), which catches a person who moved, a shifted second shot or a changed line of text. Otherwise the row is `REVIEW_DUPLICATE` in the same group, with reason `same pHash, pixels differ (edited, resized or another shot)`, or `same pHash, pixel check unavailable` when a signature is missing. Its confidence is `high` when dHash agrees, or when the pixels are identical. When dHash is unknown and the pixels differ or cannot be checked, the match is not a row: it is a hint on ungrouped rows (`same pHash, pixels differ, dHash unavailable`, GROUPING 10). An all-lossy bucket is split by pixel identity (`_pixel_clusters`, GROUPING 14): each cluster is one picture's copies with its own keeper, so a copy is `EXACT` of its own picture, and the keeper of every further cluster is a `REVIEW_DUPLICATE` of the first keeper (same pHash, pixels differ) when the dHash agrees, or a hint when it does not; shot time is not read. Byte copies (same SHA-256) are unaffected.
- **Conditions / variants:** A `REVIEW_DUPLICATE` row remains aggressive-delete eligible unless its confidence is `low`, so a `high` pixel-differ row can still be marked for deletion by the aggressive auto-select; a `low` one never exists on a grouped row: a low match is a hint on an ungrouped row, so it is not delete-eligible. The gate runs last, after the time, mean-colour and dHash gates. Both signatures are computed at scan time and never persisted to the manifest. The grey signature (16 KB per image) is spilled during the scan to a temporary file in the system temp directory, and that file is deleted after classification, so memory stays flat. A file whose grey signature cannot be stored or read gets "pixel check unavailable", never `EXACT`. Since GROUPING 13, a row kept out of pHash grouping by the entropy, dimension or contrast gate (a flat, tiny or low-contrast image, such as a near-white screenshot) is still checked for pixel identity against the gated rows that share its pHash and its dimensions (or a 90° swap), after the same mean-colour and dHash gates; a pass is `EXACT` with reason `pixel-identical copy of <keeper> (low-contrast or flat image; pHash not trusted)`, anything less writes nothing (no review row, no hint) (`_rescue_identity`); since GROUPING 14 an undated row takes part too. `GROUPING_STRATEGY_VERSION` is `"14"` (`"8"` introduced this pixel-identity check; `"13"` extends it to the rows the pHash trust gates exclude; `"14"` splits the bucket by pixel identity instead of shot time; `"11"` replaces the 32×32 mean difference with the grey block and tail test); a manifest scanned under an older version keeps its old `EXACT` verdicts until it is re-scanned.
- **Related:** [Scan grouping — complementary RAW + lossy pair](#scan-grouping--complementary-raw--lossy-pair) (the other exact-pHash gate); [Scan grouping — same-moment bursts become a stack](#scan-grouping--same-moment-bursts-become-a-stack) (a burst frame that passes the gate still ends undecided); unit tests `tests/test_dedup_exact_pixels.py`, `tests/test_dedup_grey_gate.py`, `tests/test_grey_store.py`, `tests/test_hasher.py::TestRgb32PixelSignature` and `tests/test_hasher.py::TestGrey128Signature`, and the pipeline tests `TestGreySignatureSpill` in `tests/test_scan_pipeline.py`.

### Scan grouping — a lone Live Photo is not a group
- **Area:** Scan

- **Entry point:** The result tree after a scan — a Live Photo still and its video (same name, e.g. `IMG_0001.HEIC` + `IMG_0001.MOV`) is grouped only when the two files share a device-written identity. A video that is merely named like a still stays out of the group view, and both rows stay undecided. Classifier: [scanner/dedup.py](../../scanner/dedup.py) `_collect_pair_edges` / `_pair_pass` / `_assign_group_ids`; identity read: [scanner/exif.py](../../scanner/exif.py) `_CONTENT_ID_KEYS`.
- **Trigger:** Every scan's classify pass (Pass 4 collects the content-gated pair edges; Pass 5 assigns `group_id`). The identity is read by exiftool during the scan. No user action.
- **Behaviour:** A filename never creates an edge. A video pairs with another file only when both carry the same Apple **ContentIdentifier**, so a video links to its still and to its sibling videos of the same capture (exiftool reads `QuickTime:ContentIdentifier` on MOV/MP4 and `MakerNotes:ContentIdentifier` on HEIC and JPEG stills, compared case-insensitively). Non-Apple files, stripped copies and files whose identifiers differ never pair, whatever their names. A paired video shares its still's `group_id` only when the still is grouped for another reason: a byte copy or a high-confidence near-duplicate (a low-confidence hint never groups). A lone pair gets `group_id` None on both rows, keeps `action` `""` (or `UNDATED`) with reason `unique` (or `no EXIF DateTimeOriginal` for an undated row), is unscored, and so auto-select never locks the still as KEEP. Same-stem still<->still pairs (RAW+JPG, HEIC+JPG) get no stem edge and group only through the pHash tiers.
- **Conditions / variants:** Without exiftool on `PATH` no Live Photo pairs at all, because the identity cannot be read; the scan warning names this. A JPEG still whose cluster holds a video takes the exiftool path, since PIL does not parse the Apple MakerNote. A cluster whose joined stills sit in two groups that each hold a still is not bridged: its unjoined members keep `group_id` None, and their reason says `pair link skipped: its stills are in different groups`. A video-only group (a MOV's byte copies) joins the still it shares an identity with. `GROUPING_STRATEGY_VERSION` is `"14"`; a manifest scanned under `"13"` or earlier keeps its groups until it is re-scanned.
- **Related:** [#88](https://github.com/jackal998/photo-manager/issues/88) (the MOV is still hashed and stored and never dropped; only its group is now conditional); [Scan grouping — low-confidence matches never group](#scan-grouping--low-confidence-matches-never-group) (the hint rules a Live still follows like any other photo); unit tests `tests/test_dedup_live_pair.py`, `tests/test_dedup_content_pair.py`, `tests/test_dedup.py::TestLivePhotoPair`; QA scenario `qa/web/scenarios/s11_video_live.py` (checks that a pair without a shared identity stays ungrouped).

### Scan grouping — pHash contrast (quality) gate
- **Area:** Scan

- **Entry point:** The result tree after a scan — a near-black, near-flat, or otherwise low-contrast photo no longer groups with unrelated photos just because its pHash degenerated. Classifier: [scanner/dedup.py](../../scanner/dedup.py) `_phash_quality_ok` / `_classify_phash`; scalar: [scanner/hasher.py](../../scanner/hasher.py) `_phash_quality`.
- **Trigger:** A scan hashes an image whose `phash_quality` — the population standard deviation of its 32×32 grey working image (the image pHash hashes) — is below **16.0**. Typical cases: a night shot of a dark sky with two lights, an eclipse frame, an all-black screenshot. No user action.
- **Behaviour:** The file is excluded from **pHash** near-duplicate and exact-pHash grouping, so its degenerate 64-bit hash can no longer bridge unrelated photos into one chained group. It still gets **exact-SHA dedup** (a byte-identical copy is still `EXACT`), since GROUPING 13 the **pixel-identity** check against the other gated rows that share its pHash and its dimensions (a pixel-identical copy is `EXACT` with reason `pixel-identical copy of <keeper> (low-contrast or flat image; pHash not trusted)`; `_rescue_identity`, see [EXACT requires pixel identity](#scan-grouping--exact-requires-pixel-identity)), and its Live Photo pair edge, which needs a shared ContentIdentifier (a Live Photo video joins a group only when its still is grouped, see [a lone Live Photo is not a group](#scan-grouping--a-lone-live-photo-is-not-a-group)). Such a file with no grouping lands as an undecided row (`action = ""` or `UNDATED`) like any other unmatched file.
- **Conditions / variants:** The threshold is `classify(min_phash_quality=…)`, default `16.0`; `0` disables the gate. Measured on 519 real files (dedup-core research 2026-11-05, contrast probe): the three class-A frames read 5.67 / 5.63 (2020 eclipse) and 15.36 (2023 lights in the dark); the population medians are DNG 49.7, HEIC 50.3, JPEG 52.7, PNG 43.9, so the gate removes about 1 % of real photos (about 5 % of PNG screenshots). A manifest written before recipe `"5"` stores no quality (`NULL`) and such rows pass the gate, so an existing library groups exactly as before **until it is re-scanned**. Videos, GIFs and decode failures have no quality and also pass.
- **Related:** the sibling pHash gates — the entropy guard (#516, which cannot catch this case because the median split gives every photo popcount 32) and the dimension gate (#523); unit tests `tests/test_dedup_quality_gate.py` and `tests/test_hasher.py::TestPhashQuality`.

### Scan grouping — low-confidence matches never group
- **Area:** Scan

- **Entry point:** The result tree after a scan — a low-confidence match never groups two files, so a chain of screenshots forms no group; since GROUPING 14 three captures of one scene that hash alike are one group of review rows, because shot time is not grouping evidence. Classifier: [scanner/dedup.py](../../scanner/dedup.py) `_assign_group_ids` (high and pair edges only) and `_mark_hints`; hint producers `_classify_near_duplicates`, `_classify_format_group` and `_complementary_edges`.
- **Trigger:** Every scan's classify pass (Pass 5 unions the high edges; `_mark_hints` then writes the hint text). No user action.
- **Rule toggle (PR-4a):** a PNG-to-PNG pHash match that is not pixel-identical is a hint while **B7** (the screenshot rule) is on, which is the default. A pixel-identical PNG pair is `EXACT` even while B7 is on (GROUPING 12). Off, a matching PNG pair is judged like a photo.
- **Behaviour:** A low-confidence match (a screenshot pair that is not pixel-identical, or a pHash match with no dHash to confirm it) is a hint. Since GROUPING 14 a shot-time disagreement is not a cause: shot time is not grouping evidence, so a re-shot of the same scene that hashes alike is a `REVIEW_DUPLICATE` in one group (pixels differ) and a pixel-identical copy is `EXACT` whatever its EXIF dates say. It never creates, grows or merges a group, and it never sets an action. Each of its two files names the partner in its reason. An ungrouped file that a hint touches is `low`, stays undecided (`action` empty, or `UNDATED` without a shot date), and its reason carries the marker `hint only (not grouped):`. A grouped file only gains a `hint:` clause, so its action and confidence do not move. A format duplicate groups only when dHash agrees or the 32×32 pixels are identical. An exact-pHash RAW bucket groups as one complementary group whatever its members' shot times say; only the PNG-pair rule can still split a bucket. An undated file links whatever its content matches: the GROUPING 10 refusal of an undated row that would bridge two dated moments is gone since GROUPING 14. A row whose own near-duplicate link is refused keeps no duplicate verdict: it takes back its plain verdict, and the link appears only in its hint text. An EXACT copy (byte or pixel identity) still groups whatever its date.
- **Conditions / variants:** `GROUPING_STRATEGY_VERSION` is `"14"` (`"6"` introduced the hints; `"7"` adds the [same-moment burst stack](#scan-grouping--same-moment-bursts-become-a-stack) below; `"8"` adds the pixel-identity check for `EXACT`; `"9"` makes a lone Live Photo pair ungrouped, see [a lone Live Photo is not a group](#scan-grouping--a-lone-live-photo-is-not-a-group); `"10"` makes low-confidence matches never group and counts pixel identity as the second signal; `"11"` replaces the 32×32 mean difference of the pixel-identity check with the grey block and tail test; `"12"` makes a pixel-identical PNG pair `EXACT` while B7 is on; `"13"` checks pixel identity for the rows the pHash trust gates exclude, see [EXACT requires pixel identity](#scan-grouping--exact-requires-pixel-identity); `"14"` removes shot time from every grouping decision, so a match is judged on content alone). A manifest scanned under an older version keeps its old groups until it is re-scanned. Hints are processed in sorted order, so the result does not depend on record order.
- **Related:** [#1030](https://github.com/jackal998/photo-manager/issues/1030), [#1032](https://github.com/jackal998/photo-manager/issues/1032); research report `docs/audits/dedup-core-research-2026-11-05.md` §5.1 (T3 similar — hint only, never groups). Pinned by `tests/test_dedup_hint_edges.py` and `tests/test_dedup_grouping10.py`.

### Scan grouping — same-moment bursts become a stack
- **Area:** Scan

- **Entry point:** The result tree after a scan — a burst series (a GoPro or compact-camera run, one frame per second) shows as one review group whose frames are all undecided and none is a delete candidate, instead of one REVIEW row per frame; each frame wears the **Keep all · burst** decision chip in the result tree ([#1047](https://github.com/jackal998/photo-manager/issues/1047)). Classifier: [scanner/dedup.py](../../scanner/dedup.py) `_mark_burst_stacks` / `_burst_frames` / `_is_burst` / `_relabel_burst`.
- **Trigger:** A group formed by the classify pass whose dated, pHash-bearing frames are each at most `BURST_MAX_GAP_S` (2 s) from the next, while the run's span is longer than 2 s. No user action.
- **Rule toggle (PR-4a):** the stack is made only while **B5** (the burst rule) is on, which is the default. Off, each frame keeps its classifier verdict.
- **Behaviour:** Every frame that is not a byte copy becomes `action = ""` at `match_confidence = "high"`, with reason `burst stack (keep all): N frames over S s`. A byte copy (same SHA-256 as its `duplicate_of`) keeps its `EXACT` verdict and reason, so a true copy inside the burst stays delete-eligible. The pass adds no edge and merges nothing; `group_id` is unchanged. A file that a low hint touches stays ungrouped and undecided (`low`, with the `hint only (not grouped):` marker), so it is not a frame. A burst is a run of consecutive frames at most 2 s apart inside a group (`_burst_runs`); since GROUPING 14 a group is formed on content alone and may also hold a near-duplicate shot hours away, which is not a frame of the run and keeps its own verdict. A Live Photo video peer (no pHash) is not a frame and keeps its verdict.
- **Conditions / variants:** The 2 s gap is `BURST_MAX_GAP_S`; since GROUPING 14 it is the only place the grouper reads a shot time, and it relabels verdicts only, never groups. A group with a wider gap (an undated bridge, a timezone-shifted copy) is left unchanged. A same-second burst (span 2 s or less) keeps its REVIEW verdicts and stays auto-deletable. There is no span cap: a long timelapse at 2 s per frame is still one stack. `GROUPING_STRATEGY_VERSION` is `"14"` (`"7"` introduced the burst stack; `"9"` is the lone Live Photo pair, see above); a manifest scanned under an older version keeps its old verdicts until it is re-scanned.
- **Related:** dedup-core research 2026-11-05 §5.1 (T2); unit tests `tests/test_dedup_burst_stack.py` and `tests/test_auto_select.py::TestNonKeepersForAggressiveDelete::test_burst_frames_never_delete_eligible`.

### Developer tool — memory probe
- **Area:** Scan

- **Entry point:** `scripts/memory_probe.py` (`snapshot()`, `track_qt_alloc()`), gated by `PHOTO_MANAGER_MEMORY_PROBE=1`. **No call site remains in the shipped app.** The five measurement points, and the `--manifest` / `PHOTO_MANAGER_PROBE_MANIFEST` / `PHOTO_MANAGER_PROBE_RELOAD_COUNT` auto-load handling, lived in desktop-client modules deleted in #646.
- **Trigger:** An explicit `snapshot(label, point)` call made while `PHOTO_MANAGER_MEMORY_PROBE=1`. Setting the variable before launching the web app records nothing, because nothing in `app/`, `core/`, `infrastructure/`, `scanner/` or `launcher.py` calls the probe.
- **Behaviour:** Each `snapshot()` appends one JSONL row to `~/AppData/Local/PhotoManager/logs/memory_probe_<RUN_ID>.jsonl`. A row holds:
  - `tracemalloc` totals and the top 30 allocation sites;
  - process RSS / commit / private bytes (Windows ctypes; `/proc/self/status` RSS elsewhere);
  - available system memory;
  - `gc` generation counts;
  - live-instance counts for a fixed list of type names.

  In a Qt-free process, tracemalloc, the memory counters and the `PhotoRecord` / `PhotoGroup` instance counts still mean something. The Qt parts do not: `qt_counter_qstandarditem` / `qt_counter_qimage` stay 0 because nothing calls `track_qt_alloc()`, and the `QStandardItem`, `QImage`, `QPixmap`, `QThread` and `ManifestLoadWorker` type counts are 0 without Qt.

  Optional TRIM mode (`PHOTO_MANAGER_MEMORY_PROBE_TRIM=1`) calls `SetProcessWorkingSetSize` after a point-5 snapshot and records a point-6 row. An optional referrer dump (`PHOTO_MANAGER_MEMORY_PROBE_REFERRERS=<type,…>`) walks `gc.get_referrers()` for the named types at point 5 and writes a sibling `referrers_<type>_<RUN_ID>.jsonl`.
- **Conditions / variants:** `snapshot()` returns immediately when the variable is unset. `scripts/generate_probe_fixture.py` still produces a reproducible ~13k-row SQLite manifest (seed 42). Measuring the web server would need new `snapshot()` calls at web-side points, for example around `GET /api/manifest`; none exist today.
- **Related:** `docs/audits/memory-probe.md` (usage guide, row schema, 4-hypothesis decision table — written for the desktop wiring); `tests/test_memory_probe.py` (tests the module in isolation); issues #614, #619, #624.
