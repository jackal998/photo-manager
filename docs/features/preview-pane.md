### Preview pane — byte-budget LRU cache
- **Area:** Preview pane

- **Entry point:** `infrastructure/image_service.py`: `ImageService.__init__` and `_ByteBudgetLRUCache`. The web server creates one `ImageService` at start-up (`app/web/main.py` lifespan) and `GET /api/image` ([app/web/routes/image.py](../../app/web/routes/image.py)) uses it.
- **Trigger:** Every `GET /api/image` the web client makes. Result-tree row thumbnails, grid tiles, the preview-pane image and Execute-dialog thumbnails ask for `size=512`. The full-resolution viewer asks for `size=0`.
- **Behaviour:**
  - The in-memory image cache evicts by byte budget instead of item count. There are two tiers: a thumbnail tier for requests whose longest side is ≤ 256 px, and a preview tier for everything larger, including full-res (`size=0`).
  - Total budget = `min(256 MB, RAM // 32)`, split 1:3 between the tiers (≈64 MB / ≈192 MB with ≥ 8 GB RAM; 16 MB floor each). When a tier exceeds its budget, the least-recently-used entry is evicted.
  - The web client asks only for 512 px or full size, so everything it loads lands in the preview tier. The thumbnail tier serves only requests that omit `size` (the route default is 256).
  - **Disk cache:** versioned files under `~/AppData/Local/PhotoManager/thumbs/v1/<sha1>.jpg` by default. The settings key `thumbnail_disk_cache_dir` moves that root (environment variables are expanded), and its sibling `video_transcode_cache_dir` moves the video-transcode cache the same way. The web server's lifespan loads `settings.json` through `load_settings()` and hands it to both `ImageService` and `TranscodeService` ([#874](https://github.com/jackal998/photo-manager/issues/874)). Before #874, the web client constructed both services with no settings and wrote every cache to `%LOCALAPPDATA%` no matter what was configured.
  - The **byte budget itself is not a settings key**; it comes from the RAM probe above. A recipe-version bump invalidates the old namespace.
  - On the first start after an upgrade, unversioned `.jpg` files directly under `thumbs/` are deleted. The web server builds `ImageService` without a status reporter, so the one-time "Rebuilding thumbnail cache (version N) — this is a one-time operation." message reaches the server log only.
- **Cache-key freshness (web audit Correction #11):** the cache key is `sha1(path|size|source_mtime_ns)`. The source mtime is folded in so that overwriting a photo in place (a crop or re-export saved to the same path by another program) produces a fresh key, instead of the disk/memory cache serving the pre-edit bytes indefinitely. `GET /api/image` stats the source once per request and threads that value into both the decode call and the disk-cache-path lookup used for the ETag, so an in-place edit also changes the ETag without a second stat. Responses carry `Cache-Control: public, max-age=86400, stale-while-revalidate=604800` (full-res: `max-age=3600`), so within that window the browser may keep showing its own cached copy until it revalidates.
- **Conditions / variants:**
  - **DNG fast path:** DNG files use the embedded JPEG (rawpy `extract_thumb`) when the embedded image's longest side is ≥ the requested side. That means ≥ 512 px for the web's previews and thumbnails; any embedded JPEG qualifies for a full-res request. A full `postprocess` decode runs only when the embedded image is too small or absent.
  - **EXIF Orientation is applied** to the embedded JPEG with Pillow's `ImageOps.exif_transpose` before it is re-encoded, so the JPEG the server returns is already upright. Without this, portrait-grip iPhone ProRAW DNGs (which store landscape pixels + Orientation=6/8 in the embedded JPEG's EXIF) would be served 90° rotated relative to Lightroom / File Explorer. The bitmap (non-JPEG) thumb branch is unaffected: rawpy delivers that array in the correct orientation natively.
  - **#865 — the embedded JPEG is decoded in draft mode.** For a capped request, the JPEG branch calls `Image.draft` before `exif_transpose`, so libjpeg decodes at the largest 1/8, 1/4 or 1/2 DCT reduction that meets the cap instead of at full size, and the transpose and LANCZOS shrink run on that smaller image. `draft` must precede `exif_transpose`: `exif_transpose` calls `load()`, after which `draft` is a silent no-op (the same idiom and ordering as the hasher's #569/#822 draft). Full-res requests (`size=0`) never draft. The "too small → fall through" test is judged from the pre-draft header size and runs before any pixel is decoded, so a rejected thumb no longer costs a full decode and a transposed copy first.
  - **The one visible trade-off — an undershoot of up to 2 % of the cap:** the DCT scaler offers only the 1/2, 1/4 and 1/8 steps, so a frame whose next step lands just under the cap would otherwise decode one step larger than needed (a 4032 px frame at the 512 cap would take 1/4 instead of 1/8). `_DRAFT_UNDERSHOOT = 0.02` accepts a long edge up to 2 % under the cap when that buys a whole step; a frame whose next step falls further under the cap decodes at the next larger step — at full size only when even the 1/2 step would undershoot — and is then shrunk exactly onto the cap. The draft box is matched to the image's aspect ratio, not square: `draft` constrains **both** axes (`min(w // req_w, h // req_h)`) while `thumbnail` fits only the long edge, so a square request would make the short edge binding and decline reductions that are fine.
  - **Where the #865 numbers come from:** they were measured on the J: NAS through the retired desktop preview stack at its 2048 px cap. There, iPhone ProRAW's embedded frame is the whole 8064×6048 sensor ([#826](https://github.com/jackal998/photo-manager/issues/826)), so a click decoded 3 MP rather than 48 MP. This library's 4032×3024 frames sit 1.6 % above the half-scale step for a 2048 cap, so they rendered at 2016 px instead of 2048 (≤ 41 px at that cap). The rule is relative to the cap: at the web's 512 px request the tolerance is ≤ 10 px, and the same 4032×3024 frames take the 1/8 step and come back at 504 px.
- **Related:** [#622](https://github.com/jackal998/photo-manager/issues/622) Phase 1 + Phase 3 measurement; [#865](https://github.com/jackal998/photo-manager/issues/865); [#874](https://github.com/jackal998/photo-manager/issues/874); `infrastructure/image_service.py`; `tests/test_image_service.py`; `app/web/routes/image.py`; `app/web/main.py`; `tests/test_web_image_route.py`; `docs/audits/preview-phase3-results-2026-09.md`.

### Preview pane — per-device request coordinator + 1-ahead prefetch
- **Area:** Preview pane

- **Entry point:** None — removed with the desktop client in #646. [#887](https://github.com/jackal998/photo-manager/issues/887) tracks measuring whether the web client needs one, and porting it if the NAS numbers say so.
- **Trigger:** The desktop coordinator ran on every single-view preview and grid-thumbnail request.
- **Behaviour:**
  - The desktop client serialised image decodes per physical device, using the `infrastructure/device_key.py` bucket the scanner uses ([#565](https://github.com/jackal998/photo-manager/issues/565)). It dropped superseded clicks before they read from disk ("D waits for A"), discarded a finished image whose selection had moved on, and prefetched the next group's first image.
  - **The web client has none of this.** Each `<img>` fetches `GET /api/image` on its own. FastAPI runs that plain-`def` handler in its worker threadpool ([#790](https://github.com/jackal998/photo-manager/issues/790)) with no per-device queue and no cancellation check, so a decode the server has started runs to completion even after the browser has moved on.
  - Result-tree, grid-tile and Execute-dialog thumbnails use the browser's native `loading="lazy"`. There is no prefetch.
  - The server-side decode throttles in `infrastructure/image_service.py` are `_FULLRES_DECODE_SEM = threading.BoundedSemaphore(2)`, around full-resolution `rawpy` demosaics, and the Shell/WIC thumbnail path's two-worker `_wic_executor` (each call waits at most 10 s). Neither is per device.
- **Conditions / variants:** **Source-mtime stat TTL:** `_MtimeStatCache` (5 s TTL, bounded to 512 paths) still exists in `infrastructure/image_service.py`, but only callers that do not pass a source mtime use it. `GET /api/image` always stats the source itself and passes that value in, so no web request goes through the TTL. An in-place edit is picked up on the next request, not after up to 5 s.
- **Related:** [#622](https://github.com/jackal998/photo-manager/issues/622) Phase 2 (the desktop coordinator; its Phase 3 measurement is in `docs/audits/preview-phase3-results-2026-09.md`); [#887](https://github.com/jackal998/photo-manager/issues/887); `infrastructure/image_service.py` (`_FULLRES_DECODE_SEM`, `_MtimeStatCache`); `app/web/routes/image.py`; unit tests `tests/test_image_service.py` (`TestMtimeStatCacheTTL`); `infrastructure/device_key.py` is now used only by the scanner.

### Preview pane — full-resolution viewer
- **Area:** Preview pane

- **Entry point:** [frontend/src/components/FullResViewer.tsx](../../frontend/src/components/FullResViewer.tsx). A single overlay is mounted in `App.tsx` and is open while `store.preview.fullResPath` is set (`store.openFullRes(path)` / `closeFullRes()`). The image comes from `GET /api/image?path=…&size=0` (`fullResUrl` in `frontend/src/api/client.ts`).
- **Trigger:** Double-click on the preview pane's image (`preview-single-image`), on an image tile in the group grid, or on a file row in the result tree. Double-clicking a video in the preview pane or a video grid tile does nothing; double-clicking a video file ROW opens the overlay with a video player.
- **Behaviour:**
  - The viewer is a modal overlay that fills the viewport by default and can be moved and resized ([Web — overlay window geometry (movable / resizable / persisted)](web-ui.md#web--overlay-window-geometry-movable--resizable--persisted)).
  - A spinner shows until the image loads. The title bar shows the file name and, once loaded, the served image's pixel size (`W × H`).
  - **Zoom:** Ctrl + mouse wheel, ±10 % per wheel event, clamped to 5 %–800 % ([#743](https://github.com/jackal998/photo-manager/issues/743)). **Pan:** drag with the left button. **Close:** Esc, the ✕ in the title bar, or a click on the empty area around the image. A footer hint reads "Ctrl+scroll to zoom · Drag to pan · Esc to close".
  - **Server side:** the file is decoded at its own size and returned as a JPEG. A DNG serves its embedded preview image (EXIF-rotated) whenever it has one, at whatever size it was stored. For iPhone ProRAW that is the full sensor, but a DNG with a small embedded preview shows that small image. Only a DNG without an embedded image goes through a full `rawpy` demosaic, at most two at a time (`_FULLRES_DECODE_SEM`).
  - The full-res JPEG is cached like any other request, in the preview tier of the byte-budget LRU and on disk ([Preview pane — byte-budget LRU cache](#preview-pane--byte-budget-lru-cache)), and is sent with `Cache-Control: public, max-age=3600`.
- **Conditions / variants:**
  - **One viewer at a time.** Opening another file replaces the one shown. The retired desktop client opened a separate, non-modal window per double-click.
  - **Size limit:** source files larger than **40 MiB** get HTTP 413 before any decode. The viewer cannot read the status code, so any image load failure shows "File too large for in-browser full-res preview." with an "Open in default app" button. Despite its label, that button reveals the file in Windows Explorer (`POST /api/reveal` → `explorer /select,`).
  - **Video rows:** the overlay shows a native `<video controls>` (no autoplay, no zoom/pan) with the same H.264 transcode fallback as the preview pane ([Web preview pane — video transcode fallback (V2 H.264)](web-ui.md#web-preview-pane--video-transcode-fallback-v2-h264)).
- **Related:** [#622](https://github.com/jackal998/photo-manager/issues/622) Phase 1 (PR #624); [#743](https://github.com/jackal998/photo-manager/issues/743) (zoom clamp); [#739](https://github.com/jackal998/photo-manager/issues/739) (movable / resizable); `frontend/src/components/FullResViewer.tsx`; `frontend/src/api/client.ts` (`fullResUrl`); `app/web/routes/image.py` (`size=0`, 413 guard); `infrastructure/image_service.py` (`_FULLRES_DECODE_SEM`); unit tests `tests/test_web_image_route.py` (full-res 200 + Cache-Control, 413 for a large source); QA scenarios [`qa/web/scenarios/s68_full_res_viewer_double_click.py`](../../qa/web/scenarios/s68_full_res_viewer_double_click.py) (double-click the preview image → viewer shows the basename and `W × H` → Esc closes it), [`qa/web/scenarios/s39_layout_persist.py`](../../qa/web/scenarios/s39_layout_persist.py) (viewer geometry).

### Preview pane — no-autoplay video default
- **Area:** Preview pane

- **Entry point:** [frontend/src/components/PreviewPane.tsx](../../frontend/src/components/PreviewPane.tsx) (single-file `<video>`), [frontend/src/components/FullResViewer.tsx](../../frontend/src/components/FullResViewer.tsx) (viewer `<video>`), [frontend/src/components/VideoTile.tsx](../../frontend/src/components/VideoTile.tsx) (grid tiles).
- **Trigger:** Selecting a video file row (single view), double-clicking a video file row (viewer), or selecting a group row that contains videos (grid view).
- **Behaviour:** Nothing plays on selection.
  - The single-view pane and the full-res viewer render a native `<video controls>` with no `autoplay`, so playback waits for the user's Play.
  - In the grid, each video tile is a static poster frame with a ▶ glyph and no `<video>` element until it is clicked. The click creates a `<video controls autoPlay>`, so that one tile starts playing at once.
  - The group controller bar ([Web preview pane — group sync controller (GroupMediaController)](web-ui.md#web-preview-pane--group-sync-controller-groupmediacontroller)) broadcasts only to tiles that have been clicked. Its one-shot `playAll()` fires only after every video tile in the group has been clicked.
- **Conditions / variants:** The native controls' Play starts playback as usual. When the browser cannot decode a source, all three surfaces use the same transcode fallback ([Web preview pane — video transcode fallback (V2 H.264)](web-ui.md#web-preview-pane--video-transcode-fallback-v2-h264)). Selecting another group unmounts the whole grid, so no tile keeps playing in the background.
- **Related:** [#622](https://github.com/jackal998/photo-manager/issues/622) Phase 1 (PR #624); `frontend/src/components/PreviewPane.tsx`; `frontend/src/components/FullResViewer.tsx`; `frontend/src/components/VideoTile.tsx`; component tests [`frontend/src/components/VideoTile.test.tsx`](../../frontend/src/components/VideoTile.test.tsx) (no `<video>` before the click; the click-mounted `<video>` carries `autoplay`); QA scenarios [`qa/web/scenarios/s69_video_playback.py`](../../qa/web/scenarios/s69_video_playback.py) (single-view `<video>` decodes and plays when told to), [`qa/web/scenarios/s71_grid_video_tiles.py`](../../qa/web/scenarios/s71_grid_video_tiles.py) (grid click-to-play, then group pause / play).
