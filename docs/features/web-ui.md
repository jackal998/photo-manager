### Web — preview panel resizable + persistence
- **Area:** Web UI

- **Entry point:** Drag handle (`data-testid="preview-resize-handle"`) between the result tree and the preview pane in [`frontend/src/App.tsx`](../../frontend/src/App.tsx), wired to `store.setPreviewWidth` in [`frontend/src/store/useAppStore.ts`](../../frontend/src/store/useAppStore.ts) and the persistence helpers in [`frontend/src/lib/panelWidths.ts`](../../frontend/src/lib/panelWidths.ts).
- **Trigger:** User drags the thin vertical grabber between the result tree and the preview pane. Restores the persisted width on every page load.
- **Behaviour:** Mirrors the [#685](https://github.com/jackal998/photo-manager/issues/685) column-resize recipe verbatim in structure: `mousedown` on the handle begins tracking `window` `mousemove` (so the drag keeps working once the cursor leaves the thin handle); each move updates the width in-memory only (`persist=false`) for live feedback, and the final width is written as `R-LAYOUT-2` states (`persist=true`). **End of drag ([#851](https://github.com/jackal998/photo-manager/issues/851)):** the drag ends (`R-LAYOUT-2`), window listeners removed — on `mouseup`, on window `blur`, on `pointercancel`, or on the first `mousemove` that arrives with no button held; unmounting mid-drag removes them too. The last three cover a button released where the page never hears the `mouseup` (over another application, or a system-cancelled pointer); before that the preview pane kept resizing on every later mouse move over the page, so the layout stuck to the cursor until the user clicked again and the persisted width ended up wherever the cursor happened to be. While dragging, the width is clamped to **[200px, 60% of the current viewport width]** — the 200px floor wins even on a viewport too narrow for the 60% cap — so a drag cannot squeeze either pane to invisibility. A stored width is not re-clamped when the page loads or the window is resized, so a width saved on a wide window can leave the tree very narrow, or hidden, on a smaller one. The default width is **320px** ([#878](https://github.com/jackal998/photo-manager/issues/878) layout slice PV — the pane now carries a title strip, a 4:3 frame, a five-row metadata table and a stacked decision block; 288 is where the zh-TW decision labels start wrapping). A persisted width that is exactly the OLD default (288) migrates to 320 — the drag handler writes the whole map on any resize, so an unresized pane still has a stored 288 that nobody chose; **any other stored width is the user's own and is kept**. The drag handle itself is 4px and transparent at rest, a hairline on hover and the accent while dragging.
- **Conditions / variants:** Persisted under localStorage key **`panelWidths`** — a small per-panel width map (`{"preview": <px>}`), kept as its OWN key separate from the [#685](https://github.com/jackal998/photo-manager/issues/685) column-widths key (`pm.result-tree.column-widths.v1`), since it is a distinct persisted concept. Per-browser, auto-isolated per Playwright context like the column-widths key — no server-side reset needed.
- **Full-res viewer note:** the viewer's own window chrome is no longer a divergence — it became a movable/resizable overlay in the same issue; see "Web — overlay window geometry" below. Its Ctrl+scroll zoom stays clamped **5%–800%** (#743; was 10%–1000%).
- **Related:** issue [#739](https://github.com/jackal998/photo-manager/issues/739), [#743](https://github.com/jackal998/photo-manager/issues/743) (zoom clamp); mirrors the #685 recipe ([`frontend/src/components/result/ColumnHeaderRow.tsx`](../../frontend/src/components/result/ColumnHeaderRow.tsx), [`frontend/src/lib/columnWidths.ts`](../../frontend/src/lib/columnWidths.ts)). QA scenario [`qa/web/scenarios/s39_layout_persist.py`](../../qa/web/scenarios/s39_layout_persist.py) (re-flip of `s39_window_geometry_persist` from SKIP, `qa/web/scenario_map.yml`); unit tests [`frontend/src/lib/panelWidths.test.ts`](../../frontend/src/lib/panelWidths.test.ts) (persistence) + [`frontend/src/App.previewResize.test.tsx`](../../frontend/src/App.previewResize.test.tsx) (drag + end-of-drag, #851). Same end-of-drag rule as the #796 column handle and the #739 overlay geometry — see "Web — result-tree column sort and resize persistence" and "Web — overlay window geometry" below.

### Web — overlay window geometry (movable / resizable / persisted)
- **Area:** Web UI

- **Entry point:** one shared mechanism — the drag/resize/clamp hook [`frontend/src/hooks/useOverlayGeometry.ts`](../../frontend/src/hooks/useOverlayGeometry.ts), the persistence helpers [`frontend/src/lib/overlayGeometry.ts`](../../frontend/src/lib/overlayGeometry.ts), and the corner grip [`frontend/src/components/ui/overlay-resize-handle.tsx`](../../frontend/src/components/ui/overlay-resize-handle.tsx). Applied to three surfaces: the full-resolution viewer ([`FullResViewer.tsx`](../../frontend/src/components/FullResViewer.tsx), ids `fullres-title-bar` / `fullres-resize-handle`), the Execute Action dialog ([`execute/ExecuteDialog.tsx`](../../frontend/src/components/execute/ExecuteDialog.tsx), `execute-title-bar` / `execute-resize-handle`; its title reads **"Execute Actions — Review"** since the 2026-09-14 copy audit (E6) — the dropped "— Review" half is what names the dialog as a gate before destruction) and the Set Action dialog ([`action/ActionDialog.tsx`](../../frontend/src/components/action/ActionDialog.tsx), `action-title-bar` / `action-resize-handle`).
- **Trigger:** User drags an overlay's title bar to move it, or its bottom-right corner grip to resize it. The geometry is restored every time that overlay is opened, including after a page reload.
- **Behaviour:** Mousedown on the title bar / grip begins tracking `window` `mousemove`/`mouseup`, so the gesture survives the cursor leaving the grab target; each move updates the geometry in memory only, and localStorage is written **once** per gesture — the same "live updates, one write per gesture" recipe as the #685 column resize and the preview splitter above. The gesture also ends on `blur`, `pointercancel`, or the first move that arrives with no button held, so releasing the button outside the browser window cannot leave an overlay stuck to the cursor (the #796 class). A mousedown that lands on a control inside the title bar (the viewer's ✕ button) clicks that control instead of starting a drag.
  - **Move and resize persist different things.** A **move** stores position only; the dialog keeps its automatic height and goes on growing and shrinking with its content exactly as it does un-moved. Only a **resize** pins a width/height. (Pinning height on a move meant a dragged Set Action dialog could not grow when its Preview block appeared, and the Cancel/Apply row was pushed clean out of the box — measured: dialog bottom 606, Apply bottom 716.) The one exception is the full-res viewer: dragging it while it fills the whole viewport **un-maximizes** it to 80% of the viewport, centered, and then follows the cursor — the OS window-manager convention, and what makes the viewer draggable at all given its fill-the-viewport default. That is safe because the viewer is a flex column whose image area already scrolls.
  - **Scrolling and the size floor.** Both dialogs put everything between the header and the footer in a scrollable body (`execute-body` / `action-body`, `flex: 1 1 auto`, `min-height: 0`). Because the body's flex basis is `auto`, an unpinned dialog is sized by its content exactly as before; once a height *is* pinned, the body shrinks and scrolls while the header and footer stay put, so the primary buttons are always inside the box. The minimum overlay size is **320×280 px**, set from a live measurement: with the Execute dialog's fixed chrome (header + toolbar + all-delete banner + footer ≈ 200 px) a 260 px box left the file tree exactly one row, so the floor sits above that.
  - Escape, the focus trap and each dialog's existing outside-interaction policy are untouched; so are the viewer's Ctrl+scroll zoom clamp (5%–800%, #743) and its drag-to-pan.
  - **Dialogs animate open and closed ([#852](https://github.com/jackal998/photo-manager/issues/852)).** Every Radix dialog (the shared wrapper [`frontend/src/components/ui/dialog.tsx`](../../frontend/src/components/ui/dialog.tsx)) fades in and zooms from 95% on open and reverses on close; the full-res viewer's backdrop ([`FullResViewer.tsx`](../../frontend/src/components/FullResViewer.tsx)) fades the same way. The `animate-in` / `animate-out` / `fade-in-0` / `zoom-in-95` / `data-[state=closed]:…` classes those surfaces already carried emit real CSS only because **`tw-animate-css`** (MIT, exact-pinned 1.4.0 — the Tailwind v4 successor of the `tailwindcss-animate` plugin) is imported in [`frontend/src/index.css`](../../frontend/src/index.css). Dialog content runs **200 ms** (its own `duration-200`), backdrops the package default 150 ms. Before #852 no animate plugin was installed, so those class names compiled to nothing and every dialog appeared and vanished instantly. Two consequences worth knowing: a closing dialog stays **mounted until its exit animation ends** (Radix) and its backdrop still swallows pointer events while it fades, so a driver must wait for it to detach rather than assume the DOM is clear on the next tick — `wait_manifest_loaded()` settles on that via `wait_no_modal_overlay()` ([`qa/web/_invariants.py`](../../qa/web/_invariants.py)), which is what keeps the raw-mouse drags in s39 / s47 landing on the page instead of on the fading scan-dialog backdrop; and the clamp below now measures the **layout** box (`offsetWidth`/`offsetHeight`) instead of `getBoundingClientRect`, which the entry zoom scales for those 200 ms — measured against the scaled box, a restored dialog near the bottom edge opened 22 px low with its footer off-screen (stored y=690 in a 720 px viewport settled at 310, bottom 742).
- **Conditions / variants:** Each surface has its **own** localStorage key — `pm.overlay-geometry.fullres.v1`, `pm.overlay-geometry.execute.v1`, `pm.overlay-geometry.action.v1` — separate from `panelWidths` (preview splitter) and `pm.result-tree.column-widths.v1` (#685), so one corrupt or stale blob cannot disturb the other surfaces. Stored value is `{x, y, w, h}` in CSS pixels, where **`w`/`h` are `null` until the overlay is actually resized**. **Clamp rule:** the saved position is clamped against the element's *rendered* box — on open, on every browser-window resize, and whenever the overlay's own content changes size (a `ResizeObserver`, so a dialog that grows near the bottom of the screen slides back up instead of pushing its footer off-screen). A pinned size is clamped to `[320×280, viewport]` first, then the origin, so the window always sits fully inside the viewport and a geometry saved on a larger monitor can never open with its title bar (the only drag affordance) or its footer buttons out of reach. A blob with an unusable **position** is discarded whole; an unusable **size** degrades to auto, keeping the position the user did choose. Every storage error is swallowed: the surface then renders at its **default** layout — the viewer fills the viewport, the two dialogs stay centered at their existing `max-w-4xl` / `max-w-2xl` size, so a first open is unchanged from before this feature.
- **Related:** issue [#739](https://github.com/jackal998/photo-manager/issues/739) (owner sign-off 2026-07-17: "implement it once, apply to all three surfaces"); closes divergence rows **D6**, **D7** and **D12** in [`docs/audits/web-divergence-list-2026-07.md`](../audits/web-divergence-list-2026-07.md). QA scenarios [`qa/web/scenarios/s39_layout_persist.py`](../../qa/web/scenarios/s39_layout_persist.py) (viewer) and [`qa/web/scenarios/s48_dialog_geometry_persist.py`](../../qa/web/scenarios/s48_dialog_geometry_persist.py) (both dialogs, re-flipped from SKIP); unit tests [`frontend/src/lib/overlayGeometry.test.ts`](../../frontend/src/lib/overlayGeometry.test.ts) and [`frontend/src/hooks/useOverlayGeometry.test.tsx`](../../frontend/src/hooks/useOverlayGeometry.test.tsx).

### Web — Action dialog (Set Action by Field)
- **Area:** Web UI

- **Entry point:** Toolbar `main-action-button` ("Set Action…", key `web.toolbar.set_action` — it used to borrow the dialog's own title key, whose value is the longer "Set Action by Field"; copy audit T1) — disabled when `manifest.path === null`; enabled once a scan result is loaded. `onClick` dispatches `store.openActionDialog()`. **Also reachable from the row right-click (#735):** the result-tree file-row context menu's `ctx-set-action-by-field` item (and the group-row reduced menu's item of the same testid) call `store.openActionDialog(initialField?)` — see [Web — main result tree multi-selection](#web--main-result-tree-multi-selection) for the menu itself.
- **Trigger:** User clicks the toolbar "Set Action…" button, picks menu bar **Action → "Set Action by Field…"** (the menu entry used to read "Set Action by Regex", disagreeing with this dialog's own title and with the right-click entry — regex is one of its three modes; copy audit M1), or right-clicks a file/group row and picks "Set Action by Field…". The `action-dialog` (`<dialog>` / Radix `DialogContent`) mounts when `store.action.actionDialogOpen === true`.
- **Behaviour:**
  - **Field selection** (`action-field-combo`) — `<select>` with 11 canonical English options (File Name, Score, Size (Bytes), Group Count, Similarity, Creation Date, Shot Date, …). Default value is "File Name".
  - **String-field mode** (field NOT in `NUMERIC_FIELDS`): shows `action-simple-row` (op combo + text input) and `action-regex-row` (direct regex). Simple-mode inputs write through to `action-regex-input` (the single source of truth): op "contains" + text "q9" produces the synthesised pattern `q9`; op "starts\_with" produces `^q9`; etc. The validation icon (`action-validation-icon`, span) shows ○ / ✓ / ✗ depending on whether the current pattern is empty / valid / invalid.
  - **Numeric-field mode** (field in `NUMERIC_FIELDS`: Size (Bytes), Group Count, Similarity, Score, Creation Date, Shot Date): `action-numeric-row` replaces the string rows. Two sub-modes — **Threshold** (`action-numeric-mode-threshold` radio, default): comparison operator (`action-numeric-cmp`) + value (`action-numeric-value`); **Top-N** (`action-numeric-mode-topn` radio): order (`action-numeric-order`: top / bottom) + count (`action-numeric-n`). Threshold / Top-N sub-modes encode to `__cmp__:OP:VALUE` / `__top_n__:N:asc|desc` pseudo-patterns for `POST /api/action/bulk-decide`.
  - **Action combo** (`action-action-combo`) — `<select>` with 5 options; wire values: `__keep__` (maps to empty string `""`), `delete`, `__ignore__`, `__lock__`, `__unlock__`.
  - **Live preview** — after any input change, the store calls `previewBulkDecide()` which hits `POST /api/action/bulk-decide` with `preview=true`. The match counter (`action-match-counter`) shows "N of M matched". `action-preview-list` (`<ul>`, a scrolling box) lists every matched path — a preview returns the whole resolved set — so the `action-preview-truncated` "…and N more" line appears only if a response ever carries fewer paths than it matched.
  - **Apply** (`action-btn-apply`) — disabled when `manifest.path === null || actionRunning`. An empty pattern no longer disables Apply (#741, fixing the #397 friction regression): the backend already no-ops on an empty pattern (`core/app_service/action_resolve.py:341` `if not pattern: return []`, pinned by `tests/test_action_resolve.py`), so gating the button on it added friction with no safety value. On click calls `store.applyBulkDecide()`. When `action === "delete"`, the delete-confirm gate (`execute-all-delete-confirm` / `-yes` / `-no` testids) must be accepted before the API call fires. When the server refuses under `R-LOCK-1`, the inline lock-confirm dialog (`action-lock-confirm-dialog`) appears with three verdicts — see Conditions below (#674).
  - **Recent patterns (#741)** — a "Recent:" jump-menu `<select>` (`action-recent-select`) sits above the Field combo, listing patterns previously Applied for the current field (plus legacy null-field entries, which apply to any field); picking an entry fills the pattern input and the select resets to its placeholder. `action-recent-clear` (shown only when at least one entry is visible for the current field) wipes the whole list across all fields. Entries are recorded after a (non-preview) Apply returns without a 409 lock prompt. Only the 409 stops the recording: any other failed Apply still records the pattern and closes the dialog, so a pattern that never applied can enter Recent. They are persisted under the settings key `ui.action_dialog.recent_patterns` as `[field-or-null, pattern]` tuples, deduped by exact (field, pattern) and capped at 10 entries (enforced on both write and read, so a hand-edited or cross-version settings.json can't render an unbounded list). Numeric fields (`NUMERIC_FIELDS`) are excluded — their `__cmp__:`/`__top_n__:` pseudo-patterns would be meaningless in a re-pickable Recent list.
  - **Pattern-aware delete-confirm (#741)** — when Apply is clicked with `action === "delete"`, the confirm dialog shown is no longer generic "N files will be deleted" copy: it renders a human-readable pattern summary (`action-delete-confirm-summary`, e.g. "File Name contains 'IMG'", or "{field} regex '{pattern}'" for non-Simple-representable patterns) and its confirm button reads "Mark N files for deletion" — deferred-decision wording, since Apply only queues the decision and nothing is deleted until Execute Action runs.
- **Conditions / variants:**
  - `main-action-button` is disabled when no manifest is loaded (`manifest.path === null`).
  - String mode shows both `action-simple-row` and `action-regex-row` side-by-side (no mode toggle).
  - Cheatsheet chips (`action-cheatsheet-{token}`) for `.*`, `\d`, `\w`, `^`, `$`, `\.`, `[abc]` insert tokens into the regex input.
  - The delete-confirm dialog reuses `execute-all-delete-confirm` (same testid set as the execute-dialog all-delete gate) so the flow is consistent across action entry points.
  - **Locked-rows refusal (`R-LOCK-1`, #674):** the inline `action-lock-confirm-dialog` mounts with **three verdicts** — **Cancel** (`action-lock-confirm-btn-cancel`), **Apply to Unlocked Only** (`action-lock-confirm-btn-unlocked-only`), and **Unlock & Apply** (`action-lock-confirm-btn-unlock-apply`). "Unlock & Apply" re-POSTs with `force_locked=true`; "Apply to Unlocked Only" re-POSTs with `skip_locked=true` (the backend applies the decision to the matched-minus-locked subset, computed server-side from the authoritative `is_locked` column, leaving locked rows' `is_locked` + `user_decision` untouched). The 409 body carries `matched_total` so the dialog disables "Apply to Unlocked Only" when every matched row is locked (no unlocked subset) without depending on a stale preview; `force_locked` + `skip_locked` are mutually exclusive (the backend rejects both with 422). This inline dialog is **distinct** from the execute-flow `lock-confirm-dialog` (`LockConfirmDialog`) which is path-scoped — see [Execute Action — lock-confirm dialog](execute-action.md#execute-action--lock-confirm-dialog).
  - **Column pre-fill from the context menu (#735):** `store.openActionDialog(initialField?)` accepts an optional field-option value; when the row right-click resolves a clicked column (`frontend/src/lib/actionDialogFields.ts`'s `WEB_COL_TO_FIELD`), the dialog opens with that field pre-selected instead of the default "File Name". Mapped columns: name → File Name, similarity → Similarity, action → Action, size → Size (Bytes), shot date → Shot Date; Score and Resolution are intentionally unmapped (open with no pre-fill). An omitted or unrecognised value falls back to the default field, so every pre-#735 argless callsite (toolbar button, menu bar, `ExecuteContextMenu`) is unaffected.
  - **Row-value seed (#893)** — the value half of the same behaviour. Opening the dialog from a highlighted row seeds the matcher with **that row's value for the selected field**, escaped, so the Simple inputs read `("contains", value)` and the pattern matches the row it came from (before #893 every pattern started from an empty box). Seedable fields are **File Name / Folder / Action**. The two other regex fields, Resolution and Lock, are not seeded and open with an empty pattern. The six numeric fields (Size (Bytes), Group Count, Similarity, Score, Creation Date, Shot Date) render the numeric panel, whose `__cmp__:` / `__top_n__:` pseudo-pattern a regex seed cannot express. **Changing the field re-seeds the matcher only while it still holds the previous field's seed (or is empty)** — a pattern the user typed or edited survives a field change (#347). Which row seeds it: the **right-clicked row** from the file-row context menu; **none** from the group-row menu and from the Execute dialog's Select-by entry point; the **highlighted row** for the toolbar button and menu-bar item.
  - **The Simple row follows the regex (#899).** Whenever the pattern changes under it — a hand-edited regex, a cheatsheet chip, a Recent pick — and the new pattern is Simple-representable, the Simple inputs are re-derived from it: hand-typing `^neardup_0` reads back as ("starts with", `neardup_0`), so a following op flip builds on the edit instead of silently replacing it with the stale seed. A pattern Simple cannot represent (a real regex) leaves the Simple inputs as they were, as Qt's `_reverse_parse_to_simple` did. The Simple row's own write-through never re-derives it, so clearing its text keeps the chosen op.
- **Related:** `app/web/routes/action.py` (`POST /api/action/bulk-decide`, now with `skip_locked` + the `matched_total` 409 field); `core/app_service/action_service.py` (`bulk_decide`); `core/app_service/action_resolve.py` (`resolve_matched_paths`); `frontend/src/lib/recentPatterns.ts` (Recent parse/record/visible helpers, #741 sub-item B); `frontend/src/lib/patternSummary.ts` (`buildPatternSummary`, #741 sub-item C); see also [`Set Action dialog — dual-section Simple + Regex view`](set-action-dialog.md#set-action-dialog--dual-section-simple--regex-view) and [`Execute Action — lock-confirm dialog`](execute-action.md#execute-action--lock-confirm-dialog) (#674 added the Apply-to-Unlocked-Only verdict); QA scenarios [`qa/web/scenarios/s31_simple_mode_regex.py`](../../qa/web/scenarios/s31_simple_mode_regex.py) (extended for #741 — empty-pattern Apply-enabled + pattern-summary delete-confirm), [`qa/web/scenarios/s32_lock_confirm_bulk_regex.py`](../../qa/web/scenarios/s32_lock_confirm_bulk_regex.py) (#674 lock-confirm verdict, asserted via sqlite + GET /api/manifest).

### Web — main result tree multi-selection
- **Area:** Web UI

- **Entry point:** File rows in the main result tree (`main-result-tree` → `FileRow`, [frontend/src/components/result/FileRow.tsx](../../frontend/src/components/result/FileRow.tsx)) and the row right-click context menu (`context-menu` → [frontend/src/components/ContextMenu.tsx](../../frontend/src/components/ContextMenu.tsx)). Selection state lives in the store's `selection` slice ([frontend/src/store/useAppStore.ts](../../frontend/src/store/useAppStore.ts)).
- **Trigger:** The user left-clicks rows (plain / Ctrl·Cmd / Shift) to build a selection, then right-clicks one to act on it.
- **Behaviour:**
  - **Selection model.** A plain click selects exactly one row (and points the preview pane at it). **Ctrl/Cmd+click** toggles a row in or out of an ordered multi-selection. **Shift+click** extends an inclusive range from the anchor (the last plain click) over the currently-*visible* rows — collapsed groups' rows are excluded from the range. Selected rows get a sky highlight + `aria-selected`; the highlight wins over the Ref-winner tint.
  - **Selection-aware context menu.** The Delete / Keep / Remove-from-list / Lock / Unlock verbs act on the **whole selection** when the right-clicked row is part of it, and on **just that row** otherwise (the file-manager target-resolution rule — a right-click outside the selection also resets the selection to that one row). **Open folder** always targets only the right-clicked row. Batch Delete/Keep decisions and Lock/Unlock issue a single `PATCH /api/decision` / `PATCH /api/lock` for the whole set (optimistic, all-or-nothing revert on failure); Remove-from-list instead finalizes the whole selection via `POST /api/remove` (#694, see below).
  - **Skip finalizes (#694).** The result-tree **Skip** item (labelled "Remove from list" until the 2026-09-18 vocabulary decision; the wire value `ignore` is unchanged) FINALIZES under `R-SKIP-1` (no Execute step). A refusal under `R-LOCK-1` routes through the `LockConfirmDialog` and a resulting singleton triggers the prune offer (`maybeOfferPrune`). Staging a reversible `user_decision='ignore'` instead lives on the per-row decision buttons (`DecisionControl`); the Execute-dialog "Remove from list" remains a single-row finalize behind its own confirm sheet. (Previously this menu only STAGED `ignore` — the [#694](https://github.com/jackal998/photo-manager/issues/694) parity gap, now closed.)
  - **Set Action by Field… + Execute (only selected) on the file-row menu (#735).** A post-Open-Folder group (`ctx-set-action-by-field` / `ctx-execute-selected`); the whole file-row menu reads Keep · Delete · Skip now │ Lock *or* Unlock (whichever the right-clicked row's lock state allows) · Open folder │ Set Action by Field… · Execute Action (only selected)… │ Apply best-copy decisions to this group. "Set Action by Field…" opens the ActionDialog, pre-filled from the clicked column when mapped (see [Web — Action dialog](#web--action-dialog-set-action-by-field)). "Execute Action (only selected)…" invokes the same handler as the menu-bar entry (re-reads the live selection) — see [Web — Execute (only selected)](#web--execute-only-selected).
  - **Selection clears on any manifest mutation.** Loading a manifest, executing, removing, pruning, or a bulk-decide all replace `manifest.groups` and reset the selection so it can never reference vanished rows.
- **Conditions / variants:** There is no group-header *selection* (`GroupRow` stays collapse-only for the multi-select model above — clicking a group header never adds it to `selection.selectedPaths`; since [#709](https://github.com/jackal998/photo-manager/issues/709) it **clears** them, so the highlight always matches what `d`/`k` and the context menu would act on), so a group cannot be selected as one item. However, the group header now has its own **reduced right-click menu** (#735, `GroupRow.tsx` `onContextMenu`) — `ctx-set-action-by-field` (argless, no column context) + `ctx-set-action-remove` (finalizes `outcome='ignored'` for the group's own member paths, same `removeFromList` call as the file-row entry) + `ctx-apply-best-copy` (#744, see [Web — Context menu: Apply best-copy decisions to this group](#web--context-menu-apply-best-copy-decisions-to-this-group)) ONLY. No Keep/Delete, no Lock/Unlock, no Open folder, no Execute-selected — a distinct, narrower affordance from the file-row multi-selection menu above. The single-row scenarios ([s15](../../qa/web/scenarios/s15_context_menu.py) / [s25](../../qa/web/scenarios/s25_empty_area_context_menu.py) / [s35](../../qa/web/scenarios/s35_lock_via_context_menu.py)) stay single-target because they right-click a row that was never multi-selected.
- **Related:** See also [Context menu — Set Action (per-file)](context-menu.md#context-menu--set-action-per-file) and [List menu — Remove from List](menus.md#list-menu--remove-from-list); [#694](https://github.com/jackal998/photo-manager/issues/694) (result-tree remove now finalizes — resolved); [#735](https://github.com/jackal998/photo-manager/issues/735) (By-Field + Execute-selected file-row entries, group-row reduced menu); [frontend/src/components/ResultTree.tsx](../../frontend/src/components/ResultTree.tsx); QA scenario [`qa/web/scenarios/s20_multi_remove_from_list.py`](../../qa/web/scenarios/s20_multi_remove_from_list.py) (context-menu multi-selection Skip; the menu-bar **List → Skip Selected now** surface has its own driver, [`qa/web/scenarios/s21_list_menu_remove.py`](../../qa/web/scenarios/s21_list_menu_remove.py)); [`qa/web/scenarios/s15_context_menu.py`](../../qa/web/scenarios/s15_context_menu.py) (#735 file-row + group-row phases).

### Web — Context menu: Apply best-copy decisions to this group
- **Area:** Web UI

- **Entry point:** TWO surfaces over one store action (`useAppStore.applyBestCopy`) — (1) the `ctx-apply-best-copy` menu item in BOTH the file-row and group-row context menus ([frontend/src/components/ContextMenu.tsx](../../frontend/src/components/ContextMenu.tsx)), and (2) since layout slice G, a visible **"Keep best · delete rest"** button at the right end of every group header (`group-keep-best-{group}` — deliberately NOT prefixed `row-group-`, which the qa helpers count and traverse the tree by, [frontend/src/components/result/GroupRow.tsx](../../frontend/src/components/result/GroupRow.tsx)). Both reach `POST /api/action/apply-best-copy` ([app/web/routes/action.py](../../app/web/routes/action.py)) → `core.app_service.action_service.apply_best_copy` ([core/app_service/action_service.py](../../core/app_service/action_service.py)).
- **Trigger:** User right-clicks a file row OR a group-header row and picks "Apply best-copy decisions to this group", or clicks the group header's **Keep best · delete rest** button. Acts on the right-clicked row/group's OWN `group_number`, independent of the current multi-selection (`targetPaths`) and independent of file-vs-group variant. **Both surfaces are disabled while the toolbar filter is active** (layout slice TB), with the tooltip "Clear the filter to use Keep best" / 「清除篩選後才能使用保留最佳」 (`web.tree.keep_best_filtered`): the write is server-side and scoped by `group_number`, so under a filter it would mark rows the user cannot see while the group header shows the FILTERED count right beside the button. Disabled rather than re-scoped to the visible rows — picking a "best" copy from a subset is a different decision, and a silently wrong one. Open questions Q5 promoted the action onto the header because it is the fast path through the entire screen and «a right-click action is invisible to the users who most need it».
- **Behaviour:** Within the target group, the highest-scoring row becomes the keeper (`user_decision=""` + `is_locked=true`); every OTHER row the classifier positively identified as a duplicate (`action` in `EXACT` / `REVIEW_DUPLICATE`) gets `user_decision="delete"`. A Ref-tier row pulled into the group by the ungated filename pair edge (RAW+JPG same-stem, Live-Photo MOV passenger) is left untouched — same allowlist `core.services.auto_select.non_keepers_for_aggressive_delete` uses for the scan-time aggressive auto-select path (see [Scan dialog — auto-select aggressive](scan.md#scan-dialog--auto-select-aggressive-delete-all-others)). No optimistic client-side update — the store swaps in the authoritative `groups` array from the response. A locked row in the write-set (keeper or delete-target) behaves differently per entry point, deliberately. From the **context menu** it triggers the SAME `LockConfirmDialog` used by decision/execute/remove (refused under `R-LOCK-1`, non-destructive "decision-only" copy variant) — "Unlock & Apply" force-unlocks previously-locked delete-targets in the same write (the keeper's own lock write is unaffected); "Unlocked Only" narrows the write to the unlocked subset. From the **header button** the `R-LOCK-7` exception applies: there is no dialog, a locked row keeps BOTH its decision and its lock, and the write silently narrows to the unlocked subset — Q5: «it must never override a lock, and it must say so when it skips one».
- **Behaviour — the undo toast (layout slice G, Q5):** the header button has **no confirm step**, because «the button does not delete anything … a confirm dialog in front of a reversible, non-destructive action is the classic way to teach people to dismiss dialogs without reading, which then costs you at Execute, where the dialog matters». Instead, a successful apply-best-copy from **either** entry point raises a **single-slot toast** above the status bar ([frontend/src/components/Toast.tsx](../../frontend/src/components/Toast.tsx), `main-toast`, `role="status"`): *"Group 12 · 4 files marked for deletion · Undo"* / 「群組 12 · 已標記 4 個檔案待刪除 · 復原」, plus *"1 locked file unchanged"* / 「1 個鎖定的檔案未變更」 when it skipped one. Both counts are derived client-side — the response carries only `matched` (keeper + deletes as one number) and no locked count. The locked count reports only rows the write could actually have targeted (classification `EXACT` / `REVIEW_DUPLICATE`), so a lock on the keeper or on a Ref-tier passenger — neither of which was ever a delete-target — is not reported as "skipped". It dismisses after **~6 s**, with the timer **paused while hovered or focused** and resumed with the REMAINDER, because six seconds is enough to read a sentence but not to read it, decide and aim. **Single slot:** a keep-best on a second group REPLACES the toast and restarts the clock, so Undo always reverses exactly the latest action and never a half-remembered stack. **A repeat on the SAME group is handled apart from that**, because it is the one case where replacing the snapshot destroys the undo: a second apply reads an ALREADY-APPLIED group as its "before", so snapshotting that would make Undo restore the damage. Both entry points therefore disable themselves while that group's write is in flight (`keepBestPending`), and when a later toast does land on the group the standing toast already describes, the EARLIER recording of each path wins. **Undo** restores each touched row's prior `user_decision` **and** its prior lock, from a snapshot taken before the write — the decision PATCH goes out with `force_locked` because apply-best-copy locks the keeper it chooses, so a decision-only undo would be refused by the very lock the action had just created. A failed undo leaves the toast up rather than stranding the user with an unreversible write.
- **Conditions / variants:** Deliberately NO `match_confidence` filtering — that field lives only on the scanner's transient `ManifestRow` shape and is never persisted to the manifest DB, so `core.models.PhotoRecord` (what the endpoint reads) has no such attribute; the shared helper's confidence check is naturally always-true here (owner-accepted #744 scope decision, not a gap). A group with no scored rows (e.g. every member is a passenger) is a benign no-op. **History:** an earlier version of this right-click action was removed in [PR #224](https://github.com/jackal998/photo-manager/pull/224) (closes [#210](https://github.com/jackal998/photo-manager/issues/210)) in favour of the Set Action dialog's Top-N-by-Score numeric condition, which the web dialog still offers (see [Set Action dialog — numeric comparison panel](set-action-dialog.md#set-action-dialog--numeric-comparison-panel)); #744 brought the one-click action back.
- **Related:** [#744](https://github.com/jackal998/photo-manager/issues/744); design contract `docs/design/web-port-tech-design.md:2265`; `core/services/auto_select.py` (`top_score_path_per_group`, `build_auto_select_writes`, `non_keepers_for_aggressive_delete` — reused, not reimplemented); `frontend/src/store/useAppStore.ts` (`applyBestCopy`); `frontend/src/components/dialogs/LockConfirmDialog.tsx` (`op="apply-best-copy"`); backend tests [`tests/test_web_action_routes.py::TestApplyBestCopy`](../../tests/test_web_action_routes.py); QA scenarios [`qa/web/scenarios/s72_apply_best_copy.py`](../../qa/web/scenarios/s72_apply_best_copy.py) (plain scan → group-row right-click → assert keeper/delete split via GET /api/manifest → reload + reopen via picker → assert durability) and [`qa/web/scenarios/s75_keep_best_button.py`](../../qa/web/scenarios/s75_keep_best_button.py) (the header button: lock one duplicate → click → assert the locked row keeps its decision AND its lock while the others are marked → read the toast in both locales → Undo → assert the group is byte-identical to its pre-button state, keeper's lock included). Layout slice G: `frontend/src/components/Toast.tsx`, `frontend/src/lib/groupSummary.ts`, open questions Q4/Q5.

### Web — Context menu: stays inside the window (#897)
- **Area:** Web UI

- **Entry point:** The result-tree row context menu, both variants — [frontend/src/components/ContextMenu.tsx](../../frontend/src/components/ContextMenu.tsx) (`context-menu`) — and the Execute dialog's row menu ([frontend/src/components/execute/ExecuteContextMenu.tsx](../../frontend/src/components/execute/ExecuteContextMenu.tsx)). Both measure through [frontend/src/hooks/useMenuPlacement.ts](../../frontend/src/hooks/useMenuPlacement.ts) and are placed by the pure [frontend/src/lib/menuPlacement.ts](../../frontend/src/lib/menuPlacement.ts) `placeMenu`.
- **Trigger:** Right-clicking a file row or group header anywhere in the window, including near its bottom or right edge, or in a short window.
- **Behaviour:** The menu opens below-right of the cursor when it fits, as before. When it would overflow the bottom it **flips above** the cursor (its bottom edge at the cursor, as Qt's `QMenu` did); when it would overflow the right it flips left. When neither side of the cursor has room it **slides** in until its far edge is 4px inside the window. When it is **taller than the window** it is pinned 4px from the top with `max-height: 100vh − 8px` and **scrolls internally**, so every item — the last one included — can still be reached. The menu is measured in a layout effect and re-placed before the browser paints, so it is never drawn off-screen first.
- **Conditions / variants:** Previously the menu was drawn at the cursor unconditionally (`style={{ left: x, top: y }}`): in a 400px-tall window its lower items sat past the viewport edge and could not be clicked, and s73 had to widen its window to work around it. The box carries `w-max` so a menu opened near the right edge measures at its real width instead of shrink-wrapping (and so wrapping its labels) before it is moved. The Execute dialog's row menu is `absolute` inside a layer over the dialog (to stay clickable inside the Radix modal), so its coordinates are layer-relative: it is clamped to the **window**, not the dialog — the dialog deliberately does not clip it (s30) — by converting through the layer's on-screen origin and back.
- **Related:** issue [#897](https://github.com/jackal998/photo-manager/issues/897); unit tests `frontend/src/lib/menuPlacement.test.ts` (flip / slide / scroll math), `frontend/src/components/ContextMenu.test.tsx` and `frontend/src/components/execute/ExecuteContextMenu.test.tsx` (each component applies it; the latter through a dialog-offset layer); QA scenario [`qa/web/scenarios/s15_context_menu.py`](../../qa/web/scenarios/s15_context_menu.py) step (g) — at 1280×400, right-click the last row and hit-test the menu's last item.

### Web — ScanDialog source/output persistence
- **Area:** Web UI

- **Entry point:** The Scan dialog ([frontend/src/components/ScanDialog.tsx](../../frontend/src/components/ScanDialog.tsx)) reads/writes the allowlisted `sources.list` / `sources.output` keys via `GET` / `PATCH /api/settings` ([app/web/routes/settings.py](../../app/web/routes/settings.py)).
- **Trigger:** Automatic — the source list + output path are loaded when the dialog opens and saved when the user clicks **Start Scan**.
- **Behaviour:**
  - **Load on open.** Opening the dialog fetches `GET /api/settings` and rebuilds the source rows from the persisted `sources.list` (`[{path, recursive}, …]`, label derived from each path's basename) and the output field from `sources.output`. A blank row + empty output show synchronously first; persisted values override only when present, so a freshly-typed row is never clobbered by an empty response. Malformed persisted entries (non-dict, missing `path`) are skipped.
  - **Save on Start Scan.** Clicking **Start Scan** fires `PATCH /api/settings` with the current `sources.list` (path + per-row recursive flag) and `sources.output` **before** the scan starts. The save is fire-and-forget and non-fatal: a settings-save failure never blocks the scan.
- **Near-duplicate threshold floor ([#823](https://github.com/jackal998/photo-manager/issues/823)):** the pHash and dHash number inputs render `min="2"` and their labels read **range: 2–20** — see also [Scan dialog — collapse Advanced Settings](scan.md#scan-dialog--collapse-advanced-settings). `min` is only a browser hint, so the client-side guard is `clampThresholdInput` at request-build time: a typed `1` still leaves as `threshold: 2` on `POST /api/scan`. Since [#876](https://github.com/jackal998/photo-manager/issues/876) the **authoritative** guard is the server — `WebScanRequest` bounds both hash thresholds to 2–20 and answers 422 below that — so the clamp is what keeps this dialog honest, not what keeps a bad value out of `classify`. **The field also snaps to the clamped value** — on blur and again when **Start Scan** is clicked — so what the user sees is what actually runs. Without that, `min` merely set `rangeUnderflow` and left `1` on screen while the scan ran at 2, which is the same dishonesty this ticket exists to remove. The snap deliberately does **not** fire per keystroke: clamping mid-type corrupts a clear-and-retype. Mean-colour keeps its existing behaviour (its floor is 0, so only a typed negative underflows) — a known asymmetry, not an oversight. A localized helper line under each input (`web.scan.threshold_parity_note`, `data-testid` `scan-phash-parity-note` / `scan-dhash-parity-note`) explains that photographic pHash distances are always even, so an odd value usually matches the same files as the even value below it, and that 2 is the strictest useful setting. The mean-colour input keeps `min="0"`. **Dialog height:** adding those two helper lines pushed **Start Scan** off the bottom of a 1280×800 viewport (the expanded dialog was already 807px tall in an 800px window, and the shared `DialogContent` is a centred box with no height cap), so this dialog is now capped at `max-h-[90vh]` with `overflow-y-auto`: with Advanced expanded the panel scrolls internally instead of growing past the window edge, and every control including **Start Scan** stays reachable. The shared `DialogContent` itself stays uncapped; the Execute dialog (`max-h-[90vh]`) and the delete confirm with its row list (`max-h-[85vh]`) carry caps of their own.
- **Dialog copy is catalog-driven (copy audit SC1/SC3/SC5, 2026-09-14):** this was the client's largest untranslated surface — the title, the "Sources" / "Output path" / "Advanced settings" / "Grouping sensitivity" labels, the three threshold labels + their short descriptions + their three long hover tooltips, every checkbox label, the whole source row (Label / Path placeholders, the Recursive label, and every `aria-label`), the error line and **Start Scan** were all hardcoded English, so a zh_TW user opened an entirely English dialog. Every one now resolves through `web.scan.*` in both catalogs. The English wording is unchanged (the defect was the missing `t()`, not the words); the `*_desc` lines deliberately omit a trailing "2 is the strictest useful setting" clause, because the `web.scan.threshold_parity_note` paragraph below each input already says it (copy audit SC2 — the redundancy, not a bug).
- **Conditions / variants:** The source list and the output path persist as `R-SCAN-3` states, and the **Auto-tune reader concurrency** checkbox persists — the checkbox as `ui.scan_dialog.autotune_read_knee`, read when the dialog opens and written on **Start Scan** (see [Scan dialog — read-knee autotune opt-out](scan.md#scan-dialog--read-knee-autotune-opt-out)). pHash/dHash/mean-color thresholds are **not** persisted (#736 — the Advanced settings' "Grouping sensitivity" number inputs are sent per-scan in the scan request only, never through `patchSettings`, and the `/api/settings` allowlist excludes the threshold keys) — pinned by s23b. The auto-select and aggressive checkboxes are likewise sent per-scan in the scan request and are not persisted. The source list itself renders case-insensitively **alphabetized by path** (display-only, #736; the rule dates from [#213](https://github.com/jackal998/photo-manager/issues/213)/[#223](https://github.com/jackal998/photo-manager/pull/223)) — while the underlying array stays insertion-ordered, so dedup's source-priority inference (top-of-scan = highest priority, `scanner/dedup.py`) and each row's testid `idx` are unaffected. Per-source **labels** are not durable — only `{path, recursive}` is stored, so a reopened dialog re-derives each row's label from the path basename. The async load fills only a still-pristine dialog, so reopening it while typing never clobbers in-progress edits.
- **Related:** See also [Scan dialog — multi-source scan](scan.md#scan-dialog--multi-source-scan) and [Scan dialog — folder list (no priority arrows)](scan.md#scan-dialog--folder-list-no-priority-arrows); part of the web-port FE-parity backlog [#678](https://github.com/jackal998/photo-manager/issues/678) (cluster E); [#736](https://github.com/jackal998/photo-manager/issues/736) (grouping-sensitivity thresholds + alphabetized source list); QA scenarios [`qa/web/scenarios/s23a_set_settings.py`](../../qa/web/scenarios/s23a_set_settings.py) (write side) + [`qa/web/scenarios/s23b_verify_settings.py`](../../qa/web/scenarios/s23b_verify_settings.py) (reload round-trip) + [`qa/web/scenarios/s17_scan_dialog_widgets.py`](../../qa/web/scenarios/s17_scan_dialog_widgets.py) (#736 threshold wiring + alphabetized-display proof; #823 near-duplicate floor + parity note).

### Web — result-tree column sort and resize persistence
- **Area:** Web UI

- **Entry point:** The main result tree ([frontend/src/components/ResultTree.tsx](../../frontend/src/components/ResultTree.tsx)) gained a sticky column-header row ([frontend/src/components/result/ColumnHeaderRow.tsx](../../frontend/src/components/result/ColumnHeaderRow.tsx)) with clickable **File Name** / **Size** sort cells and a right-edge resize handle on every metadata column. The column registry + sort comparators live in [frontend/src/lib/resultColumns.ts](../../frontend/src/lib/resultColumns.ts).
- **Trigger:** User clicks a sortable column header (sort) or drags a column's right-edge resize handle (width).
- **Behaviour:**
  - **Sort.** The default is server response order (no sort) — so every existing row-reading scenario is unaffected. Clicking **File Name** sorts each group's rows case-folded ascending; a repeat click toggles to descending; clicking **Size** sorts numerically on the raw byte count (not the human-readable label). Sorting follows `R-SORT-1`; **Action** (since [#923](https://github.com/jackal998/photo-manager/issues/923)) has its own cycle — see [Web — sort by decision](#web--sort-by-decision-action-header). Sort is applied **per group** (group order itself is unchanged). The chosen sort is held in the `resultView` store slice, so it survives an in-session manifest reopen (re-loading the same `.db` without a page reload).
  - **Resize + persist.** Dragging a column's right-edge handle resizes it (floor 40px); the new width is written to `localStorage` (`pm.result-tree.column-widths.v1`) and restored as `R-LAYOUT-1` states, and in a browser tab on the next launch. In the packaged app the widths are expected to reset on every relaunch, because its pywebview window runs in private mode (code-read, not live-verified; tracked as [#944](https://github.com/jackal998/photo-manager/issues/944)). localStorage is per browser; widths hydrate at store creation so a manifest load never resets them. **End of drag (#796):** the drag ends — one persisted write, window listeners removed — on `mouseup`, on window `blur`, on `pointercancel`, or on the first `mousemove` that arrives with no button held. The last three cover a button released where the page never hears the `mouseup` (over another application, or a system-cancelled pointer); before that the column kept resizing on every later mouse move over the page.
  - **Header height feeds the virtualizer (#699).** The header is a normal-flow sibling **above** the virtualizer's spacer inside the same scroll container, so the row list starts one header-height into the container's content. `ResultTree` measures the header's rendered height at runtime (a ref on `ColumnHeaderRow`'s root plus a layout effect and a `ResizeObserver`, so a late font load or a taller translated label re-measures) and passes it to `useVirtualizer` as `scrollMargin`; each row is then positioned at `start - scrollMargin` inside the spacer, so a row's on-screen position is unchanged while the virtualizer's coordinates finally equal the scroll container's own. Nothing about the rendered page changes — the value it fixes is the windowing math (which rows are mounted near a scroll boundary, and where `scrollToIndex` lands). The measured value is mirrored onto the tree root as `data-scroll-margin` so the coordinate contract is observable: `translateY + data-scroll-margin` must equal the row's offset from the container's content top.
- **Conditions / variants:** Sort persistence is **in-session only** (cross-launch sort is explicitly out of scope; s45 pins the in-session half); width persistence follows `R-LAYOUT-1`, and in a browser tab it also survives a relaunch — but in the packaged app, whose pywebview window runs in private mode, it is expected not to survive a relaunch (code-read, not live-verified; tracked as [#944](https://github.com/jackal998/photo-manager/issues/944)). No backend change — sort/resize is a pure client proxy-model concern; `GET /api/manifest` order stays the service-layer default. Header labels resolve from the `web.column.*` i18n catalog (so they translate in zh_TW); the Size header reads **"Size"** (human-readable), while the Set Action dialog's field of the same data is still named **"Size (Bytes)"**. The `scrollMargin` rule above is **measured, never a constant** — the header renders 28px since layout slice C (~25px before it), and a font/padding/i18n change moves it again, so a hardcoded number would silently reintroduce the offset. The same measurement also drives **column shedding** (slice C): the header's box width IS the table's available width, so one `ResizeObserver` feeds both the virtualizer's `scrollMargin` and the column budget — see [Web — Daylight theme and results-tree framing](#web--daylight-theme-and-results-tree-framing) § Columns.
- **Related:** See also [Main window — sort persistence within session](main-window.md#main-window--sort-persistence-within-session) and [Main window — column order/width persistence](main-window.md#main-window--column-orderwidth-persistence); part of the web-port FE-parity backlog [#678](https://github.com/jackal998/photo-manager/issues/678) ([#685](https://github.com/jackal998/photo-manager/issues/685)); sticky-header virtualizer offset + tall-manifest scroll coverage [#699](https://github.com/jackal998/photo-manager/issues/699); QA scenarios [`qa/web/scenarios/s45_sort_persistence.py`](../../qa/web/scenarios/s45_sort_persistence.py) (sort + in-session persistence) + [`qa/web/scenarios/s47_column_layout_persist.py`](../../qa/web/scenarios/s47_column_layout_persist.py) (width persist across reload — since layout slice C File Name is the FILL column, so the driver asserts the **stored** width, published as `data-col-basis`, moves by exactly the drag distance and survives the reload, plus the rendered box never falling below it; **#699 phase**: a synthetic 30-group / 60-row manifest, the only web fixture taller than the viewport — scrolls the tree and asserts the header stays pinned, the first row is not occluded, and every rendered row sits exactly where the virtualizer's coordinate says).

### Web — sort by decision (Action header)
- **Area:** Web UI

- **Entry point:** The **Action** column header in the result tree ([ColumnHeaderRow.tsx](../../frontend/src/components/result/ColumnHeaderRow.tsx)) is the canonical control. **View → Sort by action** in the menu bar ([MenuBar.tsx](../../frontend/src/components/MenuBar.tsx)) mirrors it with **Keep first**, **Delete first** and **Clear sort**. The order and its rules live in [lib/decisionSort.ts](../../frontend/src/lib/decisionSort.ts); the state lives in the `resultView` store slice.
- **Trigger:** The user clicks the Action header, or picks an entry in View → Sort by action.
- **Behaviour:**
  - **The cycle.** A click on the Action header goes to **Keep first**, a second click to **Delete first**, and a third clears the sort.
    - Keep first orders **Keep → Skip → Delete**; Delete first is the reverse.
    - A cleared sort returns every group to its default order: the server's, which is score-descending.
    - The table has **one** sort state. Picking Action replaces a File Name / Size sort and vice versa.
    - The sort applies per group, to all groups at once. Groups keep their order and the group header stays put.
  - **Ties keep the server order.** Rows with the same decision stay in the order `GET /api/manifest` sent them, which is score-descending by default (the user's `sorting.defaults` can change that). Owner decision: there is no separate score tie key, so a configured default is honoured. This is also what satisfies [#743](https://github.com/jackal998/photo-manager/issues/743)'s within-group secondary sort. **Lock is not a sort key**: a locked row sorts by its decision.
  - **The order is spelled.** ▾/▴ means little on a three-value enum, so while the Action sort is active the header reads **ACTION · KEEP FIRST** / **ACTION · DELETE FIRST** (「動作 · 保留優先」 / 「動作 · 刪除優先」). The sub-label truncates before the field name does. The View menu ticks the active entry, and **Clear sort** is disabled while no sort is active.
  - **A decision change never moves a row** (design F3's deferred re-sort). Rows are ordered by the decisions captured when the sort was applied, not by the live ones. So staging Delete on the top Keep row leaves it where it is, instead of pulling the next row under a pointer that is still moving toward an irreversible verb.
    - The header shows a **4px accent (`#a85a2c`) dot** right of ▴/▾, with the tooltip "Order is out of date — click to re-sort" / 「排序已過期 — 點擊重新排序」.
    - The next **click on the header** (or re-picking the ticked menu entry) re-sorts in place **without advancing the cycle**. The rows slide to their new places over 120ms ease-out (skipped under `prefers-reduced-motion`), and the keyboard cursor stays on its row.
    - A **group collapse/expand**, a **filter change** or a **density change** re-sorts silently: the dot clears and nothing animates.
- **Conditions / variants:** The Action sort is **not persisted**, neither across launches nor in `localStorage`; File Name / Size persistence is unchanged. The dot appears only when some row's live decision differs from the one the order was built from, so changing a decision back clears it. Opening or re-opening a manifest (including a scan's auto-load) keeps an active Action sort but starts it fresh: the loaded rows are ordered by their decisions at load time, with no stale dot, and a decision change after that is deferred as above. Owner rulings of 2026-09-29 depart from design F3 and are recorded to design as "FEEDBACK - F1 F3 implementation deviations":
  - the mirror lives in the **View menu**, not the toolbar (the toolbar strip has no width left at 1280px);
  - the buckets are **Keep / Skip / Delete**, because the #584 model has no "undecided" state (`''` *is* keep);
  - the sub-label words are "Keep first" / "Delete first".
- **Related:** [#923](https://github.com/jackal998/photo-manager/issues/923) (design ruling F3, `REPLY - review screen post-implementation.md`); [#743](https://github.com/jackal998/photo-manager/issues/743) (secondary sort); QA scenario [`qa/web/scenarios/s79_decision_sort.py`](../../qa/web/scenarios/s79_decision_sort.py); unit tests `frontend/src/lib/decisionSort.test.ts`, `frontend/src/store/decisionSort.store.test.ts`, `frontend/src/components/ResultTree.decisionSort.test.tsx`.

### Web — manifest decision persistence
- **Area:** Web UI

- **Entry point:** Any per-row decision in the main result tree — the `DecisionControl` button row (three direct-click buttons **Keep / Delete / Skip** — 保留 / 刪除 / 略過 — for the wire values `""` / `"delete"` / `"ignore"`; one click stages the decision with no menu to open, #744; each segment carries the long form in its tooltip) ([frontend/src/components/result/DecisionControl.tsx](../../frontend/src/components/result/DecisionControl.tsx)) or the right-click **Set Action** items — calls `store.setDecision` → `PATCH /api/decision` → `ManifestRepository.batch_update_decisions` ([infrastructure/manifest_repository.py](../../infrastructure/manifest_repository.py)).
- **Trigger:** Automatic — every staged keep/delete/ignore decision is persisted the instant it is made.
- **Behaviour:** The web app has **no explicit Save step and no dirty state**. `PATCH /api/decision` writes `user_decision` to the `migration_manifest` table synchronously (`executemany` + `commit()` + `close()`), and `GET /api/manifest` is stateless — it re-reads the DB on every request ("SQLite is the only source of truth"). A decision therefore survives a full page reload + manifest re-open with no user action: the Zustand store is wiped on reload, yet re-opening the same `.db` re-hydrates the decision from disk. This delivers, by construction, the **guarantee** an explicit Save step would exist for (don't lose review work) — see [Save Manifest Decisions — base flow](file-operations.md#save-manifest-decisions--base-flow).
- **Conditions / variants:** There is deliberately **no** **File → Save Manifest Decisions…** item in the menu bar ([frontend/src/components/MenuBar.tsx](../../frontend/src/components/MenuBar.tsx)): a web "Save" button would only WAL-checkpoint the already-committed DB, so it would be a semantically-hollow affordance that teaches a false "click Save or lose work" model. The backend `POST /api/save` (a WAL-checkpoint / copy-to-new-path utility — `execute_service.py` `save_manifest()`) exists and is store-plumbed but has no UI entry point. The **save-as / export-snapshot** flow (`POST /api/save` with a `target_path`) is the one genuine open product question — tracked as a deferred follow-up, not shipped here. Since [#733](https://github.com/jackal998/photo-manager/issues/733), `PATCH /api/decision` is lock-gated: targeting a locked row is refused under `R-LOCK-1` unless `force_locked`/`skip_locked` is set (see [Execute Action — lock-confirm dialog](execute-action.md#execute-action--lock-confirm-dialog) → Web parity).
- **Related:** See also [Save Manifest Decisions — base flow](file-operations.md#save-manifest-decisions--base-flow); web-port menu-bar parity backlog [#673](https://github.com/jackal998/photo-manager/issues/673) (Save-Manifest sub-item); QA scenario [`qa/web/scenarios/s12_save_manifest.py`](../../qa/web/scenarios/s12_save_manifest.py) (durability across reload + reopen + on-disk commit).

### Web — scan progress throughput / ETA / localized stages (#740)
- **Area:** Web UI

- **Entry point:** The running-state panel inside the scan dialog ([frontend/src/components/scan/ScanProgress.tsx](../../frontend/src/components/scan/ScanProgress.tsx)), fed by the SSE `stage` event's `files_per_sec` field (already captured in `ScanState.filesPerSec`, [frontend/src/store/useAppStore.ts](../../frontend/src/store/useAppStore.ts)) and a receiver-computed ETA ([frontend/src/components/ScanDialog.tsx](../../frontend/src/components/ScanDialog.tsx)). The backend half (stage emission and the throughput window) is under [Scan dialog — stage / throughput / ETA progress (#424)](scan.md#scan-dialog--stage--throughput--eta-progress-424).
- **Trigger:** Automatic while a scan is running — every SSE `stage` event re-renders the panel.
- **Behaviour:**
  - **Localized stage labels.** The raw `stage_name` the backend emits (`WALK`/`HASH`/`EXIFTOOL`/`CLASSIFY`/`SCORE`/`WRITE` — the `core/app_service/scan_runner.py` `STAGE_*` constants) is mapped to a localized label via new `web.scan.stage_*` i18n keys ([translations/en.yml](../../translations/en.yml) / [translations/zh_TW.yml](../../translations/zh_TW.yml)). The lookup lives in [frontend/src/lib/scanProgress.ts](../../frontend/src/lib/scanProgress.ts) (`stageLabel`) and is used at **both** call sites that previously rendered the raw stage id: the scan dialog's status line and the main-window status bar's "Scanning — …" text ([frontend/src/App.tsx](../../frontend/src/App.tsx)). An unrecognised stage name (a future backend stage this build predates) falls back to the raw id, and an empty stage name falls back to "Running…" — the pre-#740 behaviour — rather than crashing or rendering a blank line.
  - **Throughput.** The dialog shows a compact "N files/sec" line (`formatThroughput`, `scanProgress.ts`) — one decimal below 10/s, whole numbers at/above. Hidden entirely (not shown as "—") when the rate is 0 or undefined, e.g. before the first sample.
  - **ETA.** Computed receiver-side as `remaining / files_per_sec` (`formatEta`) and gated by the #424 rule (`ETA_MIN_SAMPLES_SECONDS = 5`): suppressed until the **current stage** has been running ≥5s AND the stage has a known total (`isEtaReady`) — an indeterminate stage (CLASSIFY/SCORE/WRITE, `total=0`) never shows an ETA, since there's no "remaining" to estimate against. The 5s clock is tracked by a new `ScanState.stageStartedAt` timestamp, re-stamped only on a stage **transition** (`useAppStore.ts` `ingestScanEvent`) so a freshly-started stage never inherits the prior stage's settled throughput. Hidden entirely while not yet meaningful; only computed while `scan.status === "running"`.
- **Conditions / variants:** The "N files/sec" number formatting is not routed through the i18n catalog, and neither are the ETA duration text `formatEta` builds (`~2m 05s`) and the "Running…" fallback shown for an empty stage name. **The rest of the panel is (copy audit SC4):** the `ETA …` label (`web.scan.eta_label`), the Cancel button (`web.scan.cancel`), the progress-bar and log `aria-label`s (`web.scan.progress_aria` / `log_aria`), and the indeterminate-stage count line, which now picks its noun per count (`web.scan.files_found_singular` / `_plural`) instead of rendering "1 files found" for the first file. The throughput and ETA rows are each suppressed independently: the throughput hides when the rate is 0, and the ETA also hides until the 5 s gate passes and whenever the stage has no known total. Both are derived in the same render from the same rate, so a rate of 0 hides both.
- **Cancel button:** the same running-state panel renders a **Cancel** button (testid `scan-cancel-button`, bottom-right of the panel) whenever `scan.status === "running"` — [frontend/src/components/scan/ScanProgress.tsx](../../frontend/src/components/scan/ScanProgress.tsx). Leaving the page mid-scan is the other cancel path — see [Main window — close-during-scan confirm](main-window.md#main-window--close-during-scan-confirm). Clicking it calls `store.cancelScan()` → `POST /api/scan/{task_id}/cancel` (`cancel_scan` in [app/web/routes/scan.py](../../app/web/routes/scan.py)), which sets the cooperative `cancel_token` the scan worker polls (returns 404 for an unknown task, 409 if the task is already terminal). The scan pipeline checks the token between stages and — critically — **before the WRITE stage**, so a cancelled scan never writes its output `.db` (`scan_runner.py` logs "Scan cancelled." and returns before the manifest write). On the SSE side this lands as `scan.status = 'cancelled'`; `ScanDialog` reacts by closing itself and calling `resetScan()` (so reopening the dialog re-arms cleanly rather than showing stale sources) — no manifest auto-loads, since `loadManifest` is only invoked on the `'finished'` SSE transition, never on `'cancelled'`. The button only exists while running — it unmounts the instant the panel does, so there is no cancel affordance once a scan is idle/finished/failed.
- **Related:** See also [Scan dialog — stage / throughput / ETA progress (#424)](scan.md#scan-dialog--stage--throughput--eta-progress-424); [#740](https://github.com/jackal998/photo-manager/issues/740); vitest [`frontend/src/lib/scanProgress.test.ts`](../../frontend/src/lib/scanProgress.test.ts) (pure helpers) + [`frontend/src/components/scan/ScanProgress.test.tsx`](../../frontend/src/components/scan/ScanProgress.test.tsx) (rendering, incl. the unmapped-stage fallback); cancel button + endpoint: [app/web/routes/scan.py](../../app/web/routes/scan.py); web scenario [`qa/web/scenarios/s03_cancel_scan.py`](../../qa/web/scenarios/s03_cancel_scan.py) (two samples — HASH-stage and WALK-stage cancel. Both assert a clean dialog close; Sample 1 also asserts the app is left with no rows, and Sample 2 asserts the output manifest was never written).

### Web — scan SSE connection-drop watchdog (#661)
- **Area:** Web UI

- **Entry point:** `useScanSSE` ([frontend/src/hooks/useScanSSE.ts](../../frontend/src/hooks/useScanSSE.ts)), mounted once in `App` for the active scan's `taskId`.
- **Behaviour:** While a scan streams, a client-side watchdog (90s) surfaces a `failed`-status error — *"Lost connection to the scanner. The scan may still be running on the server — reopen Scan to check the result."* — if the SSE stream goes fully silent, so a dead server no longer leaves the scan dialog frozen with no feedback (the error renders via the same `failed`-status surface as a real scan failure; the dialog stays open). The watchdog is reset by ANY incoming event, including a new **named `ping` keepalive** the backend emits every ~30s on an idle stream ([app/web/routes/scan.py](../../app/web/routes/scan.py) `_KEEPALIVE_TIMEOUT_S`). This replaces the previous keepalive *comment*: SSE comments keep the socket warm but fire NO JS handler, so the client could not distinguish "healthy but quiet" (a slow NAS or a big file — legitimately many seconds between progress events) from "server dead". The `ping` yields from the async event loop, decoupled from the scan thread, so it keeps flowing while the server lives regardless of scan speed; it carries no `id`, leaving Last-Event-ID resume untouched. `onerror` is still left to native auto-reconnect (a transient blip recovers via Last-Event-ID replay — see [#687 web parity](execute-action.md#execute-action--partial-execution-via-execute-selected)); only a drop that outlasts the watchdog surfaces the error. The message says the scan *may still be running* because the backend scan runs on a server thread independent of the browser's connection (`disconnect ≠ cancel`).
- **Related:** [#661](https://github.com/jackal998/photo-manager/issues/661). Bug 2 (PR #761) fixed the sibling lifecycle bug — scan status was not reset to `idle` after a scan, so reopening the dialog showed stale sources. Tests: backend [`tests/test_web_scan_routes.py`](../../tests/test_web_scan_routes.py) `test_sse_idle_stream_emits_named_ping_keepalive` (named ping on an idle stream, observed on the wire) + frontend [`frontend/src/hooks/useScanSSE.test.ts`](../../frontend/src/hooks/useScanSSE.test.ts) (fake-timer watchdog: fires after silence, rearms on ping, rearms on a real event, disarms on a terminal event). No live qa scenario — a true server-drop cannot be automated in the shared-server web-scenario batch without breaking co-tenant scenarios; the mechanism is deterministically unit-tested on both ends (server emits `ping` ↔ client watchdog consumes it).

### Web — filesystem browse dialog
- **Area:** Web UI

- **Entry point:** `FsBrowser` ([frontend/src/components/FsBrowser.tsx](../../frontend/src/components/FsBrowser.tsx)), backed by `GET /api/fs/browse` ([app/web/routes/fs.py:12](../../app/web/routes/fs.py#L12) → `core/app_service/fs_browse.py` `browse()`). The web's only filesystem picker — there is no native OS file dialog on the web port.
- **Trigger:** Three flows mount it in three different `mode`s:
  - **`mode="file"`** — Open Manifest, from the menu bar **File > Open Manifest…** and the empty-state **Open Manifest…** button ([frontend/src/App.tsx:486-493](../../frontend/src/App.tsx#L486)); see [Open Manifest — base flow](file-operations.md#open-manifest--base-flow).
  - **`mode="directory"`** — each Scan-dialog source row's **Browse** button (picks a folder to add as a scan source).
  - **`mode="save"`** — the Scan dialog's output-path **Browse** button (picks a folder + types a filename for the output `.db`) — this is also the "in-DOM save-mode picker" already referenced from [Web — scan dialog invalid source path](#web--scan-dialog-invalid-source-path).
- **Behaviour:** Opens at `initialPath` (falling back to its parent directory if that can't be listed, then to the filesystem roots — never dead-ends on an error). The roots view (testid `fs-browser-path` shows "This PC") lists Windows drive letters A-Z that exist, or a single `/` on POSIX. Navigation: clicking a directory entry (testid `fs-browser-entry`, `data-kind="dir"`) descends into it; **Up** (testid `fs-browser-up`, disabled at the roots) returns to `parent`. `directory` mode filters the listing to folders only; `file`/`save` modes also show files, with `.sqlite`/`.db` entries tagged `is_manifest` (a "manifest" pill, case-insensitive on both extensions). Confirm target varies by mode: `directory` → the current folder (disabled at the roots); `file` → the single selected file (double-clicking a file entry confirms immediately); `save` → `<cwd>/<filename>` from the filename input (testid `fs-browser-filename`, disabled until non-blank). **Confirm**/**Cancel** buttons are testids `fs-browser-confirm`/`fs-browser-cancel`. A listing error (e.g. the path was removed between opens) renders inline via testid `fs-browser-error` (`role="alert"`) rather than closing the dialog.
- **Conditions / variants:** **No root restriction (user-visible):** `GET /api/fs/browse` does **not** call the shared `_path_guard.validate_under_roots` helper that gates [`execute`](execute-action.md#execute-action--base-flow), [`image`](preview-pane.md#preview-pane--byte-budget-lru-cache), and [`media`](#web-preview-pane--video-playback-v1-streaming) — `core/app_service/fs_browse.py`'s `browse()` takes any path and lists it (404 if it doesn't exist, 400 if it's not a directory). Concretely: the picker can navigate anywhere on the local filesystem the server process can read, not just the app's configured source/output roots — this is a deliberate scope difference from the mutating/data-serving routes (a directory listing is lower-risk than a file read or a delete), but it IS the kind of filesystem-information-disclosure surface [Web — scan dialog invalid source path](#web--scan-dialog-invalid-source-path) explicitly declined to add elsewhere (`GET /api/fs/stat`) — this endpoint already provides an even broader version of that disclosure, just for directory listings rather than single-path existence checks. The exemption is a recorded decision (2026-07-22) in [fs.py](../../app/web/routes/fs.py)'s module docstring: acceptable while the server binds loopback-only — revisit before any LAN/proxy exposure or privileged execution. A rapid double-click or React StrictMode double-invoke is protected by a monotonic request-sequence guard so a stale response can never clobber a newer directory's listing.
- **Related:** [app/web/routes/fs.py](../../app/web/routes/fs.py); [core/app_service/fs_browse.py](../../core/app_service/fs_browse.py); [app/web/routes/_path_guard.py](../../app/web/routes/_path_guard.py) (the guard this endpoint does NOT use); consuming flows: [Open Manifest — base flow](file-operations.md#open-manifest--base-flow), [Web — ScanDialog source/output persistence](#web--scandialog-sourceoutput-persistence), [Web — scan dialog invalid source path](#web--scan-dialog-invalid-source-path); qa/web scenarios [`s16_open_manifest.py`](../../qa/web/scenarios/s16_open_manifest.py) (file mode via `open_manifest_via_picker`), [`s17_scan_dialog_widgets.py`](../../qa/web/scenarios/s17_scan_dialog_widgets.py) (directory/save modes referenced from the Scan dialog).

### Web preview pane — video transcode fallback (V2 H.264)
- **Area:** Web UI

- **Entry point:** `infrastructure/transcode_service.py` (`TranscodeService`, `_resolve_media_tool`, `_select_h264_encoder`); `.github/workflows/release.yml` + `pyinstaller.spec` (the bundled ffmpeg, #854); `app/web/routes/media.py` (`GET /api/media?transcode=h264`); `frontend/src/components/PreviewPane.tsx`; `frontend/src/components/FullResViewer.tsx`; `frontend/src/components/VideoTile.tsx`; `frontend/src/lib/videoCapabilities.ts` (#787 capability pre-check); `frontend/src/lib/hevcHint.ts` + `frontend/src/components/HevcHint.tsx` (#869 "install HEVC Video Extensions" notice).
- **Trigger:** The browser's `<video>` element fires an `error` event when the native codec cannot decode the source (e.g. HEVC on a browser without the OS H.265 codec pack). Since #787 a second, earlier trigger exists: the transcode `src` is chosen **up front**, with no failed attempt at all, when the capability pre-check has already established that this engine cannot decode HEVC.
- **Behaviour:** On first decode error the frontend swaps the `<video>` `src` from `/api/media?path=…` to `/api/media?path=…&transcode=h264` ONCE (swap-once, never loops). The React `key` includes the transcode flag so the element remounts and re-attempts decode on swap. While the transcode is being prepared, a "Preparing video…" indicator is shown (both PreviewPane and FullResViewer since #737). On a second error (transcode also failed) a terminal "Video cannot be played" message is displayed. The backend lazily transcodes the source to H.264 MP4 using ffmpeg (`libx264 -preset ultrafast -crf 23`, `aac` audio, `-movflags +faststart`) and caches the result under `AppData/Local/PhotoManager/transcodes/v1/<sha1>.mp4`. **Codec passthrough (#853):** on a cache miss the service first asks `ffprobe` once what the source actually holds (`-print_format json -show_entries stream=codec_type,codec_name,pix_fmt`, argv list, 30 s timeout); when the first video stream is already `h264` **in a browser-decodable pixel format** (`yuv420p` or `yuvj420p` — 8-bit 4:2:0) and the FIRST audio stream (if any) is `aac`/`mp3`, the cached MP4 is produced by a stream COPY (`-map 0:v:0 -map 0:a:0? -c copy -movflags +faststart -f mp4`) instead of a re-encode — the video bitstream is copied bit-for-bit, so there is no quality loss and no encode wait. Anything else — HEVC, VP9, AV1, or an audio track the browser cannot decode (PCM, AC-3, Opus) — keeps the `libx264` encode unchanged. **The pixel format is part of the verdict** because `codec_name == "h264"` also covers High 10 / High 4:2:2 / High 4:4:4 (10-bit and 4:2:2 output from Sony and Panasonic bodies and some screen recorders), which no mainstream browser decodes; copying one through would produce a file the `<video>` element refuses. For the same reason the encode now forces `-pix_fmt yuv420p` instead of inheriting the source's — without it libx264 re-encodes a 10-bit source back to 10-bit, so routing it to the encode would have achieved nothing. A missing `pix_fmt` in the probe output counts as "no verdict" and takes the encode. **Cache caveat:** `TRANSCODE_RECIPE_VERSION` was deliberately not bumped for this, so a cache entry created before this change from a non-4:2:0 source keeps its old (still 10-bit) bytes until the source's `mtime` changes or the cache directory is cleared. **Only the first audio stream is judged (#862)** because it is the only one the copy can produce — `-map 0:a:0?` drops every later track — so a camera/screen-recorder file with AAC first and a PCM commentary track second is now remuxed instead of taking a full encode whose output was the same `h264 + aac` pair. A non-copyable FIRST audio track (PCM first, AAC second) still takes the encode. Cache key = `sha1(source_path | mtime_ns)` so the cache auto-invalidates when the file changes. Concurrent requests for the same source serialise on a per-key lock; total concurrent **media sub-processes are bounded to 2 by one `BoundedSemaphore` — the ffprobe verdict shares the cap with ffmpeg since #862**, so a burst of cold requests for distinct files can no longer hold one 30 s-timeout ffprobe each against the same disk (measured before the fix: 8 simultaneous requests → 8 concurrent ffprobe). The source path is validated against allowed roots (path guard) before transcoding; the service-internal cache path is never exposed to the guard. **Where ffmpeg comes from (#854):** the packaged release BUNDLES its own `ffmpeg.exe` + `ffprobe.exe` — `.github/workflows/release.yml` downloads one pinned, SHA-256-verified BtbN win64 **LGPL shared** build (tag `autobuild-2026-09-05-13-10`, asset `ffmpeg-n9.0.1-26-g5c8e7e2433-win64-lgpl-shared-9.0.zip`) and `pyinstaller.spec` ships the two exes, their seven `av*`/`sw*` DLLs and the upstream licence in `_internal\ffmpeg\`. The *shared* variant is deliberate: the static one costs 218 MiB unpacked against 127.9 MiB for the same binaries sharing one set of libraries (measured). The **sub-directory** is deliberate too — the exes resolve their DLLs from their own directory first, and keeping ours in their own `_internal\ffmpeg\` folder is what stopped them resolving against the second FFmpeg DLL set the pre-#646 bundle also carried. `TranscodeService` resolves each tool in a fixed order: `ffmpeg\` next to `photo-manager.exe`, then `_internal\ffmpeg\` (`sys._MEIPASS`), then the same two locations loose, then PATH, then `None` — so a user can override the shipped build by dropping a complete set in an `ffmpeg` folder beside the exe, and a dev checkout still uses PATH exactly as before. Only when all of that finds nothing does the route return `HTTP 501`. Because a *LGPL* build is deliberately compiled `--disable-libx264` (x264 is GPL), the encoder is no longer hard-coded: the service asks the resolved binary once (`ffmpeg -encoders`, at init) and uses `libx264` when present (dev machines, CI, chocolatey/apt builds — the historical `-preset ultrafast -crf 23` recipe unchanged) and Cisco's `libopenh264` otherwise (`-b:v 4M`, the bundled build's software H.264 encoder); a probe that cannot run falls back to the historical recipe. Both recipes still force `-pix_fmt yuv420p` and `aac` audio, so the output is the same browser-playable shape either way. The encode is fully synchronous — the first byte waits for the whole file — so the `ultrafast` preset (#737) minimises the first-view stall on the owner's ~99%-HEVC library (output size is irrelevant for a throwaway cached stream); repeat views are near-instant cache hits. A passthrough remux is synchronous too but is I/O-bound rather than CPU-bound: measured on a 10 s 720p clip through the real route on a cold cache, first-byte was 0.14 s for the stream copy against 0.47 s for the encode of the byte-identical video stream (`curl -w '%{time_starttransfer}'` against `GET /api/media?...&transcode=h264`; both clips carried the same testsrc video stream, one with AAC audio and one with PCM to force the encode — see #853). Progressive streaming + a real progress % is a tracked follow-up.
- **Conditions / variants:** The fallback only fires on error — native-codec sources play without transcoding overhead. The `mediaUrl(path, { transcode: "h264" })` helper in `client.ts` appends `&transcode=h264`; zero-arg callers are unaffected (backward-compatible). **Capability pre-check (#787):** `frontend/src/lib/videoCapabilities.ts` asks `navigator.mediaCapabilities.decodingInfo` once per page life (module-level memo, shared by all three video surfaces) whether the engine can decode HEVC — `video/mp4; codecs="hvc1.1.6.L93.B0"`, then `hev1…`, at 1080p30. The result is three-state: a real "no" from the API is `unsupported`; a missing API (jsdom, pre-2019 engines) or a throwing/rejecting call stays `unknown`. Only `unsupported` changes anything, and only for `.mov` / `.m4v` sources — the Apple containers that are HEVC in practice for this library. `.mp4` is deliberately excluded (it carries H.264/VP9/AV1 just as often, and a wrong preempt costs a pointless ffmpeg encode, or a terminal "Video cannot be played" when ffmpeg is missing, on a file that would have played natively). The probe is never awaited before the first paint: until it resolves the surfaces use the original-bytes `src` exactly as before. PreviewPane and FullResViewer read the hint when the selected path changes; VideoTile reads it at click time (when its `<video>` is created). **Two-attempt contract (#787):** the error swap is now direction-aware — whichever source the element STARTED on, the first `error` swaps to the other one, and only the second error is terminal. A native start that fails swaps to the transcode (the long-standing behaviour); a hint-chosen transcode start that fails swaps back to the original bytes. That second direction is what makes the hint safe to be wrong: stock Chrome on Windows reports HEVC unsupported without the paid extension, so a preempted `.mov` whose transcode is unavailable would otherwise hit `HTTP 501` and go terminal even when its bytes are plain H.264 that the browser could have played. The contract still applies where ffmpeg genuinely is missing — a dev checkout without ffmpeg on PATH, or a bundle whose binaries were removed — even though the packaged release now ships its own (#854, below). Exactly one swap is allowed in either direction — it can never loop. **Why the passthrough still returns an MP4 (#853):** the endpoint could have handed back the source bytes instead, but that breaks the files it aims to help. `.avi` is a walked video extension (`scanner/media.py`) and no browser demuxes AVI, and Firefox does not demux QuickTime, so an H.264 `.mov` served raw fails there while today's encode works — and the two-attempt swap cannot rescue either case, because the source it swaps to is byte-identical to the one that just failed. Remuxing keeps the universally-playable MP4 container, needs no frontend change, and still deletes the encode. A stream copy that ffmpeg refuses falls through to the encode, so the passthrough can never leave a file less playable than it was before #853. **Native-decode notice (#869):** on Windows, Chrome / Edge / WebView2 decode HEVC through Media Foundation as soon as the Microsoft Store package "HEVC Video Extensions" is installed — the browser then streams the original bytes with hardware decode: no ffmpeg encode, no first-byte stall, no read-back, no `transcodes/v1/` growth. Until #869 nothing said so, so on those machines the transcode was silently the default rather than the safety net. Now, the first time in a page life that any of the three surfaces actually plays the transcode (the #787 up-front choice or the reactive swap), and only when the probe's verdict is a real `unsupported` AND the platform is Windows (`navigator.userAgentData.platform`, falling back to the UA string for Firefox), the preview pane shows ONE non-blocking notice under its title strip: «This browser cannot decode HEVC; videos are being converted first. Install *HEVC Video Extensions* from the Microsoft Store for native playback.»／「此瀏覽器無法解碼 HEVC，影片會先轉檔再播放。從 Microsoft Store 安裝 *HEVC 視訊延伸模組* 即可直接播放。」 The product name is a link to `ms-windows-store://pdp/?productid=9NMZLZ57R3T7` — the retail "HEVC Video Extensions" (the free `9N4WGH0Z6VHQ` "from Device Manufacturer" variant is an OEM preinstall that is not offered to every machine, so it is not linked; both ids checked on apps.microsoft.com 2026-09-30). Two buttons sit below it: **Dismiss** (gone for this page life) and **Don't show again** (also persists `pm.hevc-hint.dismissed.v1 = "1"` in localStorage, so it does not show again in this browser. In the packaged app pywebview runs in private mode (`launcher.py` does not override it), so localStorage is wiped on every launch and the choice lasts one launch; see #944). `supported` and `unknown` (API missing or threw) never show it — the three-state contract is unchanged — and a transcode that happens while the probe is still unanswered does not use up the one showing. It is the Q9 caution banner (the shared `CAUTION_BANNER` frame, ▲ glyph, caution tokens only) with its actions as ordinary outline buttons below it, per «caution never becomes a button». ### Web preview pane — video playback (V1 streaming)
- **Area:** Web UI

- **Entry point:** `app/web/routes/media.py` (`GET /api/media`); `frontend/src/components/PreviewPane.tsx`; `frontend/src/components/FullResViewer.tsx`.
- **Trigger:** Selecting a file row whose `media_type === "video"` in the web result tree.
- **Behaviour:** The web inline preview pane renders a native `<video controls>` element (instead of `<img>`) for video rows. The video source is `GET /api/media?path=<encoded-path>`, which streams the original file bytes with HTTP Range/206 support so the browser can seek without downloading the whole file. No autoplay — see [Preview pane — no-autoplay video default](preview-pane.md#preview-pane--no-autoplay-video-default) (PR #624). The FullResViewer overlay also renders `<video controls>` for video rows (instead of the `<img>` + pan/zoom chrome). `media_type` is derived server-side from `scanner/media.VIDEO_EXTENSIONS` (the canonical walked set: `.mp4`, `.mov`, `.m4v`, `.avi`) and returned in every `FileRow` payload from `GET /api/manifest`.
- **Conditions / variants:** `GET /api/media` reuses the same allowed-roots path guard as `GET /api/image` (403 on traversal, 400 on empty path, 404 on missing file). Range support: no Range header → 200 full file; `Range: bytes=START-END` → 206 with `Content-Range`; open-ended `bytes=START-` → 206 to EOF; suffix-range `bytes=-N` → 206 last N bytes; unsatisfiable range (start ≥ size, `bytes=-`, `bytes=-0`) → 416. Content-Type is resolved from extension (`.mp4` → `video/mp4`, `.mov` → `video/quicktime`, `.m4v` → `video/x-m4v`, `.webm` → `video/webm`, `.avi` → `video/x-msvideo`, `.mkv` → `video/x-matroska`). V1 serves original bytes only — no transcoding. Since #787 the *initial* `src` is not unconditionally the original-bytes URL: a `.mov` / `.m4v` row starts on `&transcode=h264` when the HEVC capability pre-check has positively established this engine cannot decode HEVC — see [Web preview pane — video transcode fallback (V2 H.264)](#web-preview-pane--video-transcode-fallback-v2-h264).
- **Related:** `app/web/routes/media.py`; `core/app_service/review_view.py` (`media_type` field); `scanner/media.py` (`is_video`, `VIDEO_EXTENSIONS`); `frontend/src/api/client.ts` (`mediaUrl`); `frontend/src/api/types.ts` (`FileRow.media_type`); QA scenario [`qa/web/scenarios/s69_video_playback.py`](../../qa/web/scenarios/s69_video_playback.py); fixture [`qa/sandbox/video-playback/clip.mp4`](../../qa/sandbox/video-playback/clip.mp4) (VP9-in-MP4, 2 s).

### Web preview pane — group grid view (multi-tile)
- **Area:** Web UI

- **Entry point:** `frontend/src/components/GroupGrid.tsx`; `frontend/src/components/VideoTile.tsx`; `frontend/src/components/ImageTile.tsx`; `frontend/src/store/` (`PreviewState.selectedGroupId`); `ResultTree.tsx` group-row click handler (`setSelectedGroup` + `toggleGroup`).
- **Trigger:** Clicking a GROUP header row in the main result tree (the collapse-toggle button, `data-testid="row-group-{N}"`). A group-row click calls both `toggleGroup(groupNumber)` (expand/collapse) AND `setSelectedGroup(groupNumber)` (switches the PreviewPane to grid mode via `PreviewState.selectedGroupId`). Clicking a FILE row within the group switches back to single-file preview mode (`setSelectedGroup(null)` + `setSelectedFile(path)`).
- **Behaviour:** The PreviewPane renders a scrollable tile grid (`data-testid="grid-container"`) containing one tile per group member. Tile sort order: VIDEO tiles first (sorted by aspect bucket — landscape → square → portrait — then by larger-file-first within each bucket), IMAGE tiles after (larger-file-first). Each **VideoTile** (`data-testid="grid-video-tile-{groupId}-{basename}"`) shows a poster frame — `row.thumbnail_url` (`/api/image?path=…&size=512`) rendered as `<img data-testid="{tile-testid}-poster">` — behind a click-to-play affordance. `/api/image` falls through to the Shell/WIC thumbnail provider for video paths too: after the two thumbcache-oriented `GetImage` attempts, a bare-`RESIZETOFIT` rescue attempt (flags=0) succeeds where they fail, so the poster is typically a real decoded frame (`infrastructure/image_service.py`). If the poster fails to load the tile's `onError` handler falls back to the dark background (the ▶ glyph shows either way). Clicking a VideoTile mounts a `<video data-testid="{tile-testid}-video" src="/api/media?path=…">` element inside the tile, autoplays it, and registers the element with the GroupMediaController. Each tile maintains its own independent transcode-fallback state (a `[useTranscode, videoFailed, canPlay]` triple — identical to `PreviewPane.tsx`'s pattern, replicated per tile; React rules-of-hooks forbid looped hook calls, so each tile is its own child component). Each **ImageTile** (`data-testid="grid-image-tile-{groupId}-{basename}"`) shows the thumbnail (`/api/image?path=…&size=512`) and opens the full-res viewer on double-click (the same `store.openFullRes` the single-view double-click calls). The GroupMediaController bar (`data-testid="gmc-bar"`) appears below the grid IFF at least one video tile is present in the group. Video tiles decode lazily: a tile is a static poster until clicked, so no group broadcast (pause/play/seek) reaches a tile that has not yet been clicked/mounted — this avoids an N-way HEVC decode storm on grid load.
- **Conditions / variants:** An empty group (0 members after singleton-drop) never reaches the manifest and therefore never triggers grid mode. A single-member group is also dropped by the scanner (singleton-drop); the grid only renders for groups with >= 2 members. When `selectedGroupId` is null (no group row selected, or a file row was selected instead) the PreviewPane falls back to the existing single-file preview or empty state. The GroupMediaController is absent when the group contains no video members (image-only groups show the tile grid without the controller bar).
- **Related:** [#734](https://github.com/jackal998/photo-manager/issues/734); `frontend/src/components/GroupGrid.tsx`; `frontend/src/components/VideoTile.tsx`; `frontend/src/components/ImageTile.tsx`; `infrastructure/image_service.py` (`_SHELL_GETIMAGE_FLAG_ATTEMPTS` rescue); `frontend/src/store/types.ts` (`PreviewState.selectedGroupId`); `frontend/src/components/ResultTree.tsx` (group-row click handler); `qa/web/testid_constants.py` (`GRID_CONTAINER`, `GMC_BAR`, `grid_video_tile_testid`, `grid_image_tile_testid`); QA scenario [`qa/web/scenarios/s71_grid_video_tiles.py`](../../qa/web/scenarios/s71_grid_video_tiles.py); component tests [`frontend/src/components/VideoTile.test.tsx`](../../frontend/src/components/VideoTile.test.tsx); unit test [`tests/test_image_service.py`](../../tests/test_image_service.py) (`TestShellGetImageFlagAttempts`).

### Web preview pane — group sync controller (GroupMediaController)
- **Area:** Web UI

- **Entry point:** `frontend/src/components/GroupMediaController.tsx`; `frontend/src/components/VideoTile.tsx` (register/unregister callbacks). Rendered by `GroupGrid.tsx` below the tile grid when `hasVideo` is true.
- **Trigger:** Mounted automatically when the GroupGrid renders and at least one VideoTile is present. Each VideoTile registers itself with the controller when its `<video>` element is mounted (click-to-play) and unregisters on unmount.
- **Behaviour:** Six pure helper functions in `frontend/src/lib/groupMediaSync.ts`:
    1. `isMajorityPlaying(playing, total)` — `total > 0 && playing > total >> 1` (strict; drives the group play/pause glyph).
    2. `shouldUpdateMasterDuration(newDur, curDur)` — `newDur > curDur` (master duration = MAX across all registered players).
    3. `shouldTrackPlayerPosition(dragging, isPlaying)` — `!dragging && !isPlaying` (idle-only slider sync).
    4. `computeMasterPosition(ratio, masterDur)` — `masterDur <= 0 ? null : Math.trunc(ratio * masterDur)` (ms; truncates toward zero).
    5. `computeMuteTargetVolume(cur, defaultUnmute = 0.5)` — `cur > 0 ? 0 : 0.5` (0..1 scale; the controller's 0–100 slider shows it as 50).
    6. `volumeIconForValue(v)` / `playButtonIconForState(p)` — glyph selectors.
  **Play/pause** (`data-testid="gmc-play-pause"`): clicking broadcasts `play()` or `pause()` to ALL registered tile `<video>` elements. The majority-vote glyph (`isMajorityPlaying`) shows pause when most tiles are playing and play otherwise.
  **Master progress slider** (`data-testid="gmc-progress-slider"`, `min=0 max=<masterDuration_ms>`): committing a scrub calls `seekAll(ms)` on all registered elements, setting each tile's `<video>.currentTime = ms / 1000`. The seek fires on RELEASE only — on pointer-up (`onMouseUp`) for a mouse drag and on key-up (`onKeyUp`) for keyboard scrubbing (arrow keys / Home / End on a focused slider, for accessibility). Continuous drag (`onChange`) updates only the current-time label, never seeks, so playback is not clock-locked mid-drag. The idle-only position tracking (`shouldTrackPlayerPosition`) updates the slider from a registered tile's `currentTime` only when the slider is not being dragged and the AGGREGATE majority-playing state is idle (read live via a ref so the `timeupdate` listener never sees a stale value). The master duration is the MAX across all registered players, and it is reconciled DOWN to the surviving max when the longest-duration player detaches (unregister).
  **Threshold group-autoplay**: each VideoTile autoplays its own `<video>` on click (the `autoPlay` attribute) the moment it mounts. Separately, once EVERY VideoTile in the group has been mounted and registered (registry size reaches `expectedPlayerCount`, the group's video-tile count), the controller fires `playAll()` ONCE (a one-shot ref guard prevents re-fire on further registry churn or re-renders), which calls `play()` on every mounted tile. It does not seek or reset `currentTime`, so tiles keep their own positions. Because broadcast reaches only mounted tiles, this group `playAll()` only occurs after the user has clicked through all tiles.
  **Shared volume** (`data-testid="gmc-volume-slider"`, 0–100): changing the slider broadcasts `videoEl.volume = value / 100` to all registered tiles. The mute button (`data-testid="gmc-mute-button"`) toggles the shared volume between 0 and a fixed default (50) via `computeMuteTargetVolume` (un-mute always restores the fixed default, NOT the pre-mute value — deliberate).
  **Current time / duration display** (`data-testid="gmc-current-time"` / `data-testid="gmc-duration"`): formatted as `MM:SS` (or `HH:MM:SS` when duration exceeds one hour).
- **Conditions / variants:** The controller is absent when the group contains no video tiles. Tiles that have not yet been clicked (and have not mounted their `<video>`) are not registered and therefore not included in the majority-vote or broadcast. The per-tile independent transcode-fallback state is NOT shared via the controller — each tile manages its own `[useTranscode, videoFailed]` state. If all tiles fail to decode, the controller remains visible but broadcasts to an empty set (no-op).
- **Related:** `frontend/src/components/GroupMediaController.tsx`; `frontend/src/lib/groupMediaSync.ts` (the 6 pure TS functions) + unit tests [`frontend/src/lib/groupMediaSync.test.ts`](../../frontend/src/lib/groupMediaSync.test.ts); `frontend/src/components/VideoTile.tsx`; `qa/web/testid_constants.py` (`GMC_BAR`, `GMC_PLAY_PAUSE`, `GMC_PROGRESS_SLIDER`, `GMC_CURRENT_TIME`, `GMC_DURATION`, `GMC_MUTE_BUTTON`, `GMC_VOLUME_SLIDER`); QA scenario [`qa/web/scenarios/s71_grid_video_tiles.py`](../../qa/web/scenarios/s71_grid_video_tiles.py) (group pause/play broadcast + master-scrub convergence via the React-tracked slider setter + keyup release); component test [`frontend/src/components/GroupMediaController.test.tsx`](../../frontend/src/components/GroupMediaController.test.tsx) (out-of-order duration MAX, one-shot autoplay guard, listener cleanup).
