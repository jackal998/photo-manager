# Features — File operations

Entries for the **File operations** area of the feature inventory. The index and the section schema are in [`../features.md`](../features.md).

### Open Manifest — base flow
- **Area:** File operations

- **Entry point:** Menu bar **File > Open Manifest…** (`menu-file-open`) and, while no manifest is loaded, the empty-state **Open Manifest…** button (`main-empty-open`, see [Empty-state action buttons](main-window.md#empty-state-action-buttons)). Both open the in-page [Web — filesystem browse dialog](web-ui.md#web--filesystem-browse-dialog) (`FsBrowser`, `mode="file"`). A secondary route is the toolbar's manifest-path field (`main-manifest-input`) and its **Open** button (`main-manifest-open-button`) in [frontend/src/components/Toolbar.tsx](../../frontend/src/components/Toolbar.tsx). That pair is the first thing the toolbar sheds on a narrow window, since the picker duplicates it.
- **Trigger:** User confirms a file in the picker, or types a path and clicks **Open** or presses Enter.
- **Behaviour:** Every route calls `store.loadManifest(path)` → `GET /api/manifest?path=…` → `load_review`. The picker route also writes the chosen path into the toolbar field; the post-scan auto-load does not, so after a scan the field can still show an older path. The field route trims its input and does nothing on an empty path. The picker is seeded with the field's current value. While a first load runs (no manifest on screen yet), the status bar reads "Loading manifest…"; loading over an already-loaded manifest keeps its summary on the bar until the new one arrives. On success the store replaces the groups and counts wholesale and clears the row selection, and the status bar shows the groups · files summary (see [Main window — status bar baseline](main-window.md#main-window--status-bar-baseline)). The server also registers the manifest's folders as allowed roots, so the image routes will serve its thumbnails. A failed load (400 empty path, 404 missing file, 422 load error) leaves the previous manifest on screen and shows the error in `main-status-error`. There is no native file-type filter: `FsBrowser` tags `.sqlite` / `.db` files (case-insensitive) with a "manifest" pill but still lists every file.
- **Conditions / variants:** No confirm fires when a manifest is already loaded. Every decision is already on disk (see [Web — manifest decision persistence](web-ui.md#web--manifest-decision-persistence)), so the new manifest simply replaces the old one in the view. The preview pane takes its row from the loaded groups: the single view renders only if the selected path is found there, and the group grid looks its group up by number. So a file from the previous manifest cannot stay rendered — the web form of [#431](https://github.com/jackal998/photo-manager/issues/431). The preview selection itself is not reset, so a group-grid preview whose group number also exists in the new manifest shows that manifest's group. Old manifests without the newer columns auto-migrate on load, and rows missing the cached size / dates / mtime fall back to per-row filesystem reads; re-scan once for the load-time speed benefit.
- **Recycle-bin / system-folder rows are dismissed on open ([#821](https://github.com/jackal998/photo-manager/issues/821)):** every row whose path sits under a walker skip directory (see [Scan walk — recycle-bin / system folders are never walked](scan.md#scan-walk--recycle-bin--system-folders-are-never-walked)) is written `outcome='ignored'` when the manifest is opened, using the walker's own rule. The pass runs inside every manifest load, so it also re-runs on each reload after a decision, and is a no-op write once the manifest is clean. The walk-time skip only ever stopped NEW rows; a manifest built before it kept the old ones live — scored, groupable, selectable as a group's keeper, and offered as delete targets `send2trash` then refuses. A rescan does not fix them either: it replaces the manifest file wholesale (losing every decision), so the reconcile is what makes an existing manifest correct without a multi-hour NAS re-scan. **The change is visible in two ways:** the review-set count drops on the first open after upgrading (on the author's 40,774-row manifest, 3,952 rows were dismissed and the loaded record count went 24,531 → 21,498), and a group whose only surviving partner was a recycle-bin file drops below two members and leaves the review set with it (the existing orphan-skip — 584 of those 3,033 rows). It is idempotent (a second open dismisses 0), never re-opens a row already finalised `deleted` — including one finalised by a concurrent execute batch after the reconcile read its candidate list — and touches no filesystem (path strings only, so an offline NAS costs nothing). **It is also fail-soft:** if the manifest cannot be written (a read-only file, a locked DB), the dismissal is skipped with a WARNING naming the manifest and the manifest still opens with those rows live, exactly as before this change — housekeeping the user did not ask for never turns an openable manifest into an unopenable one. A group that holds a locked row is left whole: none of its rows is dismissed, so the locked row stays in review, locked and visible, and the open's log line reports how many skip-directory rows were left in place (`R-LOCK-6`, [#982](https://github.com/jackal998/photo-manager/issues/982)). Known divergence: the reconcile has no scan root to bound with, so a manifest whose source root sits INSIDE a skip directory has its rows dismissed on open, where the walker would have indexed them; `UPDATE migration_manifest SET outcome='' WHERE …` restores them.
- **Related:** Foundation in [PR #12](https://github.com/jackal998/photo-manager/pull/12); preview clear [#431](https://github.com/jackal998/photo-manager/issues/431) (desktop origin). QA scenarios [`qa/web/scenarios/s16_open_manifest.py`](../../qa/web/scenarios/s16_open_manifest.py) (scan → reload → reopen through the `FsBrowser` picker from the empty state; the status bar after reopening equals the one after the scan) and [`qa/web/scenarios/s24_stale_manifest_paths.py`](../../qa/web/scenarios/s24_stale_manifest_paths.py) (stale paths). Open-time reconcile ([#821](https://github.com/jackal998/photo-manager/issues/821)) pinned by `tests/test_manifest_skip_reconcile.py`; the `outcome` column it writes comes from [#584](https://github.com/jackal998/photo-manager/issues/584). Route `GET /api/manifest` in `app/web/routes/review.py`.

### Save Manifest Decisions — base flow
- **Area:** File operations

- **Entry point:** None — removed with the desktop client in #646. The web menu bar deliberately has no **File > Save Manifest Decisions…** item ([frontend/src/components/MenuBar.tsx](../../frontend/src/components/MenuBar.tsx)).
- **Trigger:** None.
- **Behaviour:** The retired desktop client held decisions in memory and wrote them through a file picker, either in place or as a copy at a new path, clearing its dirty flag. The web has no save step and no dirty state: every decision is written to the manifest's SQLite the moment it is made (`PATCH /api/decision`), so there is nothing to save — see [Web — manifest decision persistence](web-ui.md#web--manifest-decision-persistence).
- **Conditions / variants:** The backend keeps `POST /api/save` (`save_manifest` in [core/app_service/execute_service.py](../../core/app_service/execute_service.py)). With no `target_path` it runs `PRAGMA wal_checkpoint(FULL)` and returns the number of in-review rows. With a `target_path`, which must pass the allowed-roots check, it checkpoints and then copies the manifest file there. The store wraps it as `saveManifest`, but no component calls it, so it has no UI entry point; a save-as / export-snapshot affordance is the open product question noted in that section.
- **Related:** Desktop dirty-flag plumbing in [PR #158](https://github.com/jackal998/photo-manager/pull/158); web menu-bar parity backlog [#673](https://github.com/jackal998/photo-manager/issues/673) (Save-Manifest sub-item); QA scenario [`qa/web/scenarios/s12_save_manifest.py`](../../qa/web/scenarios/s12_save_manifest.py) (a decision survives page reload + manifest reopen and is committed on disk).
