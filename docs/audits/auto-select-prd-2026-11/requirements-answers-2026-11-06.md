# Auto-select 需求問卷 — owner 的答案（2026-11-06）

來源：問卷 artifact 的匯出（owner 填寫，原文照錄，只調整排版）。這份是下一版 PRD 的事實依據；
PRD §5/§9/§10 與 direction-review.md 在此之前的內容視為暫定。

## A. 成功的樣子

- **A1** 掃描完成、打開 view 的那一刻，你期待看到什麼？ → 其他：預設模式只有 group、不會勾選 action；
  auto-select 模式會決定大多數的 action，然後列出使用者要特別注意的項目確認；auto-select-aggressive 會直接
  決定所有的 action。所有的 action 都需要我按下執行才會做動作。
- **A2** 可接受多少比例的群要人看？ → 看情況：要先定義出信心水準，這跟比例無關；超標的分群就是需要人看。
  App 不能決定別人的喜好。
- **A3** 選錯的代價？ → 可以接受偶發（回收桶／undo）。App 不負責這件事，只按照品質判斷；喜好無從決定；與照片
  類型無關。
- **A4** 上次選錯／必須手動看的例子？ → 上次最嚴重的都是分群分錯，所以基本上都是手動看。而且很確定目前有很多
  其實色調已經調整過的照片被當作 100% 符合（EXACT），這是不對的：它們必須是「近似」，不可以是「完全相同」。

## B. 一個群裡「好」的定義

- **B1** 挑 keeper 時看什麼？ → 全選（清晰度／對焦、曝光、構圖、表情／眼睛、解析度與格式、原檔 vs 編輯、完整性）
  加：metadata 完整度跟正確性、檔名真實性、時間正確性。
- **B2** 畫質與 metadata 衝突 → 兩張都留。
- **B3** byte 相同的複本直接 DELETE？ → 可以直接標 DELETE，但也會有其他優先級要考慮：哪一個資料夾優先、
  metadata 完整性（不限於這兩個）；需要累積樣本判斷。
- **B4** RAW + JPEG → 都留。
- **B5** 連拍 stack → 預設全留（現狀）。
- **B6** Live Photo 的 MOV → 跟著它的照片走。
- **B7** 截圖群 → 跟一般照片一樣處理。
- **B8** 有人／寵物 → 只有引擎信心很高時才能標 DELETE：必須完全 dup 才能刪除。當時會這樣決定是因為量不大、
  不佔空間，分群還不夠好時乾脆都不刪。
- **B 區總結（owner）**：整個 B 區可能因人而異；到時候看是否在 advanced setting 多一個「偏好」選項讓使用者自己
  決定。我們這邊就是預設值，但不要寫死：讓這些功能都像外掛一樣可以調整，要這條規則就引用，不然就忽略。

## C. 引擎

- **C1** 誰決定 → 不確定，用測試結果決定。
- **C2** 本機 vs 雲端 → 一定要有純本機模式，而且品質要可用。
- **C3** 可選的供應商／模型 → 全選（Claude、OpenAI、Gemini、本機開源、IQA／美學引擎）；品質價格都是考量，優先
  嘗試本地模型，真沒辦法再去研究雲端模型串接。
- **C4** 模型選擇放哪 → 設定頁讓使用者自己選供應商與模型。
- **C5** 引擎不確定時 → 可以說「不確定」→ 標 REVIEW 讓人看。
- **C6** 什麼時候跑 → 掃描流程的一部分：掃完，view 就是標好的。
- **C7** 一次全庫掃描可接受的雲端花費 → < $1。
- **C8** 可以讓掃描變慢多少 → 無所謂，掃描本來就跑很久。

## D. 輸出與 UI

- **D1** view 裡要看到 → action、一句理由、信心高低。
- **D2** auto-select／aggressive 兩模式與新引擎 → 與引擎無關，引擎是另一個選項。
- **D3** 引擎的 keeper 自動鎖定？ → 不要。
- **D4** decision log（理由、模型） → 必要。

## G. 優先序與範圍

- **G1** 第一個該做的 → 純本機模式。
- **G2** 範圍 → 照片 + 影片 + 截圖。
- **G3** 「完成」的樣子 → 1. 在選單列出足夠多的情境，讓使用者自己在特殊環境取捨或表示偏好。2. auto-select 永遠只會
  選擇，它只是無情的選擇機器，不會預設現在在看什麼內容。3. 有機械化的 gate，也有接近人為對「值得留下」的判斷，
  一樣列出成本代價讓使用者選擇。目標比較像是把功能都做出來，但讓使用者清楚知道代價跟副作用、自己判斷要不要，
  然後套用，按照這套規則去做 auto-select。目標是降低選擇負擔；這套標準理論上應該可以 cover 90% 的「近似到需要
  作選擇」的情境。
